# Milestone 4 — first playable build (0.5-m4)

The owner ran 0.4-m3 on his POCO F5 and the game genuinely booted: disc
mounted from the app-copy ISO, SYSTEM.CNF + SLUS_215.03 loaded, IRX modules
up, McPort linked, and the real Dolby intro splash on screen. His three
complaints define this build: the picture is portrait and letterboxed,
there is nothing to press (keyboard-bound input, "no host gamepad backend
on Android yet" in the log), and it runs the boot-test performance shape
(headless, 120 s limit, GS scale 3, vsync off).

0.5-m4 turns the boot test into a play session: landscape fullscreen, no
time limit, sound on, internal resolution scale 1, a full touch overlay,
and physical-gamepad support — all on the same package, signer and ISO
copy as 0.4-m3, so it installs as an update and the disc copy is reused.

## The input seam, and how the overlay feeds it

The gap the log named ("[input] no host gamepad backend on Android yet")
is `ps2_host_gamepads` in the runtime
(`runtime/ps2xRuntime/src/lib/ps2_host_gamepads.cpp`): the port's one
host-pad seam. The guest never reads it directly. The chain is:

guest SIO2 polling (the modes 0x41/0x73/0x79 exchanges the 0.3/0.4 logs
already show) → `ps2_host_input::sample()` builds the guest pad from
per-control bindings → each binding asks `ps2_host_gamepads` for a host
device's button/axis, or raylib for a keyboard/mouse source.

The finding that shaped this milestone: player 1's default bindings
(`godhand.ini`'s controls section, `controls.ini` on the phone) already
map EVERY control twice — once to a keyboard key and once to "SDL-0",
device 0 of this seam: face buttons to FaceNorth/East/South/West,
Select→Back, Start→Start, L1/R1 to the shoulders, L2/R2 to the
+trigger axes, both sticks to the matching axes, L3/R3 to the stick
clicks. So the overlay did not need new bindings at all — it needed
device 0 to exist on Android.

What was built:

- `runtime/ps2xRuntime/src/lib/ps2_android_touch.h` — the small shared
  state: a presence flag plus one pad snapshot (button bitmask where
  bit i is the seam's `Button` i, four stick axes −1..1 down/right
  positive, two trigger axes 0..1), held in atomics. The overlay side
  writes it whenever a touch changes; the game side reads it inside
  `sample()`, so no locking sits on the frame path.
- The Android branches of `ps2_host_gamepads` now answer from that
  state: device 0 is `connected()` while a source is present,
  `button()` tests the bitmask, `axis()` returns the stored axes,
  `devices()` names it "On-screen touch controls", and the update()
  log line now reads "host gamepad 0 is the on-screen touch overlay
  (Android)". The desktop SDL backend is untouched.
- JNI in the glue: `TouchPad.nativeSetPresent/nativeSetState`.
- Java `TouchPad` — holds one state per source (overlay, gamepad),
  merges them on every change and pushes the merged snapshot:
  buttons are OR-ed (neither source can release the other's press),
  each stick belongs to the source that last pushed it firmly and
  falls back to the other when it centres, triggers take the max.
- Java `TouchOverlay` — a frame over the game surface in GameActivity.
  The root lets gaps fall through to the game; each control claims
  only its own touches, so stick + button together (multi-touch)
  works. Layout, sized for landscape thumbs: left stick bottom-left
  (movement), right stick bottom-right beside the face diamond
  (God Hand's dodge stick — it ships, not skipped), face diamond
  △ ○ × □ bottom-right, L1/L2 left and R1/R2 right along the top
  edge, Start/Select small at top-centre, all semi-transparent.

Two details worth knowing:

- L2/R2 are axes in this seam, not buttons — the default bindings read
  them as "+LeftTrigger/+RightTrigger pressed past a threshold". The
  overlay's L2/R2 pills therefore write the trigger axes (1.0 while
  held), and a gamepad's analog brake/throttle axes land in the same
  place.
- Menus in this port are navigated with the D-pad (the desktop layout
  comment says the D-pad exists "so the menus can be navigated"), and
  by default only the keyboard arrows drive it. So the overlay's left
  stick also presses the matching D-pad direction past 0.55 deflection
  — menus move with the stick, and in game the D-pad doubles are the
  game's own D-pad actions. A real D-pad (hat or keys) drives the same
  bits directly.

Rumble: `setRumble` on Android stores the motor levels and never plays
them (there is no vibrator wiring yet); the bindings' motor sources are
satisfied, nothing crashes, nothing buzzes.

## Physical gamepad

GameActivity's `dispatchKeyEvent` / `onGenericMotionEvent` take events
from gamepad-class sources (SOURCE_GAMEPAD / SOURCE_JOYSTICK /
SOURCE_DPAD) and write the second TouchPad source, standard mapping:
A cross, B circle, X square, Y triangle, Start, Select, L1/R1 buttons,
L2/R2 buttons or AXIS_BRAKE/AXIS_THROTTLE (whichever pushes further),
D-pad keys or the hat axes, AXIS_X/Y left stick and AXIS_Z/RZ right
stick with a 0.15 deadzone rescaled to full tilt, stick clicks L3/R3.
The first gamepad event of a session writes one boot-log line —
"gamepad input seen: <device name>" — so a controller test proves the
path from the log alone. If a controller disconnects mid-press, an
input-device listener clears the gamepad source so nothing sticks;
pause does the same for both sources. Pair the controller before or
after opening the game — both fine, it joins on its first press.

## The play session, and the effective render settings

The glue now pins the session shape with overwrite, because the
godhand.ini already sitting on the phone says Headless=1,
TimeLimitSeconds=120, InternalResolution=3 — set by the boot-test
builds — and real environment variables beat the ini in the port's
settings chain. Forced for 0.5-m4:

| Setting | Value | Why |
| --- | --- | --- |
| GODHAND_HEADLESS | 0 | windowed play: visible window, audio unmuted, vsync default on |
| GODHAND_TIME_LIMIT_SECONDS | 0 | no limit — the app runs until he leaves it (the port skips the timer entirely at 0) |
| GODHAND_DUMP_ON_TIME_LIMIT | 0 | no hang dump hanging off a limit that no longer exists |
| PS2X_GS_SCALE | 1 | internal resolution 1280×960-ish instead of 3× — the first-pass frame-rate fix |
| argv | `--window --iso <copy>` | replaces the old `--headless --time-limit 120` |

Kept as they were: renderer stays `native` (the PCSX2-style software
path), the GS GPU flag stays off (CPU rasteriser — the OpenGL backend's
shaders are desktop GLSL and do not run on Android yet), the ISO
prefetch stays off, thread policy stays unset/off (the 0.4 run proved
the disc stable in this shape; changing threading and resolution in the
same build would blur which one helped).

VSYNC: the port exposes it as PS2X_VSYNC, and the headless branch was
what forced it off. In windowed mode nothing sets it, so the display
layer's default applies: vsync ON (FLAG_VSYNC_HINT). That also caps the
frame rate at the panel's refresh instead of spinning.

Landscape: the manifest carries `screenOrientation="sensorLandscape"`
on GameActivity, the theme is the same NoTitleBar fullscreen, and
configChanges now also covers screenLayout/smallestScreenSize so a
rotation or fold never restarts the activity. raylib sizes its Android
window from the real surface, so the picture fills the landscape screen
(the GS still renders the game's 4:3 into it as before — now wide
instead of tall).

The boot log is unchanged in shape: same file, same rungs, plus the
overlay line after onCreate, the first-gamepad line when one is used,
the native "touch pad present" line, and — as in 0.4 — the port prints
its effective [BOOT] settings, which is where scale/headless/vsync can
be read back on device.

## Files changed

- `runtime/ps2xRuntime/src/lib/ps2_android_touch.h` (new) and
  `ps2_host_gamepads.cpp`: the Android backend behind the host-pad
  seam.
- `android/glue/godhand_android_main.cpp`: TouchPad JNI exports, the
  play-session environment (headless 0, time limit 0, dump off, GS
  scale 1, `--window`), version strings.
- `android/shell/.../TouchPad.java` (new): per-source pad state, the
  merge, the JNI bridge.
- `android/shell/.../TouchOverlay.java` (new): sticks and buttons.
- `android/shell/.../GameActivity.java`: overlay install, pause/
  destroy hygiene, gamepad key/motion mapping, device-removal watch.
- `android/shell/.../LauncherActivity.java`: version strings.
- `android/shell/AndroidManifest.xml`: versionCode 5 / 0.5-m4,
  sensorLandscape, wider configChanges.

## Checks before shipping (static — the device run is the owner's)

- Native build: only the two intended translation units recompiled
  (glue, ps2_host_gamepads), static lib and libgodhand.so relinked
  clean.
- Packaged APK: versionCode 5 / versionName 0.5-m4, minSdk 26,
  targetSdk 35; signature verified v2+v3 with the same signer as
  0.4-m3 (SHA-256 9791d26c…dbc9005e), so it installs as an update.
- The packaged libgodhand.so matches the freshly linked one (size
  96,516,128) and contains the new seams ("0.5-m4", "touch pad
  present", "host gamepad 0 is the on-screen touch overlay",
  "On-screen touch controls"); the dex contains the overlay and
  gamepad code ("touch overlay added", "gamepad input seen",
  TouchPad, TouchOverlay).
- The packaged manifest reads back screenOrientation=6
  (sensorLandscape) and configChanges 0xda0 (orientation, keyboard,
  screen size/layout, smallest size).
- 0.4-m3 preserved at package/godhand-android-0.4-m3.apk.bak (+ .idsig).

One honest limit: the Java gamepad path can only be proven on the
device — this VM has no controller to feed it, and whether the
framework delivers controller events to a NativeActivity subclass's
overrides is exactly what the "gamepad input seen" log line exists to
answer. If that line never appears while a paired controller works in
other apps, the fallback is a native-side reader on the same seam
(the ps2_android_touch state does not care who writes it).

## Owner steps

1. Install godhand-android.apk (0.5-m4) over the current app — same
   signer, it lands as an update; nothing to uninstall, the ISO copy
   from 0.4 is reused (no ~1.5 GB copy wait this time).
2. Open the app and tap START. The launcher checks the disc copy as
   before.
3. The game opens in LANDSCAPE, fullscreen, with the touch controls
   over it: left stick to move (it also walks the menus), right stick
   is the dodge stick, △ ○ × □ on the right, L1/L2/R1/R2 up top,
   START and SELECT top-centre. Press START past the intro, walk the
   menu with the stick, get into the game and move around.
4. A Bluetooth/USB controller works too: pair it before or after
   opening the game, press anything once — standard layout (left
   stick moves, right stick dodges, A is cross). Touch and controller
   can be mixed freely.
5. Done playing: leave with Android Back or Recents — there is no
   time limit and no self-close anymore; the game runs until you
   leave it.
6. If anything misbehaves: open the app again and use Share boot log
   on the launcher. The log now shows the overlay line, the effective
   [BOOT] settings (scale 1, windowed, vsync), and — if a controller
   was touched — the "gamepad input seen" line naming it.
