# Milestone 8 — measure the last two suspects, fix the launcher (0.9-m8)

State after M7 and the owner's 0.8 device run (his boot log of
2026-11-02 02:27 WITA): disc prefetch off and never on in the app;
the IOP **acquitted** by its own numbers (`[iop-thread]` worker busy
12.5–27.4%, EE join wait 3.9–11.7% across the whole session); the
0.7 async CD cache visibly cured the streaming scenes (Sofdec/ADX
logo screen 4 FPS → 60 FPS, worst frame 822 ms → 33 ms) — but the
title screen still sits at **1 FPS with ~1300 ms worst frames**, and
the log carries one loud unexplained line from that scene:
`[spu2-adma] core 1 stream gave 1800 silent blocks (9600.0 ms) after
loud audio`. The title is a music + input waiting scene, and its
music stream demonstrably stalled for 9.6 s inside a ~24 s session.

This build changes **no behaviour** — like M7, it buys evidence.
Two suspects remain and each gets a dedicated witness; the launcher
defect the owner hit ("Gabisa digeser") is fixed for real.

## 1. The GS witness: PS2X_GS_WAIT_STATS

The flag already exists (`runtime/ps2xRuntime/src/lib/gs/gs_threaded_backend.cpp`,
read once at backend static-init); the glue now sets it next to the
IOP one, with the usual marker line in the boot log:

```
native: GS wait stats on (PS2X_GS_WAIT_STATS=1) - [gs-wait] lines follow
```

Every 2 s of GS activity it prints:

```
[gs-wait] t=12.34 publishes=118 queue-full waits=57 812.3 ms, drains=2 0.4 ms
```

How to read it, exactly:

- `publishes` — GIF chunks the EE/GIF side handed to the threaded
  GS backend in that 2 s window.
- `queue-full waits=N X ms` — how many times a producer **blocked**
  because the backend's chunk queue was full (the GS worker could
  not drain as fast as the game publishes), and the total time lost
  there. This is the conviction number for the GS path: the queue
  only fills when the worker — the CPU rasteriser and its band
  pool — is the slower side.
- `drains=N Y ms` — synchronous drain calls (framebuffer readbacks,
  RunOnWorker) and the time the caller waited for the worker to go
  idle. A big Y with a small X would convict readback coupling
  instead of raster throughput.

Verdicts:

- **GS convicted:** queue-full X repeatedly in the high hundreds of
  ms per 2 s window (worst case ≈2000 ms = producers blocked
  essentially the whole window) while the title crawls. The wall is
  the rasteriser; the next lever is the GS path itself (the GPU
  backend milestone), not more disc work.
- **GS cleared:** X and Y both near zero window after window. The
  producers never wait for the GS — the worker is idle waiting for
  work. Warning built into the logic: this stat measures *blocking*,
  so a slow EE also produces zeros here. Zeros do not say the
  rasteriser is fast; they say it is not what frames wait on.

## 2. The music-stream witnesses: [stall] lines

The refill path, as the code actually lays out (this mattered for
where the clocks went): the CRI ADX driver on the IOP issues IOP
`sceCdRead`s, served by `ps2xIOP/src/emulator/imports/iop_cdvd.cpp`
`readSectors()` — synchronously, on the IOP worker thread, through
its **own** host stream into the ISO under the IOP host-file mutex.
The 0.7 async CD cache serves only the EE side; **the stream refill
never touches it.** Two new witnesses plus one upgraded one:

**(a) The refill's disc leg — timed in `readSectors`.**
Any refill read whose whole call blocks longer than 50 ms prints
(first 16 occurrences):

```
[stall] iop-cd refill read: 214 ms for 32 sectors at lsn 755210 (route image) - the stream refill waited on this disc read
```

`route` is `image` (straight into the ISO via PS2CdImage) or
`virtual` (the extracted-file tree). Every 10 s window that
contained slow refills closes with:

```
[stall] iop-cd refill summary: 9 reads over 50 ms in 10 s, worst 640 ms, total 2210 ms waited on disc reads
```

**(b) The consumption end — timed in `iop_spu2.cpp`'s ADMA sampler.**
When a stream block finally arrives after the SPU2 buffer ran dry
for 50 ms or more (≥2400 samples at 48 kHz), under its own budget
of 16 lines (the pre-existing 1 ms "late" log keeps its own):

```
[stall] adma stream starved: core 1 block arrived 132.5 ms late at t=9.412 s - the stream buffer ran dry waiting on the refill
```

**(c) The EE side — same witness as before, now with names.**
`[cd-read] slow host read` (≥30 ms, budget 32) already covered
every EE guest read in 0.8 — and the 0.8 title produced **zero** of
them, which is part of why the EE disc path is not the suspect.
M8 only threads a caller tag through `readCdSectors` →
`readHostRange`, so the line now ends `... via sceCdRead`,
`... via sceCdReadIOPm` or `... via sceCdStream`. The fourth leg
one might want — the guest waiting on an IOP call — is already
covered by `[iop-thread]`'s EE join wait (3.9–11.7% in 0.8:
acquitted), so it gets no new line.

How the music-stream verdict is read from the combination:

- **Stream convicted, disc leg:** `[stall] adma stream starved`
  lines (or another long `[spu2-adma] ... silent blocks` run) at
  the title, with `[stall] iop-cd refill` lines/summaries whose
  totals are a large share of the same wall-clock span. The refill
  is behind because its disc reads are slow; the next lever is the
  IOP refill path itself (its own streaming cache/prefetch), a
  place no previous milestone has touched.
- **Stream convicted, not the disc:** starved/silent lines but the
  refill summaries stay near zero — the data arrives on time and
  the stream still starves, i.e. the stall sits between the read
  and the SPU2 (IOP scheduling of the ADX threads, decode cost).
  Narrower target, same family.
- **Stream cleared:** no `[stall]` lines of either kind and no
  silent-block runs during a full minute at the title. Then the
  9.6 s of silence in 0.8 was a load-phase event, not the title's
  frame wall.

## 3. Both clear — what remains

If a title minute produces near-zero `[gs-wait]` waits **and** no
`[stall]` lines while the counter still reads ~1 FPS, both
remaining subsystems are cleared by direct measurement, joining
the IOP, the prefetch, audio back-pressure, vsync and the EE disc
path. What is left is the one thing no stat so far has isolated:
**raw EE execution speed** — the recompiled guest code's own
throughput on this core (the guest's frame loop simply taking
~1 s of host time to produce a frame, including its poll loops).
That outcome is not a dead end; it is a precise hand-off — the
next build would be EE-side frame-split profiling (guest cycles
per frame vs host ms per frame), and the `[frame-stats]` lines
the glue already prints every 2 minutes become the baseline.

## 4. The launcher fix (owner-hit defect)

What was actually wrong — not a broken ScrollView: there wasn't
one. Every launcher row lived in a single plain `LinearLayout`
set directly as the content view. While the page was short that
was invisible; the Milestone 5 settings + two remap sections made
the content taller than the screen, a LinearLayout does not
scroll, and everything below the fold — Share boot log at the
very bottom — was unreachable. The only ScrollView on the page
was the small one around the log text.

What changed (`LauncherActivity.java` only):

- The whole page now sits inside a `ScrollView`
  (`setFillViewport(true)`, `setClipToPadding(false)` so the
  root's status-bar padding survives scrolling); the root keeps
  its own padding and insets listener. Every row is reachable by
  scrolling.
- **Share boot log moved to the top of the page**, directly under
  "2. Start the game" — the third control on the page, reachable
  with zero scrolling after a test run.
- The boot-log pane keeps its own inner scroll for the log text
  but takes a fixed height (260 dp) instead of its old
  weight-based "rest of the page", which is meaningless inside a
  scrolling page. Dragging on the pane scrolls the log; dragging
  anywhere else scrolls the page.
- Reload boot log stays where it was (bottom, above the log
  pane).

Static verification performed (the device glance is still the
owner's): source order line-checked in the built file — Start
button added at line 218, Share boot log created/added at lines
222–228, the Settings section follows at line 232; the old
weight-1 layout params are gone (log pane fixed at line 347);
the page ScrollView is constructed at line 354 and set as the
content view at line 362; the shell compiled clean in packaging
and the packaged dex contains the `Share boot log` label and the
0.9-m8 strings. What static checks cannot prove is the feel of
touch scrolling on HyperOS — the owner confirms that in one
swipe.

## 5. Nothing else changed

0.8's behaviour is otherwise byte-for-byte the baseline: the
async CD cache, overlay + EDIT mode, remapping, the settings set
(thread policy default off, disc prefetch default off and logged),
the FPS counter, frame-stats, the audio instrumentation, and the
IOP stats stay on. The two native changes are additive logging
(a timer + counter around code that already ran; the SPU2 change
is one extra `if` on a path that already counted late samples)
and the CD caller tag is a defaulted parameter — no control flow
anywhere changed.
