# God Hand Android — Milestone 20 (0.21-m20): sub-native shading rate — 2x2 block shading in the compute rasterizer

M19's census closed the upload question: the 0.20 dedup works (it skips roughly a fifth to a third of fight upload volume) and is not the fight bottleneck. The 0.20 verdict (owner run 2026-11-03 09:07 WITA, *"Masih sama"*, fight screenshot still 1 FPS / worst 1948 ms, picture clean) left the raster stream itself convicted: at native 640x448 the raster bucket runs 1555-3840 ms per ~80-field fight window, fence waits 2.0-3.8 s, presents 3-16 per window against 78-214 completed fields. The exploration for this milestone (`m20-explore.md`) established why no ordinary resolution lever exists: in this backend VRAM *is* the texture memory — one 32-bit word per guest pixel, addressed by the PS2 swizzle formats — so there is no render-target surface whose size could be halved, and `PS2X_GS_SCALE` is an integer supersampler (1-8) that cannot go below 1. What can change is the *shading rate* inside the rasterizer. That is what 0.21 does: drawn content is shaded once per aligned 2x2 guest block and the result written to all four guest pixels, while the VRAM layout — and everything that reads it — stays exactly as it was.

The short version: in the raster compute shader's new LORES mode, three of every four invocations exit immediately; the invocation at each aligned 2x2 block's corner evaluates coverage for all four block positions itself and shades each covered primitive once, at one position's interpolated values; `writePixel`'s colour and depth results are then fanned out to the four guest pixels of the block through the same `writePixelRaw` path as always. Uploads (including the 0.20 dedup), clears, copies, CLUT, present and readbacks are untouched and remain per-guest-pixel and byte-exact. The mode is on by default in this test build; `PS2X_GS_RENDER_SCALE=1` turns it off, and the boot log states the active mode either way.

## 1. Why this shape (the exploration's verdict, compressed)

- Halving VRAM or storing drawn pages at half size is not a setting, it is a different backend: every swizzle table, page map, upload, copy, texture read and readback addresses VRAM as 1 word = 1 guest pixel, and the game itself addresses its drawn pages as textures and framebuffers by guest coordinates (its flip copy FBP 0x70 -> FBP 0 and its feedback effects would sample garbage).
- A present-only downscale would shrink only the present bucket (single-digit to ~30 ms in fight windows) and the readback bytes. M19's numbers already convict the raster stream, not present.
- Patching the guest's FRAME/SCISSOR/DISPLAY registers corrupts the game's own VRAM page budget: framebuffers, Z buffers and texture pages are allocated by guest code at fixed block pointers with FBW 10.
- Block shading is the one variant inside the design: VRAM keeps one word per guest pixel; only the rate at which drawn content is *shaded* changes. Textures the game uploads stay full-resolution; only drawn content loses resolution, which is exactly the content the raster bucket produces.

## 2. What 0.21-m20 changes

Two files in the shipped tree (`godhand-recomp/runtime/ps2xRuntime`), plus one ini row. Nothing else.

### 2.1 The raster shader (`src/lib/gs/gpu/gs_gpu_shaders.cpp`)

A new compile-time mode in `kRaster`, keyed on `#if LORES` exactly the way the existing HIRES mechanism is keyed on `#if HIRES` (host-defined in the shader prefix when on, stripped as text when off; no names introduced outside the blocks):

- **Block leaders only.** In `main()`, invocations whose guest position is not an aligned 2x2 block corner (`(x & 1) != 0 || (y & 1) != 0`) return immediately. Workgroup count, tile geometry and the host binning contract are unchanged; the work simply is not done by 3/4 of the invocations.
- **Coverage stays per guest pixel.** The leader evaluates `coversPixel()` for all four block positions (corner first, short-circuiting), so a primitive covering any block pixel still shades the block. That is 4x coverage math on 1/4 of the invocations: coverage cost is roughly unchanged from today, by design — it is the shading cost that quarters. Draw order is preserved exactly (primitives are drawn in tile-list order, as the mask walk drew them; `coversPixel` reads only the immutable prim buffer, so interleaving coverage and drawing within a chunk changes nothing).
- **One shading per primitive per block.** The leader calls `drawPrim()` once — at the block corner when the primitive covers it, otherwise at the first covered block position. The fallback matters: the draw functions re-test the position they are handed (a point draws only at its own pixel, sprites and triangles clip to their bounding boxes), so handing them an uncovered corner would drop points and slivers outright. Depth and destination reads likewise happen at the shading position — the corner in the overwhelmingly common case, as designed.
- **Fan-out writes.** `writePixel()` keeps all of its logic — alpha test classification, destination alpha test, blending, fog, framebuffer mask, depth test — computed once from the single shading sample. Only its two final `writePixelRaw` calls change: in LORES mode they go through `writeBlockFanout`, which writes the same colour (and depth) word to all four guest pixels of the aligned block, each write individually scissor-tested. `writePixel`'s own scissor early-out is compiled out in LORES mode for the same reason: the shading position can sit outside the scissor while another pixel of its block is inside, and that pixel must still be written, exactly once, by its block's leader. Every guest pixel belongs to exactly one aligned block and is written by exactly one invocation, so the sub-word formats keep their existing atomic update behaviour with no new hazards.

### 2.2 The host (`src/lib/gs/gpu/gs_gpu_backend.cpp`)

- **Parse.** `Impl` gains a `renderDiv` member next to `scale`. The constructor reads `PS2X_GS_RENDER_SCALE` next to the `PS2X_GS_SCALE` parse: `0.5` (a rate) or `2` (a divisor) selects block shading; `1` or any other value is the native rate. Unset defaults to **on** for this test build, so the shipped configuration exercises the mode. The constructor forces `renderDiv = 1` whenever `scale > 1`: HIRES supersampling and block shading are mutually exclusive and never mix.
- **Plumbing.** `ensure()` adds `#define LORES 1` to the shader prefix when the divisor is 2 (the same prefix mechanism HIRES uses), and `shaderText()` strips the LORES blocks as text whenever the mode is off — the same treatment HIRES gets at 1x. With the mode off, the compiled raster source is byte-identical to the pre-M20 source (proven in section 4), so the off path is exactly 0.20's renderer and its shader binary-cache keys are unchanged. No dispatch changes anywhere; the ScaleBuffer is untouched (the mode is compile-time, like the 1x HIRES strip).
- **Boot log.** `ensure()` prints one line either way, in the existing `[gs-gpu]` style:
  - on: `[gs-gpu] block shading on: 2x2 blocks, one shading sample per block (PS2X_GS_RENDER_SCALE=1 turns it off)`
  - off: `[gs-gpu] block shading off: native per-pixel shading rate`
- **Hardware rasterizer guard (desktop only).** The desktop hardware stages are generated from the compute shader's functions but not from its block-leader `main()`, so block shading has no hardware variant; `setupHardwareRaster()` now declines while the mode is on and the compute rasterizer stays the renderer. On Android the hardware path is compiled out anyway — this guard only keeps desktop runs honest.

### 2.3 The off switch (`godhand-recomp/src/main.cpp`)

One `kIniSettings` row, `{"video", "renderscale", "PS2X_GS_RENDER_SCALE"}`, next to `internalresolution`: `renderscale=1` under `[video]` in `godhand.ini` turns block shading off, with the usual precedence (a real environment variable of the same name wins over the ini). The Android shell does not set this variable, so the ini value reaches the backend unimpeded on the phone.

### 2.4 Untouched

Uploads and the 0.20 dedup; clears; local-to-local and page copies; CLUT; the present path and the narrowed barrier; readbacks and the l2h sync reads (VRAM layout and values-per-address are unchanged — only drawn values are quantised to 2x2 blocks); the compiled VU1 programs and registry; the CPU GS backend (a separate implementation; it reads no such variable and simply does not get the mode); capture, still armed exactly as before; all Android glue and shell code except the manifest version.

## 3. Honest expected gain

Shading invocations in drawn areas drop 4x. Nothing else does: the per-tile fixed costs (the coverage loop — deliberately kept per-pixel — primitive and state fetch, the tile list walk, barriers, the ring stream) are unchanged, and M19 measured ~5.6-6.1 full-screen-equivalent passes per fight field, so the raster bucket should shrink materially — plausibly the majority of its shading share — but coverage-bound work (many tiny primitives per tile) gains little, and the guest side still needs its 70-94 ms per field. **This is not a promised 4x**, and it does not claim 60 fields/s. Judge it the way M19 said to judge it: on fields/s and the fence/present lines of the next log, not on the raster label alone, whose bucket attribution moves with the ring wrap.

## 5. Known risks — what to look for on the phone

1. **Depth within a block (the main risk).** One depth sample per 2x2 block means overlapping geometry inside a block resolves by draw order, not by depth. Fights are the worst case: two characters, weapons and effects overlap constantly at close range. Expect occasional wrong-overlap flashes on crossing limbs and weapons. This is the price of the approximation and the first thing to eyeball in the device test.
2. **Thin geometry gets fatter, not thinner.** Because coverage is evaluated at all four block positions, a 1-pixel line or a point shades its whole 2x2 block: chunkier particles, fatter lines. Nothing should *vanish* — that is what the four-position coverage is for.
3. **Blocky drawn surfaces.** Colour, texture, fog and depth are sampled once per block at one position; drawn textures go visibly coarse (the intended quality trade). Drawn-to-texture feedback samples the blocky result at full rate and can shimmer; the game's flicker-filter flip copy offsets its sprites by single guest lines, which at block granularity land in the same block row half the time, partially defeating the filter — visually minor.
4. **Measurement honesty.** The `[gs-work]` raster label will drop for two reasons (less shading work, same queue); per section 3, the verdict is fields/s, fences and presents.

## 6. Owner test

Install 0.21-m20 over 0.20 (same signer, in-place upgrade; ISO and settings carry over). Same settings (GPU on, threads off), same short route: title ~20 s, village ~1 min, one real fight ~1 min, then share the boot log and the vu-capture folder. Three things to report:

1. **The boot log's `[gs-gpu] block shading` line** — it should say *on*. If it says *off*, the mode never ran and the rest of the test says nothing about M20.
2. **The FPS label in the fight** — does it move off 1, and does the fight feel any different?
3. **Anything that looks wrong on screen** — above all, overlapping limbs or weapons flashing in front of things they should pass behind (the known depth risk), or geometry that looks missing. Screenshot it.

To A/B the mode off without reinstalling: add `renderscale=1` under `[video]` in `godhand.ini` (or set `PS2X_GS_RENDER_SCALE=1` in the environment) and relaunch — the boot log line flips to *off* and the renderer is exactly 0.20's.
