# Milestone 13 — the GPU worker accounts for itself (0.14-m13)

The owner's 0.13-m12 run (2026-11-02 11:25 WITA, log
godhand-boot_3_omnt.log, last session, `gpu=on`) lit the whole
chain for the first time — ES entry points resolved,
`EGL context created` (Adreno 725, max SSBO bindings 64),
`shader compile summary: 9 compiled, 0 failed`, zero
`[gs-gpu] failed:` lines — and split cleanly in two. At the
menu/title the GPU backend does real draw work at 60
(presents ~300/window at 16.7–17.2 ms, gs-fetch 3.4–6.8 ms,
fields +295..+300 per window; the owner confirms the menu is
fully normal). In game the picture is *correct* — his
screenshots show the actual 3D village and a loading screen —
but the guest produces almost no new fields: presents
90–108/window at 47–55 ms, dominated by the frontend's sync
bucket (82–96%, 43–47 ms), gs-fetch only 0.26–0.91 ms, fields
just +8..+16 per window (~1.6–3.2 fields/s). His perception is
exact: the label says 19–20 FPS and it feels like 1 FPS,
because the host re-presents near-identical frames while the
guest starves. The IOP is idle in game (busy 1.0–2.1%) —
acquitted again.

This build does not guess at the eater. It instruments the GPU
backend's worker so the next in-game log names it: a new
`[gs-work]` summary line, printed from inside the backend on
the same ~5 s cadence as `[frame-split]`, accounting for
fields completed, worker busy %, and the worker's milliseconds
in draw submission, batch flushes, raster execution, deferred
uploads, every read that goes through the M12 map shim,
presents and their readbacks, and the backend's blocking fence
waits. **This is a measurement-only milestone** — §7 gives the
per-candidate reasoning; no stall met the bar of "proven by
construction with a correct alternative already present", so
nothing was tuned blind. With the toggle OFF nothing here
runs: the glue still delivers env `"0"`, the GPU backend is
never constructed, `NoteFieldBoundary` is never called on it,
and the default run is the 0.13 run.

## 1. What the [frame-split] "sync" bucket actually waits on

From source (ps2_runtime.cpp, the present loop, M9's
accounting): when `presentSyncEnabled()` holds, the loop
busy-polls — 250 µs sleeps, **50 ms cap** — until
`eeScheduler().currentVSyncTick()` differs from the last
presented field, and the time spent in that poll is the sync
bucket. It waits on exactly one thing: **the guest EE
scheduler advancing to a new field**. It knows nothing about
the GS directly. The in-game windows are the cap saturating:
sync 43–47 ms of a 47–55 ms present means nearly every present
burned the full 50 ms wait, timed out, and re-latched the
previous frame (which is why gs-fetch stays at 0.26–0.91 ms —
the latch finds the worker's queue drained and `Present()`
returns an already-harvested frame or the previous one).

So "sync" convicts *guest field production*, and everything
that gates it. Two couplings matter for what follows:

- The EE side blocks on the GS worker at well-defined points:
  every `GSThreadedBackend` call that goes through
  `RunOnWorker` (Sync with any reason except Finish, Present,
  ConsumeLocalToHostBytes for uncached reads, ReadVram,
  GetTransferSnapshot, state export/import, SnapshotVram)
  enqueues a call op and `Drain()`s — the caller parks until
  the worker has executed everything queued ahead of it,
  including any GPU-blocking read inside those ops.
- If the worker itself is behind, the same drains wait for
  the backlog, and the op queue's producers (the EE-side
  frontend) stall on queue space.

`[gs-work]` exists to split those: it measures the worker
from inside, on the worker's own clock.

## 2. Per-field work on the GS worker: menu field vs in-game field

All backend entry points execute on the one GS worker thread
(the threaded wrapper's op queue / `RunOnWorker`), with the
backend's EGL context current there. A guest field arrives as
a queue of ops; the field is *complete* on the worker when
the queue has been executed through the field's VSync op
(`GS::vblank()` → `GSThreadedBackend::VSync`, which also
publishes the pending frame host-side). The GPU backend
itself has no `VSync` override (the base is a no-op) — the
VSync op is purely the queue's field boundary marker, which
is exactly what the new hook counts (§6).

Inside a field, the worker executes, in queue order:

- `Submit` per draw batch: CPU-side state building and
  binning (`addState`, `addTriangle`/`addSprite`/`addLine`,
  page bookkeeping, copy-on-write checks). May itself trigger
  `flushFor` (target/texture hazard) → `flushBatch`.
- `LoadClut` per indexed-texture state change: CPU bookkeeping
  plus a queued `ClutOp`; flushes the pending batch first if
  the CLUT source pages were written by it.
- `BeginTransfer` / `UploadImage`: host→VRAM texture data is
  *deferred* (staged into the upload lists; `deferUploads`
  defaults on) and executed at the next flush; local→local
  runs its copy dispatches immediately; local→host is §4.
- `Sync(Finish)` — the guest's SIGNAL/FINISH/LABEL register
  writes enqueue it; on the worker it is `flushFor(5)` →
  `flushBatch`.
- `flushBatch` (the field's gravity well): `executeTransfers`
  (deferred upload dispatches + copy-on-write page copies),
  page-map upload, `dispatchClutOps`, then draw execution —
  on Android always the compute rasterizer (hardware raster
  stays off on ES, M11 §4): prim/state/tile buffers uploaded
  through the 64 MB ring, one `DispatchCompute` over touched
  tiles, barrier.

A menu field is a handful of sprite batches and none of the
rest: no texture streaming, no CLUT churn, no transfers, tiny
flushes. An in-game field in God Hand is the opposite on
every axis: full triangle load, constant texture uploads,
CLUT loads for indexed textures, and — the subject of §4/§5 —
whatever local→host traffic the game issues. The
instrumentation times each of these stages separately
precisely because the menu proves the pipe is fast when the
field is light.

## 3. downloadVram and readClut: full call graphs, and why both are acquitted

`downloadVram(out, size)` — the whole-VRAM (4 MiB) read
through the map shim — has exactly two callers in the
backend:

- `GSGpuBackend::Sync(GSSyncReason::DebugReadback)`, and
- `GSGpuBackend::SnapshotVram`.

Frontend triggers for those: `GS::snapshotVRAM()`, whose only
caller is `GS::refreshDisplaySnapshot()` — a host/debug
snapshot facility with **no callers anywhere in the shipped
runtime** — plus the GS trace dump paths (inert without the
trace environment), and `GS::setRasterBackend`'s one-time
`SnapshotVram` hand-off when a backend is swapped in. None of
these is reachable from a guest field. `readClut` (the 1 KB
CLUT read through the shim) has exactly one caller:
`GSGpuBackend::ExportState` — save-state export, reached via
the threaded wrapper's `ExportState` (a `RunOnWorker` call),
again not a per-field path. (Do not confuse it with
`LoadClut`, the per-draw CLUT *load*: that one is a GPU
dispatch queued into the batch and executed by
`dispatchClutOps` at flush; it is counted in `[gs-work]` via
the `stats.clutLoads` delta and the LoadClut call counter.)

Both functions are still instrumented (count + ms) so the
device log can *prove* their innocence in game rather than
trust this audit: the expected in-game values are 0 and 0.

## 4. The shim reads that remain in the field path

Every synchronous host read in the backend funnels into the
M12 `esGetBufferSubData` map shim (gs_gl.cpp) through exactly
five call sites: `downloadVram` (§3), `readClut` (§3),
`dumpPlaneSnapshot` (debug only, `PS2X_GS_PLANE_DUMP`,
scale > 1), `harvest`'s fallback (only for readback slots
whose persistent map failed — on the owner's device
EXT_buffer_storage is present and the maps succeed, so this
site is expected to stay at 0), and `readData` — the one that
matters:

`readData` (dataBuffer read) has three callers:

- `localToHostTransfer()` — the guest's own local→host
  (TRXDIR=1) transfers, executed synchronously on the worker
  inside `BeginTransfer` processing: `flushFor(3)` first
  (the whole pending batch is flushed), then a `copyRegion`
  dispatch into dataBuffer, then `readData` drains it.
- The synchronous `Present()` readback — not taken in the
  shipped configuration: `asyncPresentMode()` is 2 on Android
  (the port's default), so presents go through
  `presentAsync`'s persistently mapped ring instead.
- `ReadVram()` — a poke dispatch + 4-byte `readData`. Its
  only callers are the recording/replay backend's
  verification path — not a live game path.

The guest's local→host transfers have one escape hatch, and
it is narrow by design: the threaded wrapper's async readback
cache (§50/§64 of the tree's own progress docs) serves a
transfer from the previous identical transfer's bytes — one
field late — only when the transfer is **at most 8×8 in a
depth format** (psm 0x30/0x31/0x32/0x3A) under the default
mode 1 (mode 2, `PS2X_GS_ASYNC_READBACK=all`, also covers
color and raises the cap to 16×16; the glue sets neither, so
mode 1 holds). First-time transfers of even an eligible block
run synchronously once (the capture), and *every* other
local→host transfer — any color read, anything larger than
8×8 — runs the synchronous path above, every time.

**Drain count per field, from the code:** synchronous shim
reads in a field = the number of local→host transfers in that
field that miss the async cache (each contributes exactly one
`readData` drain, preceded by a full batch flush) — plus zero
from every other category in normal play. `[gs-work]` prints
that number directly as `l2h sync`, next to the `readData`
count and milliseconds.

## 5. The map shim under load: why one read can cost a whole pipeline

`esGetBufferSubData` maps with `GL_MAP_READ_BIT` only — no
`GL_MAP_UNSYNCHRONIZED_BIT` — and every backend read site
issues a full `barrier()` (all barrier bits) immediately
before it. Under the GL rules, mapping a buffer range for
reading without the unsynchronized bit lets the driver block
until the GPU has finished *all* prior work touching that
buffer; and because this backend drives a single context with
a single sequential command stream, "prior work touching
dataBuffer" in practice means the GPU must walk to the exact
point of the `copyRegion` dispatch that produced the bytes —
i.e. the read drains everything queued before it, which
`flushFor(3)` has just made be *the field's entire pending
draw load* plus the copy itself. The map cannot be made
unsynchronized to fix this: the bytes being read are being
written by the dispatch immediately ahead of the map, so
waiting for them is the semantics, not an accident. The cost
of an uncached local→host read is therefore, by construction,
(the field's queued GPU work) + (a full pipeline drain), paid
on the worker — and then paid *again* in guest time, because
the EE consumes the bytes through
`GSThreadedBackend::ConsumeLocalToHostBytes`, a `RunOnWorker`
call that parks the EE-side caller until the worker reaches
it in queue order. One such read per field is enough to
serialise both threads behind the GPU once per field; several
per field multiply it. Whether God Hand actually issues such
reads in game, and at what rate, is precisely what the new
counters answer (`l2h sync` count, `readData` count/ms,
`fields` for the ratio).

The remaining blocking waits inside the backend, for
completeness — the whole `ClientWaitSync` census of
gs_gpu_backend.cpp is four sites: `harvest` and
`pollDownloads` poll with a **zero** timeout (non-blocking;
excluded from the fence bucket), and two that can block:

- `ringPut`: when an upload wraps to the next 16 MB ring
  chunk, it `ClientWaitSync`s on that chunk's previous fence
  (5 s timeout) before overwriting it — correctness, not
  waste (the alternative is corrupting in-flight uploads),
  but under heavy upload traffic the ring wraps often and
  each wrap waits out the GPU's distance to that fence.
- `presentAsync` mode 2: `ClientWaitSync(previous fence,
  8 ms)` so the present can show the previous frame's
  readback — a deliberate, bounded trade the code documents
  (mode 1's no-wait variant visibly skipped frames).

Both are now counted in the fence bucket (count + ms).

## 6. What [gs-work] measures, and what already existed

Existing machinery, surfaced rather than duplicated:

- The **GPU profiler** (`PS2X_GS_GPU_PROFILE`) already times
  every pass *on the GPU* with timestamp queries and reports
  per-120-frame `[gs-gpu-profile]` summaries, including flush
  reasons and per-target raster times. It is opt-in (always
  off in the shipped glue), it measures GPU-side pass time —
  not the worker's CPU time, not the synchronous reads, not
  the fence waits — and on Android its query plumbing is the
  M12 EXT route. `[gs-work]` complements it from the CPU
  side; if a future milestone needs pass-level GPU times,
  enabling the profiler for one run is the tool.
- **presentStats** (`PS2X_GS_GPU_STATS`, also opt-in, also
  off) already counts presents/s, drawn/s, batches and CLUT
  loads per frame and the present path's fence wait/submit
  times, printed as a `[gs-gpu]` line. `[gs-work]` reuses its
  underlying `Stats` counters (prims/batches/tiles/clutLoads
  deltas) instead of recounting them, and covers the whole
  worker rather than the present path alone.
- `hwRingWaitMs` already accumulated the ring waits for the
  `[gs-hw]` flush log; the fence bucket counts the same waits
  (plus mode-2 present waits) in the always-on window.

New in this build (all in `GSGpuBackend::Impl`, gs_gpu_backend.cpp,
plus one hook each in the header and the threaded wrapper):

- A `WorkWindow` of plain counters/accumulators — no atomics:
  every backend entry point runs on the single GS worker
  thread by the wrapper's design (`RunOnWorker` / op queue),
  and the field hook is called from that same thread
  (`GSThreadedBackend::Execute`, `Op::VSync` →
  `GSGpuBackend::NoteFieldBoundary`, after the inner VSync —
  the queue-order point where the field's work has all been
  executed). The one cross-cutting risk would be a caller
  invoking the backend off the worker; on Android the backend
  only ever sits behind `GSThreadedBackend::MakeDefault`.
- RAII timers (`WorkTimer` buckets; a depth-guarded
  `BusyTimer` for worker-busy so nested entry points —
  Initialize→Reset — never double count; a `PresentScope`
  that records each `Present` and runs the window check on
  whichever of its several return paths leaves first).
- Buckets: fields (VSync ops executed); prims/batches/tiles
  and clutOps (deltas of the existing `Stats`); worker busy %
  (outermost entry-point time over window wall time); submit
  ms (Submit CPU); flush ms (flushBatch total — it *nests*
  the next two); raster ms (flushBatch's draw-execution
  section: prim/state/tile buffer uploads + dispatch +
  barrier); uploads ms (`executeTransfers` total); per-site
  shim reads — downloadVram, readClut, readData, other
  (harvest fallback + plane dump) — each count + ms; present
  count + ms; harvest count + ms (the async readback's polls
  and copies); fence count + ms (§5's two blocking waits);
  `l2h sync` / `l2h async` (synchronous local→host transfers
  executed vs `beginDownloadAsync` takes); LoadClut calls.
- Cadence: a 5 s steady-clock window, checked from `Present`
  and from the field hook (the two places guaranteed to run
  while a game runs). A window with no fields, no presents and
  under a millisecond of busy time slides silently instead of
  printing, so an idle game cannot mint empty lines, and a
  burst is never diluted by the idle time before it.
- Cost: two clock reads per timed call and counter adds; no
  allocation, no logging inside the window, no GL calls, no
  ordering changes. One fprintf per ~5 s.

Line format (one line per window):

```
[gs-work] fields=N prims=N batches=N tiles=N busy P% | submit X ms flush X ms (raster X ms uploads X ms) | shim reads: downloadVram N/X ms readClut N/X ms readData N/X ms other N/X ms | present N/X ms harvest N/X ms fence N/X ms | l2h sync N async N, loadClut N, clutOps N
```

All times are window totals (not per-frame averages);
`[frame-split]` in the same log supplies the per-present
view of the same seconds.

## 7. Fix verdict: measurement only

Each candidate stall was checked against the bar — proven
by construction *and* a correct alternative already present:

- **Synchronous local→host reads (§4/§5)** are proven by
  construction, but the only deferred alternative in the
  tree is the async readback cache, whose one-field-late
  semantics the tree's authors deliberately scoped to tiny
  depth reads (Urban Reign's 8×8 flare test). Widening that
  scope changes guest-visible data freshness for arbitrary
  blocks — a semantic decision, not a proven fix — and the
  guest's first read of a region cannot be deferred at all:
  the EE needs those bytes to proceed. If the counters
  convict this path, the fix conversation starts from
  evidence about *which* transfers God Hand issues (size,
  format, rate), which is exactly what `l2h sync` +
  `readData` provide.
- **downloadVram / readClut** are not in the field path
  (§3); nothing to fix.
- **presentAsync mode 2's 8 ms wait** and **ringPut's fence
  wait** are documented correctness trades (§5), bounded,
  and now measured; if the fence bucket convicts one of
  them, that is a tuning conversation with numbers in hand.
- The **sync present readback** has a correct async
  alternative and already uses it (mode 2). The **harvest
  fallback** drain exists only where persistent mapping
  failed — not this device.

So this build ships measurement only, and says so. What it
must not do is leave the next run ambiguous: every bucket
above lands in one log line, next to `[frame-split]`, on the
same seconds.
