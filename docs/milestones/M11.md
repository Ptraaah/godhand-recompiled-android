# Milestone 11 — first light for the GPU renderer on Android (0.12-m11)

State after M10 and the owner's 0.11 device A/B (his boot log of
2026-11-02 04:31 WITA): the A/B landed exactly as the source said.
Run A (toggle OFF) re-proved the default (`renderer: cpu (owner
setting)`, title windows up to 1256.8 ms, gs-fetch 99%). Both ON
runs printed `[gs-gpu] GPU GS backend is only implemented for
Windows` — the stub firing on real hardware — and, with the fetch
leg skipped by the empty `Present()`, the emulation ran
16.7–18.9 ms per present (~60/s, fields +255..+300 per window).
The pipe is proven fast; what was missing is a renderer that
actually draws into it. This build removes the stub: the GPU
backend gets an Android EGL / OpenGL ES 3.2 context, its GLSL 460
core shaders are translated to GLSL ES 3.20 at load time, and the
rest of the desktop-GL surface is audited entry point by entry
point. With the toggle OFF, nothing in this build runs any of
that code — the env value delivered to the port is still `"0"`,
the backend is never constructed, and the default run is the
0.11 run.

## 1. The window question, answered from the code

The task for this milestone was to build the context "on the
same ANativeWindow the app already owns". Reading the tree says
that is neither possible nor needed:

- The window and its EGL context belong to raylib's Android
  platform (vendored raylib creates both from the NativeActivity
  window internally; `android_main` lives there, the glue's
  `main()` runs inside it). The port's GS layer is never handed
  the window or the context — the same fact M10 recorded about
  the WGL shared-present path ("raylib's context, which the port
  does not expose to the GS layer").
- The GPU backend never presents to a window anyway. It renders
  into SSBOs and FBOs and `Present()` hands pixels back to the
  host — a synchronous `GetBufferSubData` readback, or the
  `presentAsync` ring of persistently mapped buffers — which the
  host's present loop uploads as a texture. On Windows its
  context already sits on a hidden 16×16 window it never draws
  to; the window is a context-creation formality there.

So the Android context is backed by a **1×1 pbuffer surface**,
owned entirely by the GS layer. This also avoids the real
conflict the window route would have hit: an EGL window surface
can be current in only one context at a time, and raylib's
context owns the app's.

Threading is the other precondition, and it holds: every inner
backend call — `Initialize`, `Present`, readbacks, all of it —
funnels through `GSThreadedBackend::RunOnWorker` onto one
dedicated worker thread. The context is made current on that
thread in `Create()` and stays current there, exactly like the
Windows path. The one extra GL thread the design has (the
hardware-raster shader compiler) is disabled on ES (§4).

## 2. The EGL context (gs_gl.cpp, `#elif defined(__ANDROID__)`)

`GSGL::Context` gains a full Android implementation; the Windows
branch and the generic non-Windows stub (desktop Linux, Vita)
are untouched, and the stub's error string no longer exists in
the Android `.so` (0 occurrences, §6). `Context::Create`:

1. `eglGetDisplay` / `eglInitialize`.
2. `eglChooseConfig`: ES3 renderable + `EGL_PBUFFER_BIT`,
   RGBA8 — the closest match to the desktop path's RGBA format;
   the surface is never displayed, so nothing else is requested.
3. `eglCreateContext`: versioned attributes first (major 3,
   minor 2), client-version-3 as fallback; share = none.
4. `eglCreatePbufferSurface` (1×1), `eglMakeCurrent`.
5. The `Api` table is filled through `eglGetProcAddress` with
   the same missing-list discipline as the Windows loader: a
   missing core function fails creation with
   `missing GL functions: ...` in the `[gs-gpu]` line.
6. **Version gate**: `GL_VERSION` is parsed and anything below
   OpenGL ES 3.2 fails creation
   (`OpenGL ES 3.2 required, got: ...`). The translated shaders
   are `#version 320 es` (`precise` alone needs 3.20); asking
   for a 3.2 context and then verifying beats trusting either.
7. One evidence line is printed on success:

   ```
   [gs-gpu] EGL context created: OpenGL ES 3.2 V@... | Adreno (TM) 725 | max SSBO bindings <N>, max SSBO block <M> bytes, EXT_buffer_storage yes
   ```

   (renderer/version text is the driver's own; the two limits
   and the extension flag are the values §5 says to check first
   in the device log.)

`CreateWorker` / `MakeWorkerCurrent` / `DestroyWorker` are real:
a shared context (`eglCreateContext` with the main context as
share) plus its own 1×1 pbuffer — EGL's native equivalent of the
WGL shared-context workers. They have no caller on Android today
(the compile worker belongs to the disabled hardware rasterizer)
but the interface is honoured rather than stubbed.

Desktop-only entry points, resolved:

| Api entry | On ES | How |
|---|---|---|
| `glBufferStorage` | extension | loaded as `glBufferStorageEXT` **only if** `GL_EXT_buffer_storage` is in the extension string (an `eglGetProcAddress` hit alone is not trusted); otherwise a fallback shim allocates with `glBufferData` and drops the storage flags |
| `glClearBufferData` | absent | local shim: fills the bound buffer with the 32-bit pattern via `glBufferSubData` chunks. Its only caller in the tree is `PublishShared` (unavailable on Android), so the shim is completeness, not a hot path |
| `glMaxShaderCompilerThreads*` | optional | `glMaxShaderCompilerThreadsKHR` (GL_KHR_parallel_shader_compile); tolerated missing, as on Windows |
| `glGetProgramBinary` / `glProgramBinary` | core ES 3.0 | loaded normally; only used by the on-disk shader cache, which is inert on Android (the glue never sets `PS2X_GS_SHADER_CACHE_DIR`) |
| everything else | core ES 3.0–3.2 | `glDispatchCompute`, `glMemoryBarrier`, `glBindImageTexture` (3.1), sync objects, timer queries, `glGetBufferSubData`, `glGetInteger64v` — all core in the ES versions the gate requires |

**Shared presentation stays unavailable**, deliberately, and
this is the one Windows feature not ported: `PublishShared`
publishes a texture created in the backend's context into the
*host* context, and GL objects only cross contexts inside one
share group. Raylib created its context outside ours and EGL
cannot adopt contexts into a share group after the fact, so
`GSSharedPresent::CaptureHostContext` remains a no-op,
`Active()` false, and `Present()` always takes its readback
route — the route the 0.11 A/B's `[frame-split]` accounting
already measures. (`ps2_runtime.cpp`'s capture call site is
inside its desktop section; the Android stubs keep the symbols
harmless either way.)

`GSGL::Context`'s members are reused as the handle slots:
`m_dc` = EGLDisplay, `m_window` = EGLSurface, `m_context` =
EGLContext, so `Valid()` and the class interface are unchanged.
CMake: `ps2_runtime` now links `EGL GLESv3` under
`PS2X_IS_ANDROID`, next to the existing WIN32 `opengl32 gdi32`
block; the packaged `.so`'s NEEDED list gained `libEGL.so` and
`libGLESv3.so` (raylib's `libGLESv2.so` was already there).

## 3. Shader translation (gs_gpu_backend.cpp, Android only)

All nine compute programs are built by one function,
`Impl::compile()`, which composes
`prefix + shaderText(kCommon) + shaderText(body)`. On Android
the composed text passes through `translateShaderForEs()` at
the top of `compile()` — before the binary-cache fingerprint is
taken from it — so the desktop shader sources in
`gs_gpu_shaders.cpp` are never edited, and the hardware-raster
stages (which compose their own sources outside `compile()`)
are out of its reach and disabled (§4).

The rules, verbatim as implemented (word rules run on the
desktop text first; the version swap and the shim are applied
last, so the shim's own words are never rewritten):

- **V** — the leading `#version 460 core` becomes
  `#version 320 es`, followed by the shim below.
- **S1** — the shim states default precisions explicitly
  (`precision highp float; precision highp int;`). Compute
  already defaults to highp in ES; the lines make the translated
  text independent of stage defaults.
- **S2** — the shim's `gsUnpackDoubleToFloat(uvec2)`: IEEE-754
  double bits → nearest float (round bit honoured, exponent
  carry handled), saturating out of range, flushing subnormals
  and zero to 0.
- **D1** — the word `double` becomes `float`.
- **D2** — `packDouble2x32(` becomes `gsUnpackDoubleToFloat(`.

The shim text exactly as injected:

```glsl
// ---- [gs-gpu-es] GLSL ES translation shim (injected by the compile path on Android; see M11.md) ----
// Rule S1: default precisions, explicit (fragment-stage parity; compute already defaults to highp).
precision highp float;
precision highp int;
// Rule S2: IEEE-754 double -> nearest float (the rasterizer's pd() unpacks host-written double bits;
// GLSL ES has no double type. Saturates out-of-range, flushes subnormals; z data is integral in [0, 2^32).)
float gsUnpackDoubleToFloat(uvec2 bits)
{
    uint sign = bits.y & 0x80000000u;
    int exp = int((bits.y >> 20u) & 0x7FFu);
    if (exp == 0)
        return 0.0;
    if (exp == 0x7FF)
        return uintBitsToFloat(sign | 0x7F800000u);
    int fexp = exp - 1023 + 127;
    if (fexp >= 255)
        return uintBitsToFloat(sign | 0x7F7FFFFFu);
    if (fexp <= 0)
        return 0.0;
    uint mant = ((bits.y & 0xFFFFFu) << 3u) | (bits.x >> 29u);
    if (((bits.x >> 28u) & 1u) != 0u)
    {
        mant += 1u;
        if (mant == 0x800000u)
        {
            mant = 0u;
            fexp += 1;
            if (fexp >= 255)
                return uintBitsToFloat(sign | 0x7F7FFFFFu);
        }
    }
    return uintBitsToFloat(sign | (uint(fexp) << 23u) | mant);
}
// ---- end shim ----
```

**Why the double rules are the whole story.** A token census of
the composed shader set shows the compute programs are
otherwise ES-shaped already: std430 SSBOs, buffer atomics
(`atomicOr/And/Xor/Add`), `barrier()`, image store confined to
the shared-present shaders (never compiled on Android). The one
genuinely desktop-only construct is in `kRaster`: `pd()` unpacks
two prim words as an IEEE double (`packDouble2x32`) and the
triangle Z interpolation runs in `precise double`
(z0/z1/z2, `z = z0 + (z1-z0)*w1 + (z2-z0)*w2`,
`zc = clamp(z + 0.5, 0, 2^32)`). GLSL ES has no double type at
any version, so D1+D2 are unavoidable — and their cost is
stated plainly: the host still writes exact double bits, but
the interpolation now runs in float, so Z is exact only to
24 bits. At large Z, neighbouring surfaces can trade places
(z-fighting on distant/overlapping geometry) where the desktop
path stays exact. That is a precision degradation inside one
expression of one shader, not a structural change; a hi/lo
float-pair version of `pd()` and the Z math is the known
follow-up if the device picture shows it matters.

**Host validation** (the deliverable this section stands on):
the nine composed sources were extracted with the runtime's own
`shaderText()` transform replicated (scale 1 — the backend
clamps `PS2X_GS_SCALE` to ≥ 1 and the owner's 0.5 shell setting
lands on 1), translated with the rules above (the validator's
shim is byte-identical to the C++ `kEsShaderShim`), and compiled
with the NDK's `glslc` (the glslang front-end; no
`glslangValidator` exists on this VM):

- **9/9 pass** under `--target-env=opengl`, with one
  validation-only difference: loose uniforms in the validation
  copies carry explicit `layout(location = N)` (array sizes
  accounted). glslc demands locations for SPIR-V output even in
  its OpenGL mode; **GLSL ES does not** — the backend assigns
  locations by name through `glGetUniformLocation`, the standard
  ES route — so the runtime sources keep their name-based
  uniforms and the locations exist only in the validator's
  copies.
- Without the translation, the same harness fails on exactly
  the `double`/`packDouble2x32` sites and nothing else — the
  rules cover the whole incompatibility set the front-end can
  see. What no host tool can see is the device driver's own
  compiler; that verdict belongs to the owner's run (§7).

Tooling and outputs are kept at `m11-shader-validation/`
(`extract.py`, `translate.py`, `validate.py`, `translated-es/`,
`results.txt`).

## 4. The rest of the backend audit

- **Hardware rasterizer: off on ES**, by an early return in
  `setupHardwareRaster()` (Android only). Its generated fragment
  stage opens with
  `#extension GL_ARB_fragment_shader_interlock : require` —
  pixel-order rasterization over the shared VRAM buffer — which
  this tree's ES path cannot express, and its sources bypass
  `compile()`'s translation entirely. Nothing is lost by it:
  the compute rasterizer is the renderer, and on desktop any
  state without a compiled hardware variant falls back to it
  the same way. Its FBO/VAO/`FRAMEBUFFER_DEFAULT_WIDTH` usage
  (the Api's `graphics` group) is therefore never reached on
  Android; `kConservativeRasterizationNV` likewise appears only
  in that path's bookkeeping.
- **`presentAsync` null-map guard** (all platforms, behaviour
  identical where persistent mapping exists): async present is
  the port's default (`src/main.cpp` sets
  `SetAsyncPresentDefault(true)`, so `asyncPresentMode()` is 2
  on Android too) and it harvests pixels with a `memcpy` from a
  persistently mapped buffer — a desktop assumption that the
  map always succeeds. `Readback` gains a `persistent` flag set
  from the map result; if a driver without
  `GL_EXT_buffer_storage` (i.e. the fallback allocation of §2)
  ever runs this, `harvest()` now reads the slot's buffer back
  with `glGetBufferSubData` after its fence instead of copying
  from a null pointer. The upload ring and the async downloads
  already handled a null map in the original code (ring falls
  back to staged uploads; `beginDownloadAsync` returns false
  and the frontend takes its synchronous path) — they needed
  no change.
- **Shader-compile counters + summary**: `compile()` counts its
  outcomes (two inert integer increments on other platforms;
  the binary-cache hit counts as compiled — that path cannot
  occur on Android, cache dir unset) and `ensure()` prints, on
  Android only, after the nine-program chain:

  ```
  [gs-gpu] shader compile summary: 9 compiled, 0 failed
  ```

  Per-shader failures keep their existing
  `[gs-gpu] shader compile failed:` / `program link failed:`
  info-log dumps, so a bad count names its shader in the lines
  above it.
- **Untouched**: `ensure()`'s buffer set (VRAM SSBO 8 MiB at
  scale 1, swizzle/CLUT/prim/state/tile/data/page-map buffers,
  the 64 MB upload ring), the present composite, the sync and
  async readbacks' shapes, `shaderText()`, the binary-cache
  logic, every witness (`[frame-split]`, `[iop-thread]`, refill
  and adma summaries), and the CPU backend in full.

**Limits the device log will speak to** (no code depends on
guessing them): at scale 1 the shaders bind SSBOs at indices
0–9 (clutOp 8, pageMap 9), above the ES spec's guaranteed
minimum of 8 bindings, and the VRAM SSBO is 8 MiB against a
guaranteed block-size minimum far below that. Adreno-class
drivers expose far more of both (and the creation line prints
the actual values), but a device that didn't would fail its
`BindBufferBase` calls visibly rather than silently in the
numbers. Workgroup shapes are modest (16×16 raster/present,
256-wide linear passes) and the compute set uses no shared
memory outside the never-compiled present-hash shader.

## 5. What a device run should print (the evidence chain)

With the toggle ON, in order:

1. `renderer: gpu (owner setting)` — the glue (unchanged M10 line).
2. `[gs-gpu] EGL context created: OpenGL ES 3.2 ... | ... | max SSBO bindings <N>, max SSBO block <M> bytes, EXT_buffer_storage yes`
3. `[gs-gpu] <renderer> / <version>` — `ensure()`'s pre-existing
   renderer/version line, now reached with a real context.
4. `[gs-gpu] shader compile summary: 9 compiled, 0 failed`
5. `[frame-split]` windows whose gs-fetch is real GPU time —
   against run A's 679–1257 ms title windows and the stub runs'
   16.7–18.9 ms empty ones.

Failure shapes, each located: an EGL/config/version failure
stops at 2 with the error in the `[gs-gpu]` line and the backend
latching `failed` (picture = the stub runs' black/frozen, cause
different and named); a driver shader rejection shows
`[gs-gpu] shader compile failed:` + the driver's info log and a
summary short of 9; SSBO-limit trouble would appear as a live
context and compiled shaders but a broken/empty picture with
GL errors — the creation line's two numbers are the first place
to look.

## Owner steps

1. Install 0.12-m11 over 0.11 (same signer, update in place, ISO
   copy reused). Leave every setting as it is except the one
   below.
2. In the launcher, tap **GPU renderer (experimental)** to ON.
   START, go to the PRESS START title, sit a full minute, and
   note **what the screen does** — then exit and **Share boot
   log** (third button on the page) and send the file.
3. Reading the result:
   - **A real picture** (even wrong colours, torn, or slow) =
     first light: the renderer drew. The log's
     `[frame-split]` title windows price the GPU path against
     the CPU's 679–1257 ms and the stub's empty 16.7 ms.
   - **Black / frozen screen** = read the `[gs-gpu]` lines:
     which step of the §5 chain is missing or failed is the
     whole diagnosis — context, version gate, a named shader,
     or the SSBO numbers.
   - A crash is also a result: the log up to the crash plus
     where it stopped is the evidence.
4. Toggle OFF afterwards returns the exact 0.11 behaviour —
   same env value, GPU backend never constructed.
