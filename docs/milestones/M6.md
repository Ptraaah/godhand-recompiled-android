# Milestone 6 — perf rescue: the disc cache stops freezing the game (0.7-m6)

0.6-m5 reached the title screen on the owner's POCO F5 with the overlay
visible and the FPS counter working — at 1 FPS, worst frame 1230 ms. The
cause was found by code inspection, and it was Milestone 5's own cache:
in `readHostRange` (runtime/ps2xRuntime `Support.h`), a cache miss filled
a whole 4 MiB block **synchronously on the EE thread** under
`streamsMutex`, and a sequential miss synchronously filled the *next*
block too. One guest `sceCdRead` could therefore pull 8 MiB of disk IO
at the phone's flash speed (~7.7 MB/s, measured in his 0.5 log as 315 KB
in 41 ms) — roughly 1.0–1.2 s of frozen game thread, matching his worst
frame to the digit. The file's own older comment records this same
function once freezing the EE thread for 1.2 s on desktop for the same
reason: synchronous disc IO on the game thread. M5 rebuilt the trap
while trying to fix the 41–51 ms reads; M6 removes the trap and keeps
the cache.

## The new read path (same layer, `readHostRange` only)

- **The guest never reads more than it asked for.** On a cache miss the
  guest reads exactly the requested chunk from the open stream — the
  pre-M5 behaviour, bounded by the request size. Guest-visible semantics
  are unchanged: same bytes, same zero-fill past EOF, same error
  contract; reads over 2 MiB bypass the cache exactly as before.
- **All speculative work moved to one background worker thread.** It
  owns every cache fill: 1 MiB blocks (down from 4 MiB), 32 held
  (~32 MiB total, LRU). When the guest's accesses run sequentially the
  worker is asked to stay two blocks ahead; a fresh miss asks for the
  one block after it. Requests are fire-and-forget queue appends.
- **A block being filled is invisible.** Each slot carries a claim
  token; the worker reads into a private buffer *from its own streams*
  (never the guest's — no shared file position), and publishes the block
  under the cache lock only when the fill has completed. The guest
  consumes completed blocks only and never waits on a fill, on the
  worker, or on any lock held across somebody else's disk IO.
- **Stats split so the next log proves it.** `[cd-cache]` now reports
  hits/misses and served-from-cache bytes next to **guest-direct**
  reads/bytes (the guest's own bounded reads) and **worker-fills**
  count/bytes (the speculative volume). The slow-fill log line now
  comes only from the worker; the `[cd-read] slow host read` line still
  guards the guest path at the same 30 ms threshold.

## What healthy looks like in the boot log

- `[cd-cache] after 60 s: hits=… misses=… served-from-cache=… bytes,
  guest-direct=N reads/B bytes, worker-fills=F/B bytes, blocks-held=32`
  — healthy is: hits and served-from-cache climbing steadily,
  worker-fills comfortably ahead of the stream, and guest-direct reads
  staying few and small (individual game requests, never megabytes).
- `[cd-cache] slow block fill (worker): …` lines are **expected and
  harmless** now — that is the big sequential IO happening where it
  belongs, off the game thread.
- `[cd-read] slow host read: …` may still appear for a guest request of
  a few hundred KB (tens of ms at flash speed — the 0.5-m4 baseline
  behaviour). What must never come back is a ~1000 ms entry: no guest
  path can produce one anymore, because no guest path reads more than
  the request.

## The other change, and everything that did not change

- **Thread policy defaults OFF again.** The M5 Linux governor stays in
  the code and stays selectable in the launcher settings ("Thread
  placement (performance cores)"); only the default flipped, in the
  launcher toggle, the settings label, GameActivity's read of the
  preference, and the IsoHolder fallback — so the baseline is the plain
  OS scheduler, as in the owner's 0.5-m4 run. If he previously toggled
  the setting himself, his stored choice still wins; the settings row
  shows its current state.
- Nothing else moved: overlay, EDIT layout mode, remapping, all other
  settings, the FPS counter, frame-stats, the audio instrumentation,
  the ISO copy flow — byte-for-byte the 0.6-m5 behaviour.

## Owner steps

1. Install godhand-android.apk (0.7-m6) over the current app — same
   signer, it lands as an update; the ISO copy is reused, no copy wait.
2. Leave the settings as they land: thread placement is OFF by default
   again (check the settings row shows it off — if you switched it on
   while testing, flip it off so this test is clean). Keep the internal
   resolution at the 0.75 you picked last time, so the comparison with
   the 0.6 run is apples-to-apples.
3. Tap START. At the title screen, read the FPS counter: it should sit
   at the rate the software renderer can actually sustain, not 1.
4. Press START, get into the game, and play for a few minutes — the
   intro movie and the first area stream from the disc, which is
   exactly the traffic that used to freeze.
5. When done, reopen the app and use Share boot log. The log's
   `[cd-cache]` lines, the `[frame-stats]` lines, and the absence of
   any ~1000 ms `[cd-read]` entry are the verdict.

Success = title screen and gameplay at the frame rate the CPU
rasteriser can sustain, with no >100 ms disc stall on the guest thread
anywhere in the log.
