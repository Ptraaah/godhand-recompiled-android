# God Hand Android — Milestone 15 (0.16-m15): the inside-the-guest profile

0.15-m14's device verdict (owner run 2026-11-02 12:24 WITA, log godhand-boot_3) convicted the EE thread's own guest execution: in game, a field still costs ~4.92M EE cycles but takes 0.4-0.7 s of wall time (effective rate collapses from ~290 MHz at the menu to 6-14 MHz), with guest dispatch at 100%, parked time ~0, per-field dispatch counts LOWER than at the menu, GS worker idle 98%, DMA traffic tiny. The combat readData drains are real (~100-125 ms each, all rendered-class, all <=64 px) but exploration crawls with zero drains.

This milestone ships the instrument that names the mechanism: an [ee-prof] window on the same ~5 s cadence as [ee-work], splitting the window's guest wall time by execution kind, counting slow-path entries, and naming the top functions two independent ways. No fix ships in this build — the standing rule is counters first, conviction, then the fix — and the profile is built so that one owner run decides between the candidate mechanisms below. One structural finding from the source audit already narrows the field (section 2): this package contains no AOT-compiled VU programs at all, so every VU0 and VU1 microprogram runs in the cycle-accurate interpreter; whether that is where the 0.5 s goes is exactly what the VU buckets measure.

## 1. What the M14 window could not see

[ee-work] times guest dispatches as one block. Inside a dispatch, recompiled code calls back into the runtime constantly: VU0 microprograms (VCALLMS is an inline call into the runtime), VU1 starts (guest writes to the VIF1 FIFO fire callbacks synchronously), EE syscalls, and every load/store to a special address (VU memory, scratchpad, I/O registers — including the GS register polls). Any of those can burn arbitrary wall time while the counters M14 watched (dispatches, fields, cycles) stay innocent. [ee-prof] times those seams directly.

## 2. Mechanism candidates, checked in source before instrumenting

- **Per-dispatch overhead** — already ruled out by M14's arithmetic (in-game dispatches per field are ~470-900 vs ~3800 at the menu, yet the field is 25-50x slower in wall time). Not re-instrumented.
- **An EE interpreter / fallback path** — does not exist in this port. Guest EE code is 100% recompiled native functions, resolved through the dense generated table (main ELF) plus a paged module table (SNR2 overlays). There is no EE instruction interpreter to fall back into. The only "unknown target" path is a missing-function stub, which until now only ever printed its FIRST occurrence (a latched flag) and was otherwise silent — now counted, with distinct targets (see missfn). The scheduler-level count of thread entries with no function (g_loopStats.missing) takes the same report path.
- **VU0 microcode** — runs synchronously inside EE guest time: generated code inlines VCALLMS as a call to executeVU0Microprogram, which prepares state (the "lean" per-call register load, default on) and runs the VU0 interpreter (VU1Interpreter::run -> runLoopWith). COP2 macro instructions (VMUL and friends) are NOT in this bucket: they are inlined NEON/SSE in the generated code and count as native. VU0 is instrumented at two seams: the whole call (preparation + run + copy-back) and the run itself, so the per-call preparation gap is visible separately — this codebase has a history of per-call preparation dominating (Urban Reign, ~4500 VCALLMS calls per frame).
- **VU ahead-of-time compilation** — the runtime looks compiled VU programs up by FNV-1a hash of the 16 KB code image, and generated AOT sources are globbed from generated/vu1/*.cpp. **That directory does not exist in this tree: zero AOT programs are built into the package, so VU0 and VU1 both run 100% in the interpreter.** The pipeline to produce them exists in-tree (capture images with PS2X_VU0_CAPTURE / PS2X_VU1_CAPTURE, run the vu1_recomp tool with -DGODHAND_BUILD_TOOLS=ON, rebuild) — it is a milestone-sized job, not a switch. The profile counts runs that entered with a compiled program (`comp`), so the device run will show comp 0 everywhere, confirming this on device rather than by source reading alone.
- **VU1 execution** — started/resumed only from the two VIF1 FIFO callbacks (MSCAL/MSCNT). They run on whichever thread pushed the FIFO: the EE thread (inside guest time, inside a special-address store) or the async VU worker. Each callback executes in 65536-cycle slices and finishVu1Program continues up to a 1,048,576-cycle cap; VU1 cycles are also charged back into EE cycle accounting. Instrumented per callback with the thread split, plus per-run totals from the same runLoopWith recorder as VU0.
- **Memory traps / fastmem faults** — this port has no page protection and no fastmem fault path. Normal RAM access is direct pointer arithmetic in generated code (the ps2_runtime_macros.h fast path); the slow path is the special-address check routing to PS2Runtime::Load8/16/32/64/128 and Store8/16/32/64/128 (VU memory windows, scratchpad, I/O, GS registers). All ten wrappers are counted, with wall time subsampled 1-in-64 and scaled. A game that polls GS registers or pounds the scratchpad shows up here.
- **Syscalls** — every EE syscall funnels through one handleSyscall overload; timed whole.
- **Helper/emulation routines** (128-bit moves, vector emulation shims) — these execute either as inlined generated code (native bucket) or inside the timed seams above; there is no separate runtime "helper" dispatch layer to time. Naming WHICH functions burn the time is the job of the two top lists (section 4), which is the honest substitute.
- **Genuinely heavy native loops** — whatever is left after the measured buckets: printed as `native`, the residual, and cross-checked by the top lists.

## 3. What was built

A new counter channel, runtime/ps2xRuntime/include/runtime/ee_prof_stats.h (namespace ps2x::eeprof), following the gs_coupling_stats pattern from M13/M14: record functions + a Snapshot; storage and the top-list printer live in ps2_runtime.cpp. Writers:

- **VU runs** (vu/ps2_vu1_core.cpp, runLoopWith — the single funnel for VU0, VU1, compiled stretches and verify mode): an RAII recorder per run captures unit, start PC, interpreter cycle delta, whether a compiled program was present, whether the run ended on its cycle budget, and wall time. Two clock reads per run. (Verify mode would record its shadow runs too; it is off by default.)
- **VU0 whole calls** (executeVU0Microprogram): RAII wall timer after the invalid-program early return. The gap between this and the VU0 run total is the per-call preparation cost.
- **VU1 callbacks** (the MSCAL/MSCNT lambdas): wall timer + cycle delta per invocation, split by kind and by whether the calling thread is the EE scheduler's executor thread (a new read-only accessor on EeScheduler; no layout change).
- **Syscalls** (handleSyscall, the 3-arg funnel): RAII wall timer.
- **Missing functions** (reportMissingFunction): total count + distinct targets (64-slot claim table).
- **Special-address memory** (the ten Load*/Store* wrappers): one relaxed atomic increment per call; wall time from a shared per-thread 1-in-64 gate, scaled x64. Unsampled calls pay no clock reads.
- **Branch targets** (dispatchGuestBranch): one call in 32 is timed (two clock reads) and accumulated into an EE-thread open-addressing table (8192 slots) keyed by target PC. INCLUSIVE semantics: a timed call contains its callees, VU runs and parks — this is a where-does-time-go view, deliberately overlapping the exclusive buckets. Calls unwound by a dispatcher transfer exception are not recorded. Unsampled calls add exactly one counter increment to the 0.15 code path.
- **Guest position sampler** (EeScheduler::checkpointDue, full-accounting path only): every accounted cycle charge (deferred cycles included, fed exactly once at their flush) advances a reservoir; every 8192 guest cycles the running thread's current PC is recorded. At report time PCs are resolved to their recompiled function entry by walking back over identical dense-table entries; PCs outside the dense table (overlay modules) keep their raw address. Arithmetic only — no clock reads — on a path that already does full accounting.
- **Drain stage split** (gs/gpu/gs_gpu_backend.cpp, GPU backend bookkeeping only): the [l2h] line gains `stages:` — flush (the hazard flushFor(3) BeginTransfer runs before a local->host transfer), copy (copyRegion), mapread (readData, the map-shim drain itself), pack (packLocalToHost). Four time points around code that already exists; no new GL plumbing.

The printer lives in EeScheduler's window report, immediately after the [ee-work] line, under the same window and slide rules (windows with no fields and <1 ms guest print nothing).

**Overhead, stated honestly.** The profile is always on in this build (same precedent as [ee-work]/[gs-work]). Per guest call: one counter increment (branch gate), two clock reads on 1/32 of calls. Per special access: one atomic increment, two clock reads on 1/64. Per VU run / VU0 call / syscall: two clock reads. The position sampler adds a few arithmetic ops to the checkpoint full path. Worst case this is a few percent on call-dense code, and it lands inside the measured buckets themselves (the residual absorbs it) — the menu windows in the same log give the comparison baseline, since the menu ran at full speed under the identical instrumentation in every previous build's terms.

## 4. The [ee-prof] field dictionary

```
[ee-prof] guest G ms: native N ms | vu0 V ms (calls C: run R + prep P, X vcyc, interp I comp A budget B) | vu1 U ms (runs Rn, Y vcyc) vu1ee E ms (cb K, Z vcyc) vu1worker Wc/W ms | syscall S ms (Sc) | memslow ~M ms (L loads T stores) | missfn F (D distinct) | parked Pk ms
```

- **guest** — the window's wall time inside guest dispatches (the same guestMs as [ee-work]).
- **native** — residual: guest − parked − vu0 calls − vu1ee − syscall − memslow, clamped at 0. It is a FLOOR for recompiled-code time, not an exact split: VU1 callbacks fire inside special-address stores, so part of vu1ee also sits inside memslow and is subtracted twice; syscall implementations that touch the timed wrappers would do the same. Time the profiler cannot attribute can only push native down, never up.
- **vu0** — whole-call time (executeVU0Microprogram): **calls**, **run** (inside runLoopWith), **prep** = calls − run clamped >= 0 (lean register preparation + state copies), **vcyc** (interpreter cycles executed), **interp/comp** (runs that entered without/with an AOT compiled program), **budget** (runs cut by their cycle budget instead of ending on the E bit — many budget cuts mean programs are being sliced, not finished).
- **vu1** — all VU1 run time and cycles wherever they ran; **vu1ee** — the part executed synchronously inside the MSCAL/MSCNT callbacks on the EE thread (this is the part inside guest time), with callback count and VU cycles; **vu1worker** — callbacks that ran on the VU worker thread (count/time; NOT part of guest).
- **syscall** — count and wall time of EE syscalls.
- **memslow** — special-address Load*/Store* counts (every call) and estimated wall time (~, subsampled x64). GS-register polls and scratchpad traffic live here.
- **missfn** — missing-function reports in the window and the distinct-target total since boot. The scheduler's thread-entry misses take this same path (except when an invocation frame is active).
- **parked** — sum of the [ee-work] drain buckets, for the subtraction above.

```
[ee-prof:top] branch targets by time: 0xADDR ms (~calls) x up to 6
[ee-prof:top] vu0 programs by time: pc 0xPC ms (calls) x up to 3
[ee-prof:top] vu1 programs by time: pc 0xPC ms (calls) x up to 3
[ee-prof:top] guest cycles by function: 0xADDR % (~ms) x up to 5
```

- **branch targets** — inclusive, subsample-scaled (call counts are estimates, marked ~). Ancestor and callee both appear when both are hot; read it as "time passes through here".
- **vu programs** — exact run wall time per microprogram start PC (VU0 PCs are micro-memory byte addresses).
- **guest cycles by function** — the position sampler: share of sampled guest cycles resolved to function entry, with the share of the window's guest wall time as the ms estimate. This view is uniform per guest cycle and blind to runtime seams — it names the guest loops themselves. Function names for addresses resolve offline against recomp/godhand_functions.csv.

And on combat windows, [l2h] gains: `stages: flush F ms copy C ms mapread M ms pack P ms` — summed over the window's synchronous drains.

## 5. What each pattern convicts

| Reading | Conviction |
|---|---|
| vu0 dominates, run >> prep, few programs in the vu0 top | VU0 interpretation of those microprograms. Next milestone: the AOT pipeline (capture -> vu1_recomp -> generated/vu1) for exactly those images. |
| vu0 dominates with prep comparable to run | Per-call preparation (lean load / state copies) at very high call counts. A preparation diet is semantics-preserving bookkeeping — a fix candidate inside a normal milestone. |
| vu1ee dominates (vu1 runs small on the worker) | VU1 programs executed synchronously on the EE thread via VIF1 writes — the game starts VU1 from the EE and the slices + finish continuation burn guest time. |
| native dominates AND the two top views agree on one or two functions | Genuinely heavy recompiled loops — the named functions are the optimisation target (or a game-side spin the profile makes visible for the first time). |
| native dominates but branch top and cycle top DISAGREE | Time is spread across call chains rather than loops (branch view) vs long straight-line functions (cycle view) — read both before concluding. |
| memslow dominates | Special-address pounding (GS register polls, scratchpad, VU window). Which sub-path needs the wrapper's caller context — a follow-up profile round, or a semantics-preserving fast path for the specific register range if one is provably side-effect-free. |
| syscall dominates | Kernel-call cost; the specific syscall needs naming next (the syscall id is in the funnel if a second round is needed). |
| missfn nonzero and growing | Real missing targets are being stubbed every window — a correctness cost and possibly a time cost; the distinct count says whether it is one hot target or many. |
| budget cuts (vu0/vu1) numerous | Programs routinely sliced by budget rather than finished — interacts with whichever bucket owns the time. |
| [l2h] stages: mapread ≈ the whole drain | The ~110 ms is the map-shim wait itself (GPU pipeline latency on a tiny read) — favours widening the async readback cache to these small rendered reads, with the guest-visible staleness weighed explicitly. |
| [l2h] stages: flush or copy dominate | The drain pays for prior rendering work (batch flush / copy dispatch), not the read — favours fence-scoped partial flush work instead. |

## 6. Fix decision

None ships in 0.16-m15, by the milestone's own rule: the profile is the deliverable, and no mechanism is convicted until the device run reads it. The one structural fact already established — **no AOT VU programs in the package, both VUs 100% interpreted** — makes the VU AOT pipeline the leading candidate for milestone 16 IF the vu0/vu1ee buckets convict interpretation: capture the game's VU images on device (PS2X_VU0_CAPTURE / PS2X_VU1_CAPTURE over a title + village + fight session), build vu1_recomp (GODHAND_BUILD_TOOLS=ON), generate into generated/vu1, rebuild, and verify with the same profile (comp counts rise, interp falls, and the interpreter remains the fallback for any image not compiled — the mechanism is semantics-preserving by construction, since compiled programs are verified against the interpreter's semantics by the existing runVerifiedWith machinery when enabled). That is deliberately NOT improvised here: it needs a device capture session and its own verification pass.

## 7. Scope and the toggle-OFF argument

Changed: new include/runtime/ee_prof_stats.h; runtime/ps2xRuntime/src/lib/ps2_runtime.cpp (channel storage, timers, counters, branch subsample); runtime/ps2xRuntime/src/lib/vu/ps2_vu1_core.cpp (run recorder); runtime/ps2xRuntime/src/lib/Kernel/EeScheduler.cpp (sampler, printer, window snapshot) + one read-only accessor in include/runtime/ee_scheduler.h; runtime/ps2xRuntime/src/lib/gs/gpu/gs_gpu_backend.cpp (drain stage bookkeeping inside the GPU backend only); Android version strings (manifest, glue, three Java files).

With the GPU renderer toggle OFF, the app executes the CPU backend exactly as in 0.15: no CPU-backend or rasterizer source was touched, no shader source changed, and every runtime change is a counter, timer, sampler or GPU-backend bookkeeping that does not feed any execution, rendering or scheduling decision. The Windows/desktop branch and generated game code are untouched. No game data is in the package, as always.
