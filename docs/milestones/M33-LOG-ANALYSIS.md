## Verdict first

- **The premise failed on device.** L2 (the callback diet: lean execute + capture bitset) was priced to cut the vu1worker − vu1 gap from 17.1% of worker time to ~5–10% (3.77 µs/run → ~1.1–2.2 µs/run). The returned session's gap is **15.0% pooled over gameplay (7,674 ms of 51,201 ms worker time, 3.26 µs/run)** — a −2.1-point share improvement and −13.5% per run against a priced recovery of 40–70%. Worker time per run overall moved 21.98 → **21.78 µs/run (−0.9%)**. The honest expectation printed in the build report (worker busy −7–12% in heavy windows) did not happen; the owner's "feel unchanged from m32" is the accurate summary of this line.
- **The bench was not lying; it was measuring a smaller thing than the device gap.** The bench A/B isolated the fixed stack around a clean-ending run at ~0.37 µs (off) → ~0.18 µs (lean). The device gap is 3.26 µs/run — roughly eighteen times the lean bench stack. Whatever dominates the device-side gap (per-run worker overhead outside the [ee-prof] vu1 run accounting) is not the scheduler reset or the capture map increment, and no counter in this log decomposes it further. L2 removed the part it aimed at; the part it aimed at is a minor share of the device gap. That is the finding, and it closes the gap-diet direction until the gap is decomposed by instrumentation (see Next lever).
- **Attribution moved — but in a pattern that points away from the lever.** Pooled gameplay ns/vcyc is **10.70** vs m32's 10.28 (+4.1%), which fails the "stays ~10.28" check as a pooled line. The failure is entirely in the session's second half: windows 5–10 pool at **9.52** (better than m32), windows 11–20 pool at **11.47**. In the late windows every program inflates together (0x0358-cd8f 16.7 → 25.4 µs/call across the session, 0x0520-2cfd 14.0 → 18.7, 0x00c8 26.0 → 64.9, 0x2378 10.8 → 15.1) — a uniform, load-coincident, machine-state pattern. Lean execute does not touch run code (bench cycle counts were identical apart from the +16 gap cycles, digests identical), so a uniform late-session inflation of programs it never modified is not a lean signature; it is what a hot, saturated SoC does to every thread on it. Stated plainly: the pooled attribution line FAILS, the lever is not the plausible cause, and cross-session pooled comparisons at this session length (~100 s of windowed play, most of it crowd) carry a thermal/saturation confound this log cannot subtract.
- **The 0x0358 split landed, and it is maximally uneven — this is the session's decisive new fact.** Entry 0x0358 exists in two captured images. In the device tops, only one of them ever appears: **img cd8f1fc2068bd71d — 11,955.4 ms over 566,263 calls = 21.11 µs/call, present in all 17 profile blocks, 31.9% of all listed program time and 27.5% of gameplay run time.** The second copy (img 5dce334b68799d95) appears in **zero** of the 17 top-6 lists; even if it sat just under the top-6 cut in every block it would total under 1,684 ms against cd8f's 11,955 ms, and the realistic reading is that it is negligible on device. There is no merged-figure ambiguity left: 0x0358's device cost is one image's cost, and it can be aimed at as one image.
- **Outcomes barely moved, in the directions the build honestly allowed.** Heavy fields/s: floor **41.8** (m32: 41.6 — unchanged), ceiling **56.7** (m32: 55.7), median 53.1 (m32: 52.9). Worst join **938.9 ms** (m32: 1,040.9, −9.8%) — inside the build report's own honest band of ~920–970 ms, but four gameplay windows carry joins of 842–939 ms, and the median gameplay join rose to 413.1 ms (m32 heavy median: 119.5 ms; the sessions differ in composition — this one is sixteen straight gameplay windows, thirteen of them at VU ≥ 57% — so the medians are not like-for-like, while the worst-join comparison at matched peak load is).
- **Correctness: clean on every observable.** Zero `[vu1-lean]` lines in the entire appended log, dropped_captures = 0 in all 17 pipeline lines, interp/fb/budget = 0 in all 20 profile blocks with comp = runs everywhere, the capture set is byte-identical in membership to m32's return (same 5 images, same 22 (image, entry) pairs), and the owner reported no visual defect of any kind. The staleness failure signature this lever risked did not appear in anything the return can see (limits stated in the correctness line below).

## Premise verdict — L2, the callback diet

**Not delivered on device.** The mechanism is real in isolation (bench: fixed stack 0.37 → 0.18 µs per execute, ~51% recovered, all soaks byte-identical, audit checker clean at scale) and the build is correctness-clean on device (line 7). But the device gap it was priced against — 3.77 µs/run in m32 — turned out to be mostly something else: with the reset and the capture-map increment both removed or reduced to an atomic op, the gap stands at 3.26 µs/run and holds its share (~15%) as runs lengthen, which a fixed stack cannot do. The measured outcome of the whole lever on the layer it aimed at is worker µs/run 21.98 → 21.78 (−0.9%) and gap share 17.1% → 15.0%. Against the build report's honest expectation (−7–12% worker busy, +1–3 fields/s in mid crowds, ceiling 57–59, worst join ~920–970), only the worst-join band and the ceiling's lower edge landed (938.9 ms; ceiling 56.7) — and both are within session variance of m32, so even those cannot be credited to the lever with a straight face. The remaining measured walls, in order: 0x0520's run cost (17,828.9 ms, 41.0% of gameplay run, already L1-harvested twice, both copies even at ~17 µs/call); **0x0358-cd8f's run cost (11,955.4 ms, 27.5% of gameplay run, 21.11 µs/call, L1-unresponsive)**; the gap (7,674.2 ms, 15.0% of worker, composition unknown — not attackable until decomposed); then the join bill as a consequence of saturation. GIF volume (274.5–525.8 MB per gameplay window, GS idle 50–76%, median 68%) and the job layer (drain + publish 0.46% of split busy, consumeBytes 0.00 MB) are ruled out by this log's own counters, as before.

## Next lever for m34 — PATH-STAGEPROG: one image, pc 0x0358 img cd8f1fc2068bd71d

**The lever.** Stop treating 0x0358 as a merged program. The split this build carried as a passenger has decided the question it existed to decide: there is exactly one 0x0358 that matters on device — the cd8f1fc2068bd71d copy, 566,263 calls in this session alone at 21.11 µs/call, 27.5% of gameplay run time, present in every profile block. m34 is a single-image attack on that copy, in two steps with a gate between them:

1. **Step 0 (decomposition, the gate).** Profile this one image's cost composition offline from the captured binary (`vu-capture/vu1_cd8f1fc2068bd71d.bin` is already in this return) on the fixture rig, in the PATH-THROUGHPUT step-0 discipline: what fraction of its 21.11 µs/call is FMAC-class (already fast — expect little, the L1 fixture said this image's class gained only ~5%), what is loads/stores and address arithmetic, what is scalar/integer and branch overhead, what is divider/EFU or other stall-class work. The m32 fixture numbers for the responsive 0x0358 image (−33.5%) must not be assumed for this copy; this copy is the other one. If no single removable class prices at ≥ ~15% of the entry's cost, stop and report — the same stop rule L1's step 0 carried.
2. **Step 1 (the fast path for the dominant class).** Whatever class step 0 names gets the L1-style treatment: a targeted fast path inside this image's compiled code, kill-switched (`PS2X_VU1_FAST_STAGE=0` restoring the current codegen for this entry), verified by the same soak discipline (digests, the sign-of-zero accepted class only, sequence equality). One image, one class, one switch.
