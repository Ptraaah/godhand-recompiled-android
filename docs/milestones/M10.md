# Milestone 10 — A/B the GPU renderer (0.11-m10)

State after M9 and the owner's 0.10 device run (log of 2026-11-02
03:11 WITA, the first full measured title minute): the
`[frame-split]` verdict on the PRESS START title is decisive.
Healthy windows (intro/FMV) run 17.5–18.4 ms with gs-fetch at
62–78%; once the title settles, three consecutive windows read
742.3 / 679.2 / 768.0 ms average with **gs-fetch at 99–100%**,
sync/draw/swap/rest all ~0, and fields advancing normally
(+224..+300 per window — the guest is producing fields on time).
A fourth window (123.1 ms, gs-fetch 99%) catches the transition.
The wall is the fetch/present leg of the CPU rasteriser:
`UploadFrame()` → `latchHostPresentationFrame()` (backend
Flush/Sync/Present) + framebuffer copy + texture upload, every
frame, for a scene that barely changes. Every other suspect is
measured and cleared (IOP, both disc routes, present/compositor,
draw, guest execution). This build A/Bs the one path never tried
on this phone: the port's own GPU backend, behind an owner
toggle, with the witnesses left running so the comparison is
number against number.

## 1. How the port selects its backend (source evidence)

The GS frontend constructs its backend through one factory —
`GSThreadedBackend::MakeDefault()`
(`runtime/ps2xRuntime/src/lib/gs/gs_threaded_backend.cpp:157`),
called from the frontend's constructor and reset paths
(`gs_frontend.cpp:336, 348, 2089`):

```cpp
const char *gpu = std::getenv("PS2X_GS_GPU");
const bool useGpu = (gpu && *gpu) ? *gpu != '0' : s_gpuByDefault.load();
if (GSPcsx2Backend::Requested())
    return std::make_unique<GSThreadedBackend>(std::make_unique<GSPcsx2Backend>());
if (useGpu)
    return std::make_unique<GSThreadedBackend>(std::make_unique<GSGpuBackend>());
```

Three facts follow:

- **The gate is the `PS2X_GS_GPU` environment variable**, read by
  `getenv` at backend construction — inside `godhand_port_main`,
  at runtime initialisation. It is *not* a load-latched constant,
  so it does not suffer the M9 autopsy's failure mode: a `setenv`
  from the Android glue in `main()`, before `godhand_port_main`
  is called, is the value that lands.
- **The port's own code defaults GPU on**: `src/main.cpp:654`
  calls `GSThreadedBackend::SetGpuByDefault(true)` (with the
  comment that both sibling ports ship these defaults). But the
  env, when set to anything non-empty, wins over that default in
  the expression above.
- **Inside the app, the env has always been "0".** The Android
  glue pre-set `PS2X_GS_GPU=0` as a no-overwrite default from
  Milestone 2a on (`godhand_android_main.cpp`, next to the
  prefetch preset M7 found), so the GPU backend has never been
  selected in any shipped build — the desktop default never got a
  say. The M2A note's mechanism was right; what was missing was
  any way for the owner to flip it.

`PS2X_GS_RENDERER=native` (the ini value in every boot log) is a
separate axis — it chooses the port's own GS frontend over the
PCSX2 GS — and is untouched by this build.

## 2. What the GPU backend is

`GSGpuBackend` (`runtime/ps2xRuntime/src/lib/gs/gpu/gs_gpu_backend.cpp`,
~3,600 lines, plus `gs_gpu_shaders.cpp` ~1,500 lines and the
`GSGL` layer in `gs_gl.cpp/.h`) is a compute-shader GS emulator:
it rasterises through GLSL compute shaders with SSBOs
(swizzle tables, CLUT, texture pages), renders into GL
framebuffers, and its `Present()` either publishes into a shared
host texture or reads the frame back into a pixel buffer the
present loop uploads (`presentAsync` / `readData`) — the same
`PresentationFrame` the CPU backend returns, so the M9 present
loop and `[frame-split]` consume it unchanged. It maintains its
own GL context through `GSGL::Context`, separate from the host
window's context, with worker contexts shared from it.

It is a desktop-GL design end to end:

- The shader prefix is built as the literal
  `"#version 460 core\n"` (`gs_gpu_backend.cpp`, in `ensure()`),
  and the shaders use compute/SSBO idioms throughout.
- `GSGL::Context::Create` is implemented **for Windows only**:
  a hidden `CreateWindowExA` window, `wglCreateContextAttribsARB`,
  a core-profile WGL context. The shared-present host capture
  (`GSSharedPresent::CaptureHostContext` etc.) is likewise
  WGL-based.
- The API table it fills is desktop GL (program binaries,
  persistent-mapped buffers, `glMaxShaderCompilerThreads`, NV
  conservative rasterisation).

## 3. The blocker, precisely: init, not compile or link

Milestone 10's first question was whether the Android build even
contains this backend. It does:

- **Compile: yes.** `gs_gpu_backend.cpp` and `gs_gl.cpp` are in
  the Android build's `build.ninja` and have been compiled into
  `libgodhand.so` all along (the threaded wrapper also
  `dynamic_cast`s its inner backend to `GSGpuBackend*` at
  `gs_threaded_backend.cpp:532`).
- **Link: yes.** The packaged 0.11 library carries the backend:
  14 `[gs-gpu]` format strings are present in the shipped `.so`.
- **Init: no — and this is the whole blocker.** Outside
  `#if defined(_WIN32)`, `gs_gl.cpp` compiles a stub:

```cpp
bool Context::Create(std::string &error)
{
    error = "GPU GS backend is only implemented for Windows";
    return false;
}
```

  (with `PublishShared`/`SharedAvailable` and the
  `GSSharedPresent` host functions stubbed to false alongside).
  That exact error string is present, once, in the packaged
  Android `.so` — the stub is the code Android runs. There is no
  GLX, EGL or GLES branch at all: desktop Linux hits the same
  stub. The failure mode is defined by `GSGpuBackend::Impl::ensure()`:
  the first GS call prints `[gs-gpu] GPU GS backend is only
  implemented for Windows` to stderr (the boot log), latches
  `failed = true`, and every entry point then no-ops;
  `Present()` returns an empty frame
  (`if (!d.ensure()) return result;`). By source, an ON run is
  therefore expected to **keep running** — guest fields advance,
  sound plays, the FPS label ticks, `[frame-split]` prints —
  **but produce no new picture** (black screen, or the last CPU
  frame frozen, depending on what the latch does with an empty
  frame). A crash is *not* the predicted outcome; if the device
  run crashes anyway, that is new information, and the log is
  the evidence either way.

Why no minimal fix was attempted: making `Create()` work on
Android means writing an EGL shared-context implementation
against raylib's context (which the port does not expose to the
GS layer), replacing the WGL shared-present host path, and
auditing ~5,800 lines of backend + shaders written against
`#version 460 core` for translation to GLES — the GPU-renderer
port M5 already sized as the largest milestone in this project,
with wrong-pixels risk throughout. Faking a smaller version of
it to make the toggle "do something" would produce numbers that
mean nothing. The honest deliverable is the toggle, the default
untouched, and this autopsy: the GPU path blocks at **context
creation**, before a single shader compiles.

## 4. What changed: the toggle, plumbed like disc prefetch

No runtime source file is modified in this build. The native
rebuild recompiled exactly one translation unit — the glue.

- **Launcher** (`LauncherActivity.java`): a new settings row
  "GPU renderer (experimental)", below Disc prefetch, backed by
  the boolean preference `set_gpu`, default off, same
  tap-to-toggle + refresh pattern as every other row.
- **Holder** (`IsoHolder.java`): `optGpuRenderer` (default
  `"off"`) with the `gpuRenderer()` accessor, mirroring
  `optDiscPrefetch`/`discPrefetch()`.
- **GameActivity**: copies `set_gpu` into
  `IsoHolder.optGpuRenderer` (`"on"`/`"off"`) with the other
  settings, before `System.loadLibrary`; the Java "settings
  loaded" log line gains `gpu=`.
- **Glue** (`godhand_android_main.cpp`): caches the
  `gpuRenderer` method ID in `cacheJni`; in the settings block
  it reads the holder value and sets the port's real gate with
  overwrite — `setenv("PS2X_GS_GPU", gpuOn ? "1" : "0", 1)` —
  replacing the silent no-overwrite default that stood at the
  top of `main()` since Milestone 2a. Anything but an explicit
  "on" (including a failed bridge lookup) resolves to off. The
  old site keeps a comment recording the move.
- **Boot-log proof, every run**: the glue's settings line now
  ends `... prefetch=off gpu=off`, followed by the dedicated
  line in the same style as disc prefetch:

  ```
  renderer: cpu (owner setting)
  ```

  or, with the toggle on:

  ```
  renderer: gpu (owner setting)
  ```

  A GPU run then carries the backend's own testimony a few
  seconds later: `[gs-gpu] GPU GS backend is only implemented
  for Windows`. The pair — owner line says gpu, backend line
  says where it stopped — is the complete evidence chain; a CPU
  run is proven by `renderer: cpu (owner setting)` plus the
  ordinary `[frame-split]` numbers.
- **Witnesses unchanged**: `[frame-split]`, `[iop-thread]`, the
  refill and adma summaries, `[frame-stats]`, the FPS counter —
  all exactly as in 0.10, so an ON run's numbers sit directly
  beside 0.10's. (Prediction worth checking in the ON log: with
  no pixels produced, gs-fetch should collapse toward the
  healthy-window shape or lower — the fetch leg is precisely
  what an empty `Present()` skips.)
- Everything else is byte-for-byte 0.10 behaviour: async CD
  cache, overlay + EDIT mode, remapping, all other settings and
  defaults, the M8 launcher (ScrollView, Share boot log third).
  With the toggle off, the env value delivered to the port is
  `"0"` — the identical value the silent default always
  delivered — so the default run is the 0.10 run.

## Owner A/B steps

1. **Run A (control).** Install 0.11-m10 over 0.10. Leave the
   new "GPU renderer (experimental)" row **OFF** and every other
   setting as it is. START, sit at the PRESS START title for a
   minute, note the FPS counter (expect ~1 FPS, as in 0.10),
   exit, **Share boot log** (third button) and send the file.
   This run re-proves the default path on the new build: its log
   should read `renderer: cpu (owner setting)` with
   `[frame-split]` title windows like 0.10's.
2. **Run B (experiment).** In the launcher, tap "GPU renderer
   (experimental)" to **ON**. START and go to the same title for
   a minute. Note the FPS counter — and note **what the screen
   does**: by the source, the expected picture is sound playing
   and a black or frozen screen (the backend refuses to create
   its context and produces no frames), but whatever it
   actually does is the result. If it crashes, shows garbage,
   or — against the source's prediction — shows a picture, all
   of those are valid outcomes of this experiment. Exit, Share
   boot log, send the file.

Reading the pair together: run A's log anchors the build
(`renderer: cpu`, familiar numbers). Run B's log either shows
the `[gs-gpu]` line that confirms the init blocker on real
hardware — closing the GPU question until someone funds the
EGL/GLES port as its own milestone — or it surprises us, in
which case its `[frame-split]` lines say what the GPU path did
to the fetch leg and the A/B becomes a performance comparison
after all.
