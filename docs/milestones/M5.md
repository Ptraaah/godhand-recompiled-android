# Milestone 5 — the owner's-controls release (0.6-m5)

0.5-m4 played on the owner's POCO F5 — landscape, no time limit, the pad
detected (the game's button prompts even switched to controller style) —
but his verdict named the defects: the touch overlay was INVISIBLE on
screen, there were no settings and no FPS counter he could switch on,
the game still stuttered (his log showed "[cd-read] slow host read:
41 ms" and "51 ms" from the disc image), and — added by the owner while
this milestone was being briefed — there was NO SOUND at all, he wanted
to move and remap the buttons himself, and the lag work was to be
treated as top priority. 0.6-m5 is all of it in one package: same
package dev.ptraaa.godhand, same signer (SHA-256 9791d26c…dbc9005e),
versionCode 6, installs as an update over 0.5-m4 (preserved at
package/godhand-android-0.5-m4.apk.bak), ISO copy reused.

## 1. The invisible overlay — root cause and fix

Root cause: the overlay was a view inside the activity. NativeActivity
takes ownership of its window's surface for the native renderer
(Window.takeSurface): the surface the views would draw into is the very
surface raylib presents the game into, up to 60 times a second, so every
UI draw was overwritten by the next present before the compositor ever
showed it. It was never an opacity problem — the button labels were
near-opaque white (alpha 225/255) and would have shown over the dark
boot screens had a single draw survived; and the pad demonstrably
worked (the native side saw it, touches were wired), only compositing
failed.

Fix: the overlay now lives in its OWN window. GameActivity adds
TouchOverlay through WindowManager (TYPE_APPLICATION, TRANSLUCENT,
FLAG_NOT_FOCUSABLE so gamepad keys keep flowing to the game window,
FLAG_NOT_TOUCH_MODAL), and the system compositor layers that window
above the game surface — the same mechanism that lets an on-screen
keyboard draw over a game. Paints were also raised (stick base fill
alpha 56→110, button fill 84→130, strokes ~130→200+, labels fully
opaque), scaled by the owner's opacity setting. And after the first
layout the shell writes ONE boot-log line with every control's
on-screen bounds — "overlay layout (0.6-m5): root=… stick_left=[x,y
WxH] btn_triangle=[…] …" — so a future invisibility can be told apart
from a zero-size/misplaced layout from the log alone.

## 2. Settings (launcher, before starting the game)

A SETTINGS section in the launcher: big cycle buttons, saved to
SharedPreferences the moment they are tapped, read by GameActivity at
game start. Scale / threads / vsync travel through the IsoHolder static
bridge (the M3 pattern) and the glue turns them into the port's
environment — they REPLACE Milestone 4's hard overwrites. The glue logs
one line at boot: "settings: owner chose scale=… fps=… threads=…
vsync=…", next to the port's own [BOOT] settings lines.

- Internal resolution scale: 0.5 / 0.75 / 1 / 1.5 / 2 / 3 →
  PS2X_GS_SCALE (default 1).
- Show FPS: on/off (default ON) → the FPS label in §3.
- Thread policy: off / on → PS2X_THREAD_POLICY off / auto. The values
  the runtime accepts are off|auto|spread|ccx; on Android there is now
  exactly one implementation (§5), so the toggle maps on → auto.
  Default ON — see §5 for why that is safe.
- VSync: on/off → PS2X_VSYNC 1 / 0. The port honours it in windowed
  mode (ps2_runtime's vsyncEnabled(): unset or ≠'0' = real vsync,
  '0' = the software 60 FPS limiter), so the toggle is real, not
  decorative. Default on.
- Overlay opacity: low / medium / high (default HIGH this build) →
  scales every overlay paint alpha (1.0 / 0.72 / 0.45).
- Button size: 80–140% in steps (default 100%) → scales every control.

## 3. The FPS counter

The port's own PS2X_SHOW_FPS overlay was NOT used, deliberately. Its
draw path is raylib DrawText/DrawRectangle into the game surface — a
different path from the button-prompt sheet builder whose "build
failed" appears in the device log (that builder, sheets::buildIconSheet
in button_prompt_sheets.cpp, composites replacement textures for the
game's prompt art; it neither uses nor proves raylib text) — but
whether raylib's default font renders in this Android build cannot be
proven from the VM, and its numbers are the wrong ones anyway: the
overlay's "Game FPS" counter is fed by noteGameFrame(), which this
port never calls (TODO in the port's main: the game main-loop address
is unknown), so it would have shown Game 0 forever.

What shipped instead (the brief's fallback): the runtime now keeps
present-interval statistics in ps2_host_display (fed once per host
present by the existing FpsOverlay::present()): a one-second window of
presents/sec + worst interval, plus cumulative average and spike
buckets. The glue exposes fpsText() ("47 FPS - worst frame 63 ms")
through a new JNI entry on the existing TouchPad bridge, and the shell
polls it ~2x/second into a plain Java TextView in the overlay window —
visible by the same construction as the controls, and only when the
setting is on.

## 4. Stutter — the CD readahead cache

The read path behind the owner's slow lines is readHostRange (Kernel
stubs' Support.h): one persistent ifstream per file, but every
sceCdRead still did its own seekg + small read, synchronously, on the
EE thread. On his phone's flash that cost 41 ms for 315,392 bytes and
51 ms for 4,096 bytes.

Now in front of the stream, under the same lock: a block cache of
4 MiB file-aligned blocks, 8 blocks LRU (32 MiB max). A read of
≤ 2 MiB is served from blocks (memcpy on a hit); a miss fills the whole
block in one sequential read; a miss on the block after the previous
miss for the same file also prefetches the next block, so AFS/movie
streaming stops touching the disk. Reads > 2 MiB bypass the cache.
Guest-visible behaviour is unchanged: identical bytes, identical
zero-fill past EOF, identical error contract, no timing semantics
touched. Evidence in the next device log: a "[cd-cache] after 60 s:
hits=… misses=… prefetches=… served-from-cache=… bytes, disk-read=…
bytes" line (then every 300 s), and slow fills keep a "[cd-cache] slow
block fill" line so a genuinely slow disk still shows.

VM-side measurement: the VM's only disc image is the 4.7 MB synthetic
one (the full ISO exists only on the owner's phone), and its boot stops
at the port's own IRX gate before guest CD streaming starts, so a
like-for-like read benchmark cannot be produced here — the honest
before/after pair is his 0.5-m4 log (41/51 ms small reads) against the
[cd-cache] stats line in his 0.6-m5 log. The cache code was
compile-verified on the Android target (every TU that includes the
header rebuilt clean); a host (Linux) rebuild was started as a
regression check but escalated into a 13,221-step rebuild of the whole
generated game code and was stood down as disproportionate for a disc
that cannot exercise the path anyway.

## 5. Lag — thread policy, frame-time evidence

Thread policy review finding: on non-Windows, thread_policy.cpp's
startFromEnvironment() was an EMPTY STUB — PS2X_THREAD_POLICY did
nothing at all on Android (and the phone's godhand.ini shipped it as
off anyway). The Windows policy (off|auto|spread|ccx) reads the CPU
topology and pins the emulator's named threads by core.

What shipped: a reduced Linux/Android implementation in the same file,
safe by construction, and therefore the default is ON (the setting can
turn it off):
- the heavy threads are found by name in /proc/self/task — the runtime
  names them through ThreadNaming (pthread_setname_np on Linux):
  GameThread, GSThread, VUThread, GIFThread, the GSBand raster workers;
  the IOP worker is named to match in this build, as is the main thread;
- each is given the PERFORMANCE cluster as affinity — every core whose
  max frequency is ≥ 70% of the fastest core's (the POCO F5's Cortex-X2
  + A710 cluster), intersected with the affinity mask the OS already
  allows the process. No thread is ever confined to a single core,
  nothing outside the allowed mask is requested, unknown threads are
  never touched;
- flat/unreadable topology (performance cluster == everything) or an
  OS refusal logs one "[thread-policy] android: …" line and leaves the
  threads to the scheduler. Applied placements log one line per thread,
  so his next boot log shows exactly what it did.

Frame-time instrumentation: the statistics of §3 are also logged by a
detached glue thread every 120 s: "[frame-stats] presents=N avg frame
X ms worst Y ms | <=16.7ms:… <=25ms:… <=33ms:… <=50ms:… <=100ms:…
>100ms:…" (a post-main line was not possible — a full session ends
inside the port via std::_Exit). The next perf step reads these
numbers, not impressions.

## 6. Button editor + remapping (owner addition)

Layout editor, on the overlay itself: an EDIT pill at the top centre of
the game screen. Tapping it enters edit mode — overlay input into the
game is suspended (TouchPad gate), every control gets a bright outline,
and any control (both sticks and all ten buttons) can be DRAGGED
anywhere with a thumb; releasing it saves its position
(SharedPreferences lay_<id>_x/y). DONE leaves edit mode; a RESET pill
(in edit mode, and a "Reset button layout" button in the launcher)
restores the default arrangement. Button SIZE is the launcher's size
setting (§2) — one thumb-simple stepper instead of per-button resize
handles.

Remapping, in the launcher: a REMAP section with one cycle row per
control — the ten touch buttons (face four, L1/L2/R1/R2, Start, Select;
the sticks are layout-only) and the gamepad's A/B/X/Y, L1/R1, L2/R2,
L3/R3, Start, Select — each row cycles through all 16 PS2 controls.
Implementation follows the existing architecture: PadMapping holds the
model, TouchPad's merge layer resolves control → target when writing
(a target of L2/R2 writes the trigger axis, as the port's bindings
expect), GameActivity's gamepad handlers resolve key → target the same
way, and the native side is byte-identical in behaviour (one merged
bitmask + axes through the same JNI). Applied at game start; a "Reset
mapping" button restores the standard layout.

## 7. No sound — the audio chain, traced

The chain, end to end: IOP SPU2 mix → flushAudio → the IOP host
adapter's submitPcm → PS2AudioBackend's ring buffer → a raylib
AudioStream callback → raylib's device (miniaudio; AAudio with OpenSL
ES fallback) → the phone. Every link from the SPU2 to the stream is
platform-neutral code that produces sound on desktop; the audio
machinery is verifiably in the binary (miniaudio + AAudio are linked,
the configure log shows "Audio Backend: miniaudio"); no mute gate is
set in windowed mode (PS2X_AUDIO_MUTE is only defaulted on by the
port's headless branch, and the 0.5-m4 settings block shows it unset).
The [spu2-silence] lines in his log are a mixer diagnostic for
momentary dropouts, with loud SPU2 output around them — samples were
being produced; the failure is in the last, Android-only leg, and that
leg was a black box: raylib logs to logcat on Android, which the boot
log never sees, so 0.5-m4 carried zero audio evidence.

What shipped: the black box is opened. The glue installs a raylib
TraceLog callback that forwards raylib/miniaudio's own lines into
godhand-boot.log ("raylib: AUDIO: Device initialized successfully",
"> Backend: miniaudio | AAudio", or the failure warnings if the device
did not open). The runtime logs "[audio] InitAudioDevice: device
ready / DEVICE NOT READY" after InitAudioDevice; the backend logs
"[audio] output stream created and playing … PS2X_AUDIO_MUTE=…" when
the stream is made; and the first time the device actually pulls
samples, "[audio] device callback alive: the audio device is pulling
samples". His next boot log therefore proves which link is dead: no
"device ready" = miniaudio could not open a device (its reason is in
the forwarded lines); ready + stream playing + no callback line = the
device opened but never runs (the AAudio-on-this-ROM failure shape, and
the next step would be forcing the OpenSL path); callback alive +
silence = the samples themselves, chased with PS2X_AUDIO_OUT_DUMP.
No code in the chain was found broken by inspection, so no speculative
rewrite was shipped in its place — the fix in this build is that the
path is now observable end to end, with each link's verdict on record.

## 8. The deep cure — GPU renderer verdict (proposed milestone 6)

The known ceiling stands: the game renders through the port's CPU
rasteriser (the "native" GS, software, at internal scale 1), while the
port's GPU backend exists but its shaders are desktop GLSL (#version
460) that do not compile on Android's GLES. Evidence for the verdict:
the 0.5-m4 run held together at scale 1 on the CPU path with the
bottleneck in host CD reads and rasterisation; this build removes the
CD stalls and adds the frame-stats line — milestone 6 should start
from those numbers (if avg frame is already near 16.7 ms in quiet
scenes and spikes concentrate in draw-heavy scenes, the rasteriser is
the wall and the GPU port is the cure; if spikes track disc areas
instead, the cache numbers will say so first).

Estimated size of the GPU port: the GS GPU backend is a self-contained
backend behind the same GS interface (gs_gpu_backend.cpp +
gs_gpu_shaders.cpp + the shared-present path). The work is (a) shader
translation: the backend's GLSL 460 shaders (a bounded set — vertex/
fragment pairs for the draw, copy and present paths) re-expressed in
GLES 3.0/3.1 ES, mostly mechanical (version header, precision,
texture/sample syntax, integer ops) with a few real differences
(compute/image features may need fallback paths); (b) the backend's GL
calls audited for desktop-only entry points; (c) the present path
(currently a CPU upload into a raylib texture) re-plumbed so the GPU
frame stays on the GPU. Realistic estimate: the largest single
milestone of the project so far — several focused build cycles, on the
order of the M1 generation + M2 shell work combined, with the shader
set's true size the main unknown until a first compile pass lists
every error. Risk: moderate-high — not architectural (the backend
interface already isolates it, and the CPU path stays as the fallback
behind PS2X_GS_GPU), but fiddly: silent wrong-pixels failures are the
classic failure mode, and the only renderer judge is the owner's eyes
on device. What it unlocks: internal resolution above 1 without the
CPU cost (the scale setting becomes a real quality lever instead of a
slowdown dial), the frame budget the CPU rasteriser cannot reach in
draw-heavy scenes, and headroom for the IOP/EE threads on the cores
the rasteriser gives back. Recommendation: do it as milestone 6, but
gate it on this build's [frame-stats] evidence from real play first.

## Owner steps

1. Install godhand-android.apk (0.6-m5) over the current app — same
   signer, it lands as an update; the ISO copy from 0.4 is reused.
2. Open the launcher: the SETTINGS section is under the Start button.
   Suggested first test: Internal resolution 0.75x, FPS counter ON,
   Thread placement ON, VSync ON, Button opacity high, Button size
   100%. (Remap only if you want a button somewhere else — the
   standard layout is the default.)
3. Tap Start. The game opens in landscape with the controls VISIBLE
   over it and the FPS counter at the top. If you want the buttons
   somewhere else: tap EDIT (top centre), drag them, tap DONE.
4. Play a few minutes — past the intro, into a fight. Watch the FPS
   number: note roughly where it sits in quiet scenes and where it
   drops. Listen for the intro jingle and the menu music.
5. Afterwards, Share boot log from the launcher. This log is the
   evidence pack for everything above: the "settings: owner chose"
   line, the "overlay layout" bounds line, the "[thread-policy]
   android:" lines, the "[audio]" lines (device ready? callback
   alive?), the "[cd-cache]" stats, and the "[frame-stats]" lines
   every two minutes.
