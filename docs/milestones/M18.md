# God Hand Android — Milestone 18 (0.19-m18): the 0.18 verdict — AOT proven, two new convictions, three fixes

0.18-m17 shipped the five captured VU programs compiled into the package, and the owner's run (2026-11-03 ~01:01 WITA) came back: *boots and enters directly, but still lags hard* — a combat screenshot reading 1 FPS with a 1063 ms worst frame, and a new complaint with its own section below: his phone frame-drops **even outside the game** while/after it runs. This milestone is the forensic pass over that session (full log + capture folder returned; the session is the last of three appended in the log), a three-way comparison against the 0.15 and 0.17 sessions, and a fix build for what the evidence convicts. Counts and behaviour only, as always — no image hashes, no game bytes.

The short version: **the AOT fix worked** (section 1) — and it was not the whole wall. Underneath it, the guest still spends ~72 ms per field (section 2), the *displayed* 1 FPS in the heavy windows is a separate present-path collapse (section 2.3), and the outside-the-game stutter has a concrete mechanism in the shell's thread lifecycle (section 3). 0.19 fixes the present path and the lifecycle, and makes AOT dispatch provable on device from now on (section 4). It does not reach 60 fields/s, and section 5 says so plainly.

## 1. Q1 — did the compiled programs actually execute on the device? Yes. Proven two independent ways.

**The log alone could not prove it — that suspicion was correct.** The [ee-prof] printer has always printed the interp/comp split only for VU0; the VU1 segment carried runs and cycles but no comp count, even though the counter exists in the snapshot. And the absence of `[vu1-aot]` miss lines proved nothing either way: `findCompiledVu1Image` (the only place a miss is reported) is reached only through `lookupCompiledVu1Program`, which returns early — silently — when the registry is empty. An empty registry and a populated registry with all hits produce the identical log: no lines at all. So the 0.18 session log, read strictly, was consistent with both "AOT ran" and "AOT never ran". The instrumentation gap is closed in this build (section 4.1).

**Source trace: the EE-callback path does consult the registry — there is no bypass.** Every VU1 execution entry point in the runtime was enumerated:

- The MSCAL callback fires `VU1Interpreter::execute()`; the MSCNT callback and the budget-continuation helper fire `resume()`. Both funnel into `run()`.
- `run()` (VU1 branch) reaches `runLoop(..., allowCompiled = true)` on every path — directly, or via the frame-stats branch (that branch is env-gated, the env is unset in the app, and even it passes `allowCompiled = true`).
- `runLoop` resolves the compiled program via `lookupCompiledVu1Program` (registry, per-(memory, code, generation) cached, memcmp-verified recent-image cache underneath) and hands it to `runLoopWith`, which enters it before interpreting anything.
- The only other `runLoopWith` callers are the verify-mode pair (interpreter + shadow), gated by an env the app never sets.

So if the registry was populated, the callbacks used it. Registration itself is called from the port's main (after the HLE bindings install, under the same define the census verified), and the glue calls that same main — the chain has no Android-specific detour.

**Performance arithmetic: the speedup is exactly the AOT signature, and nothing else changed.** 0.18 differs from 0.17 only by the generated programs, the registration call and version strings. Per-VU-cycle run cost, in-game windows:

| build | VU1 ns per cycle | VU1 µs per run | guest fields/s |
|---|---|---|---|
| 0.17 (all interpreted) | 232–875 | 400–1800 | 1.0–4.2 |
| 0.18 (5 programs compiled) | 10–35 | 17–57 | 10.3–32.2 |

Per-run cycle counts are the same in both (~1,500–2,100 cycles — the same programs, started the same way), while the cost per cycle fell 15–50×. An empty registry cannot produce that. Two more details in the 0.18 log agree: essentially all VU1 time sits at three entry points, all three inside the compiled set's recorded entry list; and VU0 never appears at all (calls 0 in every window — this game drives everything through VU1 on this route, so the VU0 side of the machinery stays untested by it, as before). One 0.17 curiosity the comparison also explains: its per-cycle cost *degrades* across the session (232 → 875 ns/cycle) while 0.18's stays flat (10–35) — consistent with the SoC thermally throttling under the interpreter's sustained full-core burn, and the compiled code not heating it the same way. Consistent with, not proven by, the logs.

**Where VU1 still stands after the fix:** in the steady in-game windows the compiled VU1 costs 1.6–2.5 s per 5 s window over 59k–92k runs (vu1ee, the callback view, runs ~0.16–0.25 s higher: ~2.6 µs of per-callback machinery each — start/reset, the budget check, the callback timer). Per run that is ~25 µs for ~1,600 cycles. The remaining cost is the compiled code's own scheduled work plus its generic-op fallbacks (each generic instruction round-trips the full flag state), not dispatch overhead: the per-call fixed costs in the compiled entry (write materialisation, flag load/store, one dispatch-table walk) are small next to 25 µs, and the fallback counter added in this build (section 4.1) will show whether run/interpreter alternation adds anything on top.

## 2. Q2 — the three sessions, window by window

Windows are the port's ~5 s [ee-work]/[ee-prof] windows. Menu = title screens; transition = loading/streaming between areas; in-game = village + combat. The 0.15 build predates [ee-prof], so its cost split is [ee-work]-only; 0.16's profile of the same behaviour is M15's subject and is not repeated here.

### 2.1 Menu / title

| | 0.15 | 0.17 | 0.18 |
|---|---|---|---|
| fields/s | 57–60 | 54–60 | 58–60 |
| effective EE | 278–295 MHz | 264–295 MHz | 287–295 MHz |
| shape | — | native ~1.0–2.1 s, parked 0.3–1.9 s | native ~1.4–2.1 s, parked 0.7–1.8 s |

The menu was never the problem and did not change: full rate in all three, guest cycles concentrated in one menu-loop function.

### 2.2 In game

| per 5 s window | 0.15 | 0.17 | 0.18 |
|---|---|---|---|
| fields/s | 1.2–2.9 | 1.0–4.2 (degrading) | 10.3–19.1 steady (25–32 in transition) |
| effective EE | 6–14 MHz | 5–21 MHz | 51–94 MHz |
| guest share | 100%, idle 0% | 100%, idle 0% | 100%, idle 0% |
| cycles/field | ~4.92M | ~4.92M | ~4.92M |
| native (residual EE) | n/a (pre-profile) | ~0–0.5 s | **2.2–3.2 s** |
| VU1 runs / window | n/a | 2.3k–12k | 59k–92k |
| VU1 cost | (interp, in guest) | 3.9–5.2 s | **1.6–2.5 s compiled** |
| parked | ~0 (M14) | 0.1–1.0 s | 0–0.15 s steady |
| readData drains | combat-only, ~100–125 ms each | ~90–125 ms each | clustered in transition/first-fight windows (see 2.3) |

The field now costs ~52–98 ms of guest time instead of ~350–830 ms: native ~45 ms + VU1 ~26 ms + parked ~2 ms in a representative steady window. **Native is now the largest bucket.** It has no hot spot: the cycle sampler spreads it across the whole game (no function above ~1%), and the branch view's biggest entry is a trampoline-shaped target with millions of calls and ~20 ms of sampled time — frequency, not cost. At ~5–7 ns per EE cycle (vs ~1.3 at the menu, where one tight loop dominates) this is the recompiled game's real working set — physics, animation, AI, display-list building — running through a phone core's instruction cache. The profile offers no surgical target inside it; section 5 names what that means honestly.

Combat specifically (the owner's screenshot is from the first fight): the heaviest steady windows are the combat ones — the last window of the session is the worst (10.3 fields/s; VU1 2.5 s at 35 ns/cycle, its most expensive per-cycle reading, on fewer, longer runs: ~1,620 cycles each). The synchronous readData drains did **not** return in the steady combat windows; where they appear is the transition and first-fight windows (one 1.94 s single drain during streaming; 37 drains ≈ 87 ms each; 14 drains ≈ 121 ms each — all of it in the map/read stage, as always). They are the guest reading back freshly rendered pixels and waiting on GPU completion — which connects them to section 2.3's conviction, not to the VU or EE buckets: their cost is GPU backlog, paid on the EE thread.

### 2.3 The displayed 1 FPS is the present path, not the guest

The cleanest before/after in the whole comparison:

| [frame-split], in game | 0.17 | 0.18 heavy windows |
|---|---|---|
| presents per window | 91–113 | **5–6** |
| present interval | 44–55 ms | **887–1198 ms** |
| of which "sync" (waiting for a guest field) | 83–96% | ~0% |
| of which "swap" | 1–9 ms | **865–1200 ms (97–98%)** |
| GS worker busy | 14–21% (starved) | 63–73% |
| GS ring-fence waits | — | 15–19 per window, **2.8–3.9 s total (~200 ms each)** |
| queued-chunk wait (worker-side) | ~0 | avg 51–104 ms |

In 0.17 the presenter waited on the guest; in 0.18 the guest waits on nobody (fields advance 10–19/s) but the screen updates ~once a second in the heavy windows, because the swap blocks behind a saturated GPU command stream. The mechanism, from source: this backend is a compute-shader rasterizer over storage buffers (the hardware raster path is compiled out on Android by design), it flushes thousands of batches per window, and after **every** batch section it issues `glMemoryBarrier(GL_ALL_BARRIER_BITS)` — the widest barrier GL has. On a tile-based mobile GPU that barrier drains the entire pipeline; the upload ring's fences (placed a full 16 MB chunk earlier) still complete ~200 ms late, 15–19 times per window; texture uploads add 0.4–1.4 s of worker time in the same windows; and the window's own swap — one textured quad — queues behind all of it. The owner's screenshot (1 FPS, worst frame 1063 ms) is this, measured from the other side: the FPS label counts presents.

Also settled here, since it was asked: the [ee-work] queueWait figure (avg 51–104 ms) is **not** EE time. It is worker-side queue latency — how long a submitted chunk sat before the GS worker picked it up (menu: 1.5 ms). It is a symptom of the same backlog, charged to no guest bucket, and it inflates nothing in [ee-prof].

## 3. Q3 — the phone stutters outside the game: mechanism found in source, fixed

The audit traced every thread the process runs and what stops it:

- **Frontend (present) thread**: raylib's Android poll blocks indefinitely while the activity is not enabled — this one thread did park when the app was backgrounded. ✓
- **GS worker, async GIF/VIF workers, IOP worker**: all wait on condition variables and idle correctly *when unfed*. ✓ (one async stage polls on a 2 ms timed wait — a negligible 500 wakes/s, noted for completeness, not the cause).
- **EE game thread**: **nothing parked it.** Pausing the activity touched only the frontend; the EE scheduler kept executing the guest at full pace — EE, GS raster, IOP and audio all running in a process nobody was looking at, for as long as the process lived. On a phone that is not a subtle leak: sustained multi-core emulation load heats the SoC until the *whole system* throttles — launcher, other apps, and the game itself when he comes back to it. That is precisely "frame-drops even outside the game, while/after running it".
- **Destroy was no exit either**: the frontend loop's only close check sits inside its window-minimized branch, which Android never takes; the shell's activity asked nothing of the native side on destroy; so the frontend, the game thread and the workers all outlived the game screen inside the still-running app process, until Android reaped the process on its own schedule.

The fix (section 4.2) wires the activity lifecycle into the emulation for the first time.

## 4. What 0.19-m18 changes

### 4.1 AOT dispatch, provable on device (instrumentation only)

- The [ee-prof] VU1 segment now prints the same split VU0 always had: `interp I comp C budget B fb F` per window (the counters existed in the snapshot for both units; the printer only used unit 0's). `fb` is new: compiled invocations that returned Fallback — run/interpreter alternation is now measured instead of guessed at.
- One boot line after registration: `[vu1-aot] N compiled VU program(s) registered`. In the owner's next log this must read 5, and every in-game window must read `comp == runs` (modulo any genuinely new image, which would also print its one `[vu1-aot]` miss line). Together they close Q1 on device, permanently.

### 4.2 Lifecycle: a backgrounded game stops burning the phone (Android only)

- New seam `ps2_android_host` (header + state beside the touch state): two atomics, suspended and stop-requested, written by the shell through two new JNI exports, forwarded from `GameActivity.onPause` (suspend), `onResume` (clear) and `onDestroy` (stop). Each transition also writes one boot-log line (`native: app suspended ...` / `app resumed ...` / `app stop requested ...`), so the next log shows the wiring working.
- The EE scheduler's main loop parks while suspended (25 ms sleeps, stop-aware). Guest time is cycle-driven and the host-pacing anchor already gives up beyond an 8-field lag, so resuming costs no catch-up burst; the GS/GIF/IOP workers simply starve into their condition-variable waits.
- The frontend loop honours stop-requested: it calls the runtime's existing requestStop (which also stops the scheduler), joins the game thread as it already does on every exit, and returns — so the port's main reaches its normal exit and the process can actually end with the activity.
- Desktop and every other platform compile none of this (all of it is behind `#if defined(__ANDROID__)` or in Android-only files).

### 4.3 The present path: the barrier is narrowed to what the backend actually needs (Android only)

`barrier()` in the GPU backend now issues, on Android only, `SHADER_STORAGE | SHADER_IMAGE_ACCESS | BUFFER_UPDATE` barrier bits instead of `GL_ALL_BARRIER_BITS`. Justification from the backend's own structure: every GPU-to-GPU dependency inside it flows through storage buffers or shader images (VRAM, prim/state/tile data; the upload ring is persistent+coherent mapped, and reuse of a ring chunk is fenced separately before overwriting). Nothing in the Android path draws into a framebuffer (the hardware rasterizer is off) or samples a texture another pass rendered. The desktop build keeps `GL_ALL_BARRIER_BITS` byte-for-byte. If the narrowed set were missing a real dependency, the symptom would be visual corruption in specific effects — exactly what the owner's screenshots show every run — and the CPU renderer remains one settings toggle away as the comparison. Expected witnesses in the next log's heavy windows: ring-fence totals per window down from seconds toward the menu's ~5 ms each, swap's share of the present interval collapsing, presents per window climbing back toward the field count.

Untouched in this build: the interpreter and the compiled programs (the same five, same generated sources), the matching/verification design, the CPU GS backend, all shaders (no retranslation — nothing shader-adjacent changed), the Windows branch, capture (still armed), and all other instrumentation.

## 5. Honest limits

- **This is not a 60 fields/s build, and it does not claim to be.** The guest-side arithmetic is unchanged by 4.2/4.3 and only better-instrumented by 4.1: at ~45 ms native + ~26 ms compiled-VU1 per field, fields advance ~10–19/s in game regardless of how fast the screen can present them. What 0.19 should change is (a) the *displayed* rate in the heavy windows — from ~1/s toward the field rate, if the barrier conviction is right — and (b) the phone's behaviour outside the game. The owner's verdict metric stays feel + the FPS label + the log.
- Native EE cost is the largest remaining bucket and this profile gives it no address: it is spread across the whole game at ~1% per function. Levers not in this build: the owner's thread-policy setting (his sessions run it off; the policy exists to move the heavy threads onto the performance cores — a zero-cost A/B for a later run, deliberately not folded into this one's comparison), and anything that reduces the game's own per-field work, which is the game's, not the port's.
- Compiled VU1 at ~15 ns/cycle is ~4–5× off what the same silicon does on simple native loops; the generic-op flag round-trips inside the compiled blocks are the named suspect, and the new `fb` counter plus the per-entry table will say whether alternation adds to it. Optimising the generated blocks is a vu1_recomp milestone of its own, not a runtime patch.
- VU0 remains unexercised by this route (0 calls in every window of both AOT sessions); if a later area uses it, its images capture and compile the same way, and its [ee-prof] split already prints.
- Coverage is unchanged: the same five images. New areas still run interpreted until a session captures them, and capture stays armed.

## 6. Verification

- **Android build**: full rebuild, 12,748 steps, zero failed steps; a follow-up run reports no work to do. Host tree rebuilt for the stub proof: 147 steps, zero failures.
- **Register-count stub (host, never shipped)**: the M17 stub extended with the same count accessor the new boot line uses. Output: count 0 before registration, count 5 after `registerGeneratedVu1Programs()`; all five captured images resolve through the real registry lookup; an unknown image correctly resolves to nothing; exit code 0. The number the owner's next boot log prints as `[vu1-aot] 5 compiled VU program(s) registered` is therefore proven against the real registry here first.
- **Package**: versionCode 19, versionName 0.19-m18, same package name as always. Signature verifies under both v2 and v3 schemes with the same signer certificate as every previous build, so it installs as an in-place upgrade. APK size 98,501,132 bytes (0.18 was 98,497,036 — the delta is the new code only). The 0.18 package is preserved alongside as a backup.
- **Packaged-library census**: the library inside the APK is byte-identical to the build tree's (SHA-256 `b347f0d7…` both sides). Its symbol table holds the registration entry point exactly once and exactly five compiled-program entry points — emitted == registered == packaged, as in M17. The new format strings are present in the packaged library: the `[vu1-aot]` registration line, the VU1 `interp / comp / budget / fb` segment of the `[ee-prof]` format, and the suspend / stop lifecycle lines. The capture-arming string is present exactly as in 0.18 (count 1 in both) — capture stays armed, untouched.
