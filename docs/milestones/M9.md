## 1. The frame-split witness: [frame-split]

M8's plan — reuse the audit's `PS2X_GS_WAIT_STATS` — failed on
device for a reason §2 autopsies. The replacement puts the clocks
in the path that demonstrably presents on this device: the
`PS2Runtime::run()` present loop in
`runtime/ps2xRuntime/src/lib/ps2_runtime.cpp`. Four phases of one
loop iteration are timed, and whatever an iteration spends outside
them lands in a printed residual:

- **sync** — the present-sync wait at the top of the iteration:
  with present sync enabled, the loop sleeps (250 µs polls, 50 ms
  cap) until the EE scheduler's vsync tick advances past the last
  presented field. This is where the loop waits *for the guest*.
- **gs-fetch** — from just before the PCSX2/native branch to just
  after the shared-frame resolution: in the native path this is
  `UploadFrame()` — the GS latch (below), the framebuffer copy out
  of the GS, and the raylib texture upload.
- **draw** — `BeginDrawing()` to just after `fpsOverlay.draw()`:
  the fullscreen texture blit, the debug-UI callback, the
  save-state message, the controls screen, the FPS overlay itself.
- **swap** — `EndDrawing()` alone: raylib's buffer swap, i.e. the
  present / compositor wait. Zero on iterations that do not present
  (PCSX2-GS iterations with no host UI).
- **rest** — the printed residual: avg frame minus the four
  buckets (clamped at 0). Input sampling, controls tick, menu /
  save-state requests, the frameTimes tracing when enabled, and
  the tail of the previous iteration all live here.

The interval between consecutive iterations is measured
stamp-to-stamp at the accumulation point, in the same place every
iteration; an interval over 5 s is treated as a pause (load, focus
loss) and skipped — the same sanity idea as
`notePresentInterval`, tighter. Buckets fold into a window that
closes when the **accumulated frame time** reaches 5 s (not wall
time, so a 1 FPS scene yields a line every ~5 presents and pauses
do not dilute it), printing:

```
[frame-split] presents=5 avg 1003.2 ms fields +5 | sync 812.40 ms (81%) gs-fetch 121.05 ms (12%) draw 3.10 ms (0%) swap 9.85 ms (1%) rest 56.80 ms (6%)
```

`fields` is the guest vsync ticks advanced across the window
(`eeScheduler().currentVSyncTick()` delta) — the EE-side witness
that needs no timer on the game thread: at the title, one field
per present is the healthy shape; fields crawling while the
buckets sit small is the signature of the guest itself.

### Call-path proof (why this witness cannot watch an empty room)

The Java FPS label on the owner's screen — the "1 FPS - worst
frame 1328 ms" he screenshotted on 0.8 — ticks through exactly
this chain:

1. `PS2Runtime::run()` present loop → `fpsOverlay.present(field)`
   (ps2_runtime.cpp:3331).
2. `FpsOverlay::present()` → `ps2_host_display::notePresentInterval(...)`
   first, before its own `lastPresent` moves — the interval
   statistics live in `ps2_host_display` (ps2_runtime.cpp:151).
3. `ps2_host_display::fpsText()` renders
   `"%.0f FPS - worst frame %.0f ms"` from that window.
4. Glue JNI `Java_dev_ptraaa_godhand_TouchPad_nativeFpsText`
   (godhand_android_main.cpp:267) returns `fpsText()`.
5. `TouchPad.nativeFpsText()` (TouchOverlay/TouchPad.java:291) →
   `GameActivity` polls it (GameActivity.java:76) →
   `overlay.setFpsText(...)` → the on-screen label.

The `[frame-split]` accumulation block sits **immediately after
that same `fpsOverlay.present(...)` call** (ps2_runtime.cpp:3331,
block from :3333), fed by the phase timers of the same iteration.
Any run in which the label ticks — every device run so far — is a
run in which the block executes; there is no flag and no second
path. The fetch bucket's inner leg, for the record:
`UploadFrame()` (ps2_runtime.cpp:781) →
`rt->gs().latchHostPresentationFrame()` (gs_frontend.cpp:758) →
backend `Flush()` (a no-op in the threaded backend) /
`Sync(Presentation)` / `Present(request)`, then
`copyLatchedHostPresentationFrame()` + `UpdateTexture()` back in
`UploadFrame`.

## 2. Autopsy: why [gs-wait] never printed

Two layers, both in `runtime/ps2xRuntime/src/lib/gs/gs_threaded_backend.cpp`:

- **Reachability.** The printer `gsWaitStatsMaybePrint()` is
  called from exactly two places: the tail of
  `GSThreadedBackend::PublishLocked()` (:298) and the stats branch
  of `GSThreadedBackend::Drain()` (:325). No other caller exists.
  The plumbing *would* have reached it — the latch leg above runs
  `Sync`/`Present`, which in the non-shared path go through
  `RunOnWorker()` → `Drain()`, and `VSync()` publishes per field —
  but every one of those calls, and all the counters themselves,
  is gated on the flag below.
- **The flag latched before the glue could set it.**
  `g_gsWaitStats` (:237) is a namespace-scope `const bool`
  initialised by a getenv lambda — dynamic initialisation at
  **library load**. On Android the library is loaded by
  `System.loadLibrary("godhand")` in `GameActivity.onCreate`,
  before the NativeActivity thread runs the glue's `android_main`,
  which is where M8 put the `setenv`. The flag therefore latched
  `false` on every app start, permanently. On a desktop shell the
  variable is set before exec, so the same code "worked" there.
  Contrast the IOP witness, which printed on every run:
  `PS2X_IOP_THREAD_STATS` is read by a **function-local** static
  (iop_subsystem.cpp:463) that initialises on first execution —
  when the IOP worker starts, after the glue's setenv.

Disposition: the glue no longer sets `PS2X_GS_WAIT_STATS` and no
longer prints the banner; a retirement note at the old site
(godhand_android_main.cpp, where the M8 block stood) records why.
The backend's own code is untouched — the flag still works for
desktop runs that set it before exec. Verified in the packaged
library: the retired marker string is absent (0 occurrences).

## 3. The refill witness, upgraded: all reads, real distribution

M8's `noteSlowRefillRead` counted only reads ≥ 50 ms, so 0.9's
zero `[stall]` lines could not distinguish a fast refill path
from a witness staring at the tail. In
`runtime/ps2xIOP/src/emulator/imports/iop_cdvd.cpp` it is now
`noteRefillRead` (:698), called from both `readSectors` exits
exactly as before, and it counts **every** refill read — count,
total ms, worst ms, over-50 ms count (members renamed:
`refillWindowCount`, `refillWindowSlowCount`, `refillWindowTotalMs`,
`refillWindowWorstMs`, `refillWindowStart`, `refillLogsLeft`). The
per-read `[stall] iop-cd refill read:` lines are unchanged (≥ 50 ms,
budget 16). The 10 s summary now prints whenever a window closes
with count > 0, in the new format:

```
[stall] iop-cd refill summary: 212 reads in 10 s, avg 1.8 ms, worst 46 ms, total 382 ms on disc reads, 0 over 50 ms
```

A quiet path now proves itself quiet with numbers (low avg, low
total); a path made of a thousand small waits shows its total
instead of hiding under the threshold.

## 4. The consumption end: [stall] adma starve summary

The per-event `[stall] adma stream starved` line (M8) has a
budget of 16 and then goes silent; nothing counted what happened
after. Inside the existing late-block handler in
`IopSpu2::admaSample()` (`runtime/ps2xIOP/src/emulator/devices/iop_spu2.cpp`,
handler at :447), every late event now also folds into
combined-core window counters keyed to **stream time** (the same
`t = m_cycle / (768 × 48000)` the `[spu2-adma]` lines print):
late blocks (≥ 48 samples / 1 ms), starved blocks (≥ 2400 samples
/ 50 ms), and the longest starve. A late event landing 10 s or
more of stream time after the window opened closes it — the
closing event is counted first, as in §3 — with:

```
[stall] adma starve summary: 141 late blocks (>=1 ms), 3 starved (>=50 ms), longest starve 132.5 ms in 10 s of stream time
```

The M8 per-event lines and the `[spu2-adma]` 1 ms log keep their
own budgets, untouched; `[spu2-silence]` and the
`[spu2-adma] ... silent blocks` duration line remain the other
audio witnesses.

## 5. Reading the title minute — the verdict table

Run the owner steps below; the log's title span will carry
`[frame-split]` lines plus (if the stream misbehaves) the two
`[stall]` summaries. Read them together:

- **gs-fetch dominant** (the clear majority of avg frame, window
  after window): the frame's time is spent in the latch —
  backend Flush/Sync/Present plus framebuffer copy and texture
  upload. The raster/fetch path is convicted; the next lever is
  the GS path itself (the GPU backend milestone), not more disc
  or IOP work.
- **swap dominant**: frames are built cheaply and the loop waits
  in `EndDrawing()` — the present / compositor leg (vsync
  configuration, surface pacing) is the wall. Next lever is the
  present configuration, not the renderer.
- **draw dominant**: the raylib draw leg itself (blit, overlay,
  debug UI) — narrow and cheap to chase, and not expected.
- **sync dominant, or all four buckets small while avg frame
  stays huge and fields crawl**: the present loop spends its life
  *waiting for the next guest field* or outside its timed phases
  entirely — the guest is not producing fields. With the IOP,
  the disc (both routes, now with distributions), audio
  back-pressure and the GS legs all measured, that leaves the
  last suspect standing: **raw EE execution speed** — the
  recompiled guest code's own throughput. That outcome hands off
  to EE-side profiling (guest cycles per field vs host ms per
  field); the `[frame-stats]` lines are its baseline.
- **Music stream, either summary hot at the title**: refill
  totals (or a fat worst/avg in the refill summary) in the same
  span as starved blocks convict the refill's disc leg — the
  next lever is the IOP refill path's own streaming cache, a
  place no milestone has touched. Starved blocks with a cold
  refill summary put the stall between the read and the SPU2
  (ADX thread scheduling / decode), same family, narrower door.
  Both summaries cold for a full title minute clears the stream:
  0.8's 9.6 s of silence was a load-phase event.
