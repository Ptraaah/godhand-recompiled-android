# Milestone 7 — the prefetch suspect, closed properly (0.8-m7)

The read-only audit (AUDIT-M6.md, suspect 7) found a second whole-session
cost the M6 cache fix does not touch: in `src/main.cpp` (~line 615), a
detached thread sequentially reads the entire 1.5 GB ISO "into the OS
file cache" — gated on `!headless`, default ON, and the Windows branch
drops the thread to the lowest priority while the Linux/Android path
sets no priority at all. On the owner's slow, nearly-full flash, that
thread would saturate the storage for the whole session, and the audit
ranked it prime suspect for the 0.6 regression because its active
window (windowed builds only) matched the headless→windowed timeline.

## The finding that reframes it: inside the app, it never ran

The port's gate is a plain getenv:

```cpp
// src/main.cpp:615
if (!headless && envFlag("GODHAND_ISO_PREFETCH", true))
```

(`envFlag`, main.cpp:106, reads `std::getenv` and treats "0" as false.)

But the Android glue has pre-set that variable since the very first
build. M2A.md documents the glue's two env defaults verbatim:
`PS2X_GS_GPU=0` (CPU rasteriser) and `GODHAND_ISO_PREFETCH=0`
("headless skips prefetch anyway; belt and braces"), installed with
`setenv(..., 0)` — a no-overwrite default — next to each other in
`main()` before `godhand_port_main` is called. Nothing in the Android
app process sets `GODHAND_ISO_PREFETCH` before that point, so the
default always landed, in every shipped build from 0.1-m2a through
0.7-m6, headless and windowed alike. The prefetch thread has never
been spawned inside the app; the audit read the port's default but
not the glue's preset, and its timeline argument does not survive
the preset, which was identical in both eras. (Support, not proof,
from the device side: no "disc image prefetched into the OS file
cache" completion line appears in any device boot log quoted in this
project — those logs are partial pastes, but the code path is
deterministic: getenv "0" → gate false → no thread.)

So prefetch is dead as the cause of the 0.6 regression — not fixed
by this build, never alive in the app. What this build does is make
that state explicit, owner-controlled and logged, so the question
stays closed, and it turns on the audit's next evidence target.

## What changed

**1. Disc prefetch is an owner setting now (default OFF).**
- Launcher settings gain a row, "Disc prefetch (experimental)",
  stored as `set_prefetch` (boolean, default false), same
  tap-to-toggle pattern as the other settings; it applies at the
  next game start.
- The chain is the existing one: GameActivity copies the preference
  into `IsoHolder.optDiscPrefetch` ("on"/"off") before the library
  loads; the glue reads `IsoHolder.discPrefetch()` through the JNI
  bridge and sets the port's actual gate —
  `setenv("GODHAND_ISO_PREFETCH", "1"/"0", 1)` — with overwrite.
  The silent no-overwrite default line is gone. Anything but an
  explicit "on" (including a failed bridge lookup) resolves to off.
- Every boot log now states it, before the port starts:
  `settings: owner chose ... prefetch=off` and the dedicated line
  `disc prefetch: off (owner setting)` (or `on`). If it is ever
  switched on, the port's own completion line ("disc image
  prefetched into the OS file cache: 1496 MB in X ms") appears when
  the thread finishes — X on his flash is itself a storage-speed
  measurement.
- Honest warning: ON is expected to *hurt* on this phone — that is
  the audit's concern, a full-speed sequential 1.5 GB read competing
  with the game on slow storage. The toggle exists so the question
  is testable, not because on is recommended.

**2. IOP thread statistics are on for this build (evidence only).**
The audit's suspect 3 is IOP serialisation: the EE leads the
interpreted IOP by at most ~14.2 ms of EE time and joins on every
RPC, so a slow IOP caps the whole machine. `PS2X_IOP_THREAD_STATS`
**exists** in this codebase (`runtime/ps2xIOP/src/iop_subsystem.cpp`,
read once via getenv when the IOP worker starts), so the glue sets
it to "1" and the runtime prints, every ~5 s of IOP activity, into
stderr — which is the boot log:

```
[iop-thread] N batches/s, worker busy X% (Y us/batch), EE join wait Z%, worker wakes W/s, EE join sleeps S/s
```

A glue line ("native: IOP thread stats on ...") marks where they
start. How to read them, per the audit: worker busy ≈100% with a
high EE join wait **convicts** suspect 3 (the interpreted IOP is the
ceiling; the next lever would be an IOP threading experiment);
low busy and low join wait **clears** it and points back at the GS
path (then `PS2X_GS_WAIT_STATS`, AUDIT-M6 suspect 1). No IOP
behaviour changes: `PS2X_IOP_THREAD` is untouched, the worker model
is exactly 0.7's.

**3. Nothing else.** 0.7's async CD cache, the overlay and its EDIT
mode, remapping, all other settings, the FPS counter, frame-stats
and the audio instrumentation are byte-for-byte the 0.7 behaviour.
One audit note that matters for reading this test: `PS2X_GS_SCALE`
is a no-op on the CPU backend (the game always renders at native GS
resolution), so the scale setting cannot affect the outcome either
way.

## Owner steps

1. **Skip 0.7-m6 entirely** — install this 0.8-m7 over whatever is on
   the phone (same signer, update in place, ISO copy reused, no
   copy wait). It contains everything 0.7 had plus this milestone.
2. Leave the settings as they land: the new "Disc prefetch
   (experimental)" row OFF, thread placement OFF. The resolution
   setting cannot affect this test (see above) — leave it wherever
   it is.
3. Tap START. At the title screen, read the FPS counter; press
   START and play for a few minutes — the intro movie and the first
   area are the streaming traffic that used to freeze.
4. When done, reopen the app and use Share boot log.

Success = a session free of both disc hazards — no guest-thread CD
stall (0.7's cache) and the prefetch question closed by the log's
own `disc prefetch: off (owner setting)` line — with the
`[frame-stats]` and `[iop-thread]` lines saying what remains: if
the FPS is healthy, the performance front is done; if it still
crawls with the IOP worker pegged near 100% busy, suspect 3 is
convicted and the next build is the IOP experiment.
