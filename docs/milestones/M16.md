# God Hand Android — Milestone 16 (0.17-m16): the VU fix, step 1 — capture wired, pipeline proven

M15's source audit found the structural hole: this package contains no AOT-compiled VU programs at all (`generated/vu1/` did not exist), so VU0 and VU1 run 100% in the cycle-accurate interpreter while the recompiled EE does its work natively — the standing explanation for the in-game field costing 0.4–0.7 s of guest time at ~100% dispatch while the GS worker idles. The owner ordered the fix directly, skipping the 0.16 profile-run gate. This milestone is the fix's first half, and it is honest about which half it is: **the capture is wired into the shipped build and the whole downstream pipeline (capture format → vu1_recomp → generated sources → build glob → registration → registry) is built and proven on the host with a fabricated fixture. The compiled programs themselves cannot exist until one device session records the game's real VU images** — for the reason in section 2, no machine available to this project can produce them except the owner's phone running the game. 0.17 is therefore a capture build, but unlike the M13–M15 measurement builds it is on the fix path and is the last prerequisite: the follow-up build (0.18) only has to run the tool over the returned folder and rebuild.

## 1. The VU machinery, mapped from source

All of it lives in `runtime/ps2xRuntime/src/lib/vu/ps2_vu1_core.cpp` (+ `ps2_vu1_impl.inl`, `include/runtime/ps2_vu1.h`). One interpreter class serves both units.

**Execution.** `VU1Interpreter::run()`/`resume()` funnel into `runLoopWith` (the M15 recorder's home). Runs are cycle-budgeted: VIF1 callbacks execute VU1 in 65,536-cycle slices and `finishVu1Program` continues up to a 1,048,576-cycle cap; VU1 cycles are charged back into EE cycle accounting. Decoded-pair flags (I/E/M/D/T) come from the upper word (E bit = `upper & 0x40000000`, ps2_vu1_core.cpp:1233). XGKick output flows through the same interpreter state and packet sink whether a stretch runs interpreted or compiled.

**How microprograms arrive.** VU1 code is uploaded by the game into VU1 micro memory through VIF1 MPG packets; PS2Memory carries a VU1 code *generation* counter bumped whenever code memory changes, and programs start/resume only from the two VIF1 FIFO callbacks (MSCAL/MSCNT), on the EE thread or the VU worker. VU0 programs are EE-driven: generated EE code calls `executeVU0Microprogram` (VCALLMS) synchronously inside guest time. This port backs VU0's 4 KB code/data memories with 16 KB (zero above 4 KB) and runs VU0 microprograms with the 16 KB sizes, so a VU0 image has exactly the VU1 image shape and is captured, recompiled and registered identically; a VU0 code generation counter exists likewise.

**Compiled lookup and dispatch (already in the runtime; only the programs were missing).**
- Registry: `vu1CompiledRegistry().programs`, a map from FNV-1a-64 hash of the full 16 KB code image to a `CompiledProgram` function pointer. Populated by `registerVu1CompiledProgram(hash, fn)`, called from `registerGeneratedVu1Programs()` (a file vu1_recomp emits) by `src/main.cpp` under `#if GODHAND_HAS_VU1_PROGRAMS`, right after the HLE bindings install.
- VU1: the wrapper caches the lookup per (memory, code pointer, generation); on a generation change `findCompiledVu1Image` re-resolves — a memcmp-verified 8-entry recent-image cache, then the hash map. A miss returns nullptr → the interpreter runs the image, and `reportUncompiledVu1Image` logs `[vu1-aot] image <hash> has no compiled code` once per image and dumps the image to PS2X_VU1_MISS_DIR. A hit substitutes the compiled `runImage<hash>` inside the same `runLoopWith` budget machinery: the compiled code returns the same `StepResult` (cycles consumed + stop reason) the interpreter loop produces, so slicing, budgets and cycle charging are unchanged. PS2X_VU1_RECOMP=0 disables dispatch; PS2X_VU1_VERIFY runs every program both ways and reports divergence (=obs compares only observable state).
- VU0: `lookupCompiledVu0Program`, a thread-local cache keyed by (memory, code, VU0 generation). vu1_recomp emits VU0-sized images twice — fast FMACs under the plain hash, exact FMACs under `hash ^ 0x5655304558414354` ("VU0EXACT"); PS2X_VU0_FAST=0 selects the exact one, PS2X_VU0_RECOMP=0 disables, PS2X_VU0_VERIFY=1 verifies per call.

**Capture (already in the runtime; only the directories were missing).** `VU1Interpreter::run()` calls the capture hook on every run, for both units; the hooks act only when the image's generation changed:
- PS2X_VU1_CAPTURE=<dir>: writes `vu1_<hash>.bin` (the 16 KB image) per new VU1 image, appends `<hash> <entry pc>` lines to `entries.txt` the first time each (image block, entry) is called, and maintains `calls.txt`.
- PS2X_VU0_CAPTURE=<dir>: writes `vu1_<hash>.bin` per new VU0 image.
- Both file sets are exactly what vu1_recomp consumes (16 KB, named by content hash).

**vu1_recomp** (`runtime/ps2xTest/tools/vu1_recomp.cpp`, target behind `-DGODHAND_BUILD_TOOLS=ON`): `vu1_recomp <capture-dir> <out-dir> [max-pairs-per-block]`. It reads every `vu1_*.bin` (must be exactly 16,384 bytes), recompiles reachable segments with microVU-style analysis (block segmentation, dead MAC/status-flag elimination, latency scheduling), and emits `vu1_<hash>.cpp` (+ `_N.cpp` parts) and `vu1_programs.cpp` (the `runImage<hash>` declarations + `registerGeneratedVu1Programs()`). Defaults that matter for this game, from the tool's own comments: fast FMACs on (VU1_RECOMP_EXACT_FMAC=1 turns them off); loads stay *normalized* — raw loads are off by default because a documented God Hand case (character program 4dfe leaving integer bit patterns in vf31 that stage program cd8f multiplies) breaks geometry under raw loads; VU0-sized images are dual-emitted fast + exact. Build wiring (`src/CMakeLists.txt`): `generated/vu1/*.cpp` is globbed (CONFIGURE_DEPENDS) into a `godhand_vu1_code` static library, linked into the godhand target with `GODHAND_HAS_VU1_PROGRAMS=1` — the same CMake serves the desktop and Android builds, so programs generated once dispatch on both.

**Semantic safety of the dispatch design.** (1) A compiled program runs only for the exact image it was compiled from: identity is the full-image FNV-1a hash, the recent cache is memcmp-verified, and any code-memory write bumps the generation and forces re-resolution — a changed image falls back to the interpreter, never to a stale program. (2) The generated code is built from the same `ps2_vu1_impl.inl` instruction semantics the interpreter executes, and returns through the same StepResult/budget path, so cycle accounting, slicing and XGKick behaviour are the interpreter's own. (3) Anything not captured stays interpreted — coverage grows image by image, correctness never depends on it. (4) Kill switches and verify modes exist per unit (above) if a follow-up build ever needs them.

## 2. Route decision: host capture is impossible on this machine; the premise checked and corrected

The working assumption handed to this milestone was that a full disc image exists at `disc/God Hand (USA).iso` and the host build could capture from it. The file does not support that:

- `disc/God Hand (USA).iso` is 4,767,748 bytes, ISO 9660 volume id **`GODHAND SYNTH GEN`**, containing exactly four files: SYSTEM.CNF, SLUS_215.03 (3,607,008 bytes — the real boot ELF), GODHAND.FST, and a 1,083,809-byte `_DATA.AFS`. It is the generation milestone's synthetic boot disc, not a retail image.
- The port's disc contract (`src/godhand/game_disc.h`, `game_disc.cpp`) requires, among others, `MODULES/IRX.IMS` (314,304 bytes); a missing required file is a hard boot error — and indeed the M1C host smoke run with this very disc stopped at `[BOOT] ERROR MODULES/IRX.IMS (IRX module archive) not found on the disc; expected SLUS-21503` before any game code, let alone a VU program, could run.
- A filesystem-wide search (all of `/` for ISO/IMG/BIN files over 800 MB, and a full `~/workspace` ISO inventory) finds **no full disc image on this machine**. The owner's complete 1,567,686,656-byte ISO exists only inside the app on his phone.

So route (a) cannot capture anything — not even title-screen programs, since verification stops the boot. Route (b) it is: capture inside the shipped build, which turns out to need no runtime work at all (section 1: the hooks were already there). Everything downstream of capture that *can* be done host-side was done host-side in this milestone (section 4), so the returned folder converts to a fix build mechanically.

## 3. What 0.17-m16 changes

One functional change, in `android/glue/godhand_android_main.cpp`: after the existing settings block, the glue creates `vu-capture/` in the app's external files dir (next to the boot log; the literal fallback path if the JNI bridge failed) and sets, with overwrite, before `godhand_port_main` runs:

- `PS2X_VU1_CAPTURE=<external files>/vu-capture`
- `PS2X_VU0_CAPTURE=<external files>/vu-capture`
- `PS2X_VU1_MISS_DIR=<external files>/vu-capture` (the once-per-image uncompiled dumps land in the same folder, same filenames — belt and braces behind the capture hooks)

plus one boot-log line: `vu capture: <dir> (PS2X_VU1_CAPTURE / PS2X_VU0_CAPTURE / PS2X_VU1_MISS_DIR) - VU microprogram images land here as vu1_<hash>.bin for the AOT pipeline`. The capture singletons read these lazily at first VU run, after the glue's setenv — the same ordering the GPU toggle already relies on. Everything else is version strings (manifest 17 / 0.17-m16, glue banner + entry line, three Java log/title strings). No runtime source, no shader, no CPU-backend, no Windows-branch and no generated-code change; `generated/vu1/` remains absent, so the package contains no compiled VU programs (verified below) and `[ee-prof]` will still read `comp 0` — expected on a capture build; the new evidence is the `[vu1-aot]` lines, the `vu capture:` line and the folder's contents.

**Toggle-OFF argument.** The capture block is not gated on the GPU toggle (or any toggle): it runs identically in both modes, and it cannot feed back into execution — the hooks only hash on generation changes and write files for images not seen before; no rendering, scheduling or emulation decision reads them. With the GPU toggle OFF the app therefore runs 0.16's CPU backend exactly as before, plus inert file writes when the game uploads a new VU image. The one cost is a 16 KB file write per distinct image (a session sees images in the dozens at most) and a hash pass per code-generation change.

## 4. Host proof (the pipeline, end to end, minus real game images)

- **Tool built from this tree**: linux-m1a reconfigured with `-DGODHAND_BUILD_TOOLS=ON`; `ninja vu1_recomp` (131 steps) → `build/linux-m1a/runtime/ps2xTest/vu1_recomp`.
- **Fixture**: a fabricated 16 KB image (pair 0 = lower NOP `0x8000033C`, upper NOP with E bit `0x40000000`; the rest zero) — written for this proof only, never shipped, and not game data. The tool compiled it and, because the image is nonzero only inside VU0's 4 KB, dual-emitted it as a VU0 candidate: fast `vu1_88166fbc90e3fbbc.cpp` and exact `vu1_de435ff9c8a2b8e8.cpp` (3 pairs, 1 block, 1 part each), plus `vu1_programs.cpp` registering both hashes.
- **Compile proof**: the five emitted sources were placed in `generated/vu1/` temporarily; `ninja godhand_vu1_code` in the host tree compiled every TU and archived `libgodhand_vu1_code.a` cleanly — i.e. the CMake glob, the include wiring and the `runImage<hash>` specialisations all build against the current runtime headers.
- **Link + run proof**: a stub main (`m16-fixture/stub.cpp`, kept) that calls `registerGeneratedVu1Programs()` was linked against `libgodhand_vu1_code.a` + `libps2_runtime.a` + `libps2_iop.a` + `libps2_gs_reference.a` + rlImGui/imgui/raylib and **executed**: it printed `registerGeneratedVu1Programs() returned` — both registrations resolved against the runtime's real `registerVu1CompiledProgram` and landed in the real registry.
- **Cleanup**: the fixture sources were then deleted from `generated/vu1/` (the directory removed, restoring the pre-M16 tree). The Android build was made *before* the fixture existed, and the packaged `.so` was verified to contain neither the fixture hashes nor any `registerGeneratedVu1Programs` symbol.
- **Not done, deliberately**: a full host relink of `bin/godhand` with programs present — flipping `GODHAND_HAS_VU1_PROGRAMS` in that tree invalidates the game-code libraries (a ~12,800-step rebuild), and the host binary cannot boot the game anyway (section 2), so it could yield no dispatch evidence beyond the stub link+run, which is the proportionate proof.
- **glslc**: not re-run — M16 touches no shader source and no GS code; M15's 9/9 revalidation against the byte-identical translated set stands.

## 6. Counts, gaps, and what remains

- Real VU images captured so far: **0** — none exist on this machine; capture begins with the owner's first 0.17 session. (Fixture, not counted: 1 fabricated image → 2 registered programs in the host proof.)
- Coverage is inherently play-driven: an image is captured only when the game uploads it, so the title/village/fight route captures the programs that own the measured stall (M15's suspects) plus whatever the intro and menus upload; programs used only in later stages or rare effects will still run interpreted until a session visits them — by design (section 1, point 3) that costs speed, never correctness, and any later session's folder can extend the set.
- The follow-up build (0.18) is mechanical: run `vu1_recomp <returned vu-capture> generated/vu1`, rebuild host + Android, and read the witnesses — `[vu1-aot]` lines should stop for compiled images and `[ee-prof]` comp counts should rise from 0 while interp falls. Verify modes (PS2X_VU0_VERIFY=1 / PS2X_VU1_VERIFY=obs) are available in-tree if a divergence check is wanted before trusting the fast path; PS2X_VU0_FAST=0 isolates the VU0 fast-FMAC variant if a VU0 program misbehaves.

## 7. Owner test (this is the capture session — the play IS the work)

Install 0.17-m16 over 0.16 (same signer, in-place upgrade; ISO and settings carry over). GPU renderer toggle ON, as usual. Then just play the normal route, a few minutes total: title ~20 s, into the village and walk around ~1 min, then a real fight ~1 min. Every distinct VU image the game uploads is being written to disk as you play; nothing about the game's behaviour changes. Afterwards send back **both**:

1. the boot log (Share boot log, as usual) — it should show the `vu capture:` line and one `[vu1-aot]` line per image seen, and
2. the whole **`vu-capture` folder** from `Android/data/dev.ptraaa.godhand/files/vu-capture/` — a set of small files (`vu1_<hash>.bin`, 16 KB each, plus `entries.txt` / `calls.txt`).

That folder is the entire input the fix build needs.
