# God Hand Android — Milestone 19 (0.20-m19): the 0.19 verdict — the barrier was innocent; the queue is the wall; upload dedup

0.19-m18 shipped three fixes: AOT dispatch made provable on device, the lifecycle park/stop wiring, and the narrowed present barrier. The owner's run (2026-11-03 03:56 WITA, single session) came back *"Masih sama kacau"* — still the same mess: two combat screenshots at a displayed 1 FPS with worst frames of 2978 ms and 2187 ms. Both screenshots also show **no visual corruption**, which clears the barrier change visually. This milestone is the forensic pass over that session against the 0.18 session, the conviction it supports, and the fix build 0.20-m19. Counts and behaviour only, as always — no image hashes, no game bytes.

The short version: 0.19's lifecycle fix works (the log shows the park/resume lines, and the owner confirms the phone feels normal after closing the game — that front is closed). The AOT instrumentation works exactly as designed: `[vu1-aot] 5 compiled VU program(s) registered` at boot, and every window reads interp 0, comp = all runs, fb 0. But in the heavy-fight windows 0.19 is **statistically identical to 0.18** — the barrier narrowing changed nothing measurable there, because the barrier was never the cost. What fills the windows is the aggregate GPU stream itself: in the worst window essentially *all* of the GS worker's "busy" time is fence-blocked time, waiting for the GPU to retire work submitted about a second earlier. Section 3 answers the present-decoupling question with the frame math; section 4 ships the one structural reduction this evidence supports — content dedup on the upload path — plus the byte accounting that should have existed all along, so the next log convicts the upload stream's true size instead of leaving it inferred.

## 2. Q1 — what actually fills the GPU queue in fight windows

**The worker's busy time is mostly waiting time.** In the worst 0.19 fight window, ring-fence waits total 4,330 ms inside a ~5.35 s window whose GS busy reads 81% (~4.33 s): essentially *all* of the worker's busy time in that window is time blocked in `ClientWaitSync` on ring fences — counted as busy because the waits happen inside backend entry points. This also resolves the apparent contradiction of "busy only 55–81% while fences eat seconds": the complement of busy is not GPU idleness. It is the worker starved on its own op queue, because the EE thread upstream is itself throttled — its queueWait averages 90–168 ms in the same windows. Both threads are waiting, in a chain, on the GPU.

**What each fence waits on.** The upload ring is 4 chunks × 16 MB. A fence is placed when a chunk fills and waited on when the ring wraps back into that chunk, so a wait means "the GPU has not yet retired work submitted three chunks (≈48 MB of stream) ago". Fight windows wrap the ring 8–19 times (2–4.75 laps per window), each wrap waiting 154–433 ms on average. Read as a rate: the GPU retires roughly one 16 MB chunk of mixed stream per 0.3–0.5 s in these windows and runs on the order of a second behind submission. The fences are not a synchronisation defect; they are the back-pressure gauge of a stream the GPU cannot retire in real time.

**The stream, per field, in a steady fight:** ~3,900–4,600 primitives (≈0.7 MB staged with state words), ~6,300–6,900 tiles — about 5.6–6.1 full-screen passes over the 640×448 frame (1,120 tiles per pass) — across only ~40 batches, plus ~160 barriers per field (one after each flush section), plus CLUT work, plus texture uploads. The per-bucket attribution in [gs-work] is misleading by construction and this log proves it: in one window raster reads 4,302 ms against uploads 87 ms; in another, uploads read 3,754 ms against raster 54 ms; a third reads uploads 3,527 ms / raster 79 ms. The fence wait lands in whichever section happens to trigger the ring wrap — including `executeTransfers` called mid-submit on the overlap path (reason 2), which is how an "uploads" bucket can hold 3.5 s while raster does nothing. The total blockage is conserved; only its label moves. **The wall is the aggregate byte stream through one ring into one GPU, not any single section of it.**

**CLUT is a symptom, not the wall.** loadClut runs 164–247 times per field and queues 87–307 grouped ops per field — the guest churns materials constantly — but each op is a ≤256-entry copy staged as 24 words, one grouped dispatch per flush: tens of KB per field at most. Its dispatch count is real but small next to multi-MB prim/upload traffic. The single-entry CLUT key (alternating palettes always miss) is a known wart; fixing it would shave dispatches, not seconds.

**Uploads are the actionable stream — and the one never measured.** Two fight windows are upload-dominated with raster near zero, which proves the upload stream alone can saturate the queue. Yet nothing in any shipped build counted upload *bytes*: [gs-work] counted calls and ops everywhere else. What the game streams per field — genuinely new textures, or the same textures re-sent — was unanswerable from the 0.19 log. That gap is closed in 0.20 (section 4.2), and the re-send case is exploited in 4.1.

**VU1 pc 0x0520's wandering cost is a contention symptom.** Its per-call cost reads 26.5 µs in raster-dominated windows, 105.6–163.6 µs in the upload-dominated windows, 18.4 µs in the final window — at near-constant call counts (~17.5k–19.4k per window). The compiled code does not change between windows; the SoC's other cores and memory bus are saturated by the same backlog (and the part is hot). AOT counters stay clean throughout (interp 0, fb 0), so this is charged to contention, not to the compiled programs.

## 3. Q2 — can the present path be decoupled? It already is; the math says the label is swap-bound

The proposed decoupling — present the latest completed frame, don't drain the queue — is **already the shipped behaviour**: async present mode 2 is the default, `presentAsync` harvests the newest completed readback and returns it, and in fight windows the gs-fetch segment of [frame-split] is only 12–30 ms. Present never drains the GS queue.

The frame completion math from the fight windows:

- Fields **complete** at 10.6–14.3/s (54–73 per window).
- Presents **run** at 4–8 per window — frames complete roughly ten times faster than they are shown.
- The present interval is 97–99% **swap**: the frontend's own `eglSwapBuffers` blocks 0.87–1.47 s per present, because the display composition queues behind the same saturated GPU. Presents per window ≈ window length ÷ swap block (5.3 s ÷ ~1.2 s ≈ 4.4) — the display loop is swap-bound, and the swap inherits the GS queue's saturation.

So decoupling further would not change the displayed rate: there is no queue-drain left in the present path to remove. Bounding frames-in-flight could only help by deleting queued GS work, and that is unsafe in this backend — uploads, CLUT loads and copies are VRAM state that later fields read, and this guest provably reads rendered pixels back (the section 1.2 drains). Dropping fields would corrupt state, not just drop frames. A non-blocking swap would only move the throttle into Android's compositor (BufferQueue), not remove it. **The only lever that moves both the completion rate and the swap is shrinking the stream itself** — which is what 0.20 does, on the one stream section 2 convicts as both large and unaudited.

## 4. What 0.20-m19 changes

### 4.1 Upload content dedup: stop re-writing bytes VRAM already holds (the fix)

PS2 games re-stream textures constantly, and this backend has always re-dispatched every staged chunk unconditionally — including chunks that write byte-identical data to a destination that already holds exactly those bytes. 0.20 filters staged uploads at `executeTransfers()`, the single choke point where staged chunks become GPU work:

- **Key**: the chunk's descriptor geometry — destination block pointer, buffer width, pixel format, row width, start pixel, pixel count, destination x/y.
- **Value**: an FNV-1a hash of the chunk's staged bytes.
- **Validity**: an entry vouches for its destination pages only until any GPU write touches them. Writes are tracked with exactly the page sets that already feed M14's `renderedPages` provenance — draw targets in `prepareTarget`, local→local copy destinations, framebuffer clears, `WriteVram` pokes — accumulated into a dirty set and applied at the top of every `executeTransfers`, in stream order. A kept chunk also evicts older entries overlapping its pages before recording its own, so overlapping writes inside one batch order correctly.

The skip is sound because of how uploads write: the upload shader addresses **physical VRAM pages directly** (`writePixelRaw`) — there is no epoch page map in the upload write path. (The copy-on-write shadow pages are reader-side state for draws; an upload, dispatched or skipped, never touches them, and the post-state of a skipped upload is byte-identical to a dispatched one.) A skipped chunk never enters the ring: no bytes copied, no dispatch, no trailing barrier — it removes stream volume at the exact point section 2 measures. The table is bounded (8,192 entries, oldest half evicted) and the whole mechanism has a kill switch, `PS2X_GS_UPLOAD_DEDUP=0`, restoring the previous always-dispatch behaviour.

### 4.2 Byte accounting, always on (instrumentation)

Every [gs-work] line now ends with the stream's byte census: payload bytes actually dispatched for uploads, bytes and chunk counts skipped by the dedup, and total bytes pushed through the upload ring. One fight window of the next log will state exactly how large the upload stream is, what fraction of it was re-sends, and what fraction of the ring the raster stream owns — the three numbers sections 2–3 had to infer.

### 4.3 Untouched

The compiled VU1 programs (the same five, same generated sources) and the registry; all shaders; the present path and the narrowed barrier (kept — proven visually safe, harmless); the lifecycle wiring; the CPU GS backend; the desktop build's behaviour (the dedup is platform-neutral and equally valid there; the counters likewise); capture, still armed exactly as before.

## 5. Honest limits

- **If the fight's upload stream is mostly genuinely new data, the dedup skips almost nothing and 0.20's fight gain is small.** The counters will say so in a single run, in bytes, not impressions. What remains even in the best case is a compute rasterizer pushing ~4.4k primitives and ~6.5k tiles per field at native framebuffer resolution while the guest itself needs 70–94 ms per field: both sides of the pipeline are saturated simultaneously, and this build does not claim 60 fields/s.
- **There is no half-resolution lever to reach for.** `PS2X_GS_SCALE` is an integer supersampling factor (the ctor clamps `atoi` to 1–8); the owner's "0.5" setting parses to 1 and always has — the rasterizer has run at native 640×448 in every session, and in this design VRAM *is* the texture memory, so lowering internal resolution is a different backend, not a setting. A real resolution/quality scaler, or a faster rasterizer, is a milestone of its own.
- The dedup costs CPU hashing on the GS worker (byte-at-a-time FNV-1a, ~1 GB/s class). Worst case it adds single-digit ms per field against dispatches that cost tens of ms on a saturated queue; if a future log ever shows it in the submit timings, the kill switch exists.
- The dedup's failure mode, if the invalidation audit missed a VRAM writer, would be a stale or wrong texture on screen — visible in exactly the screenshots the owner already sends every run. One screenshot settles it, as with the barrier.
- Coverage is unchanged: the same five VU images; new areas still run interpreted until captured. VU0 remains unexercised by this route.
