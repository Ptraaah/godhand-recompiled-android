# God Hand Android — Milestone 17 (0.18-m17): the fix build — the owner's captured VU programs, compiled in

M16 wired the capture and proved the pipeline on a fabricated fixture; the owner's 0.17 session (2026-11-02 23:17 WITA) returned the real thing. This milestone runs the pipeline over that capture set and ships the result: **the five VU program images the game actually uploaded during the title/village/fight route are now compiled ahead of time into the package and registered at startup**, dispatched by the runtime's existing hash-keyed, generation-checked machinery, with the interpreter still underneath everything the set does not cover. This is the build the whole M13–M16 chain was aiming at: the in-game stall was convicted to guest VU time running in the cycle-accurate interpreter, and for the captured programs that interpreter is now bypassed.

Counts only in this report, by design: the captured images are game code, so they and anything derived from their bytes live only in the local workspace — never in git, never quoted here (no image hashes, no byte content).

## 1. The pipeline over the real capture set

Input (the owner's returned folder, staged verbatim into `m17-input/`): 5 images of 16,384 bytes each, an entries file listing 22 entry points across the 5 images, and a calls file recording 100,000 VU calls in the one short session. `vu1_recomp` (the host tool built in M16, unchanged) ran over the set and exited 0:

| image (by size class) | pairs compiled | blocks | emitted parts |
|---|---|---|---|
| full-size program A | 1139 | 9 | 3 |
| full-size program B | 1139 | 9 | 3 |
| full-size program C | 1139 | 9 | 3 |
| full-size program D | 1139 | 9 | 3 |
| smaller program E | 575 | 5 | 2 |

(emission order and identities are in `m17-recomp.log`; four of the five are near-identical in shape — same pair/block counts — consistent with the related program family M16's tool comments describe for this game.) Tool totals across the set: 741 known segments, 2,076 pairs whose dead MAC/status flags were eliminated, 8 self-looping segments, all 5 images reported without sticky accumulation. **No image and no entry point was rejected or partially handled** — the tool emitted a complete program for every captured image: 20 sources in `godhand-recomp/generated/vu1/` (5 program roots, 14 parts, and `vu1_programs.cpp` carrying exactly 5 `registerVu1CompiledProgram` calls).

**The VU0 dual-emission question does not arise for this set.** Per M16, the tool dual-emits (fast + exact, the exact under the VU0EXACT-derived key) only for an image whose code is confined to VU0's 4 KB window. All five captured images carry nonzero code beyond that window (their used spans end near 4.6 KB and 9.1 KB respectively), and their recorded entry points include addresses in the upper half of the 16 KB image — they are VU1 programs, each emitted exactly once under its plain content hash. No VU0-sized image was captured in the session at all (no additional image files), so there is no fast-versus-exact variant choice to make and nothing was silently defaulted: the semantics-exact preference governs a choice this set never presents. (For completeness: the VU1 emission used the tool's documented defaults for this game, as recorded in M16 — fast FMACs on, normalised loads; the documented God Hand geometry case is what rules out the raw-load alternative.) The host proof below additionally probed the registry for the five exact-variant keys and found none registered — exactly as expected.

## 2. Host proof against the real generated set (no game boot)

Following M16's stub pattern, extended to count (stub: `m17-fixture/stub_count.cpp`, kept): the real generated sources were built in the host tree (`ninja godhand_vu1_code`, 24 steps, exit 0 — 16 generated translation units plus the archive), and the stub was linked against `libgodhand_vu1_code.a` + the host tree's real `libps2_runtime.a`, `libps2_iop.a`, `libps2_gs_reference.a` and the raylib/imgui support libraries. Running it:

- `registerGeneratedVu1Programs()` returned normally against the runtime's real registry;
- probing the registry through the runtime's own `findCompiledVu1ProgramByHash` for each captured image: **5 of 5 REGISTERED**;
- probing the five VU0EXACT-derived keys: **0 registered** (section 1);
- probing an unknown key: **missing** — the fallback is intact at the registry level: an image outside the set resolves to nothing compiled and the interpreter serves it.

(The probe declares the lookup with a pointer return type; the Itanium mangled name of a non-template function does not encode its return type, so the declaration links against the real symbol and is ABI-identical — the same spirit as M16's empty EE-table stub. No game was booted for this proof — no full disc exists on this machine, and none was attempted, per M16 section 2.)

## 3. Android build

Adding `generated/vu1/*.cpp` flipped the tree exactly as M16 section 1 describes: the CONFIGURE_DEPENDS glob populated `godhand_vu1_code`, `GODHAND_HAS_VU1_PROGRAMS=1` landed on the godhand target, and `main.cpp`'s existing registration call compiled in. The define flip invalidated the cached tree, so the Android build was effectively full: **13,212 ninja steps, zero failed** (log: `m17-build.log`), after which a re-run reports "no work to do". Tree `libgodhand.so`: 98,424,408 bytes, SHA-256 116714dde7fcb2a79fdac3259d42b9d294518078dccdadf4dfdf59fd825ae403. Symbol census on the tree `.so`:

- `registerGeneratedVu1Programs` present (called from `main()` under the define);
- **5 distinct compiled-program entry points** (the `runImage` specialisations, one per registered image, with their dispatch tables);
- the runtime's registration/lookup symbols present and unchanged;
- the `vu capture:` arming string and both 0.18-m17 banner strings present.

Compiled programs in the binary == programs emitted == programs registered in the host proof: **5 == 5 == 5**.

Untouched in M17: every runtime source (including the interpreter, the generation-keyed + memcmp-verified matching, and both kill switches), the CPU GS backend, the shaders (no glslc re-run — nothing shader-adjacent changed; M15's 9/9 stands, as in M16), the Windows branch, and the generated EE code. The only source edits are the new `generated/vu1/` set and version strings (manifest 18 / 0.18-m17, glue banner + entry line, three Java log/title strings). The glue's capture arming is byte-identical to 0.17.

## 5. What the GPU toggle does and does not change for VU dispatch

The launcher's GPU toggle selects only the GS backend (GPU renderer vs CPU renderer). **VU AOT dispatch is orthogonal to it**: the compiled programs register in `main()` and dispatch in the runtime's VU layer regardless of which GS backend renders, so toggle OFF boots and plays with the same 5 compiled VU programs active — what changes with the toggle is only which GS backend draws (0.17 behaviour on that axis, CPU backend untouched). Toggle OFF does **not** disable VU dispatch, does not disable capture, and does not change any instrumentation. (The runtime kill switches `PS2X_VU1_RECOMP=0` / `PS2X_VU0_RECOMP=0` still exist in-tree for diagnosis; the glue does not set them.)

## 6. Expected witnesses in the owner's next log

- The `vu capture:` line (arming unchanged) and the 0.18-m17 banner.
- `[vu1-aot]` miss lines: should appear **only** for images outside this set of 5 — i.e. content the capture session never uploaded (later areas, unseen effects). On the same title/village/fight route, the expectation is **none** for the programs that owned the stall.
- `[ee-prof]`: VU time should shift from the interp buckets to the comp buckets for VU1 (comp counts rising from 0, interp falling) while the guest fields-per-second climbs. VU0, if the game calls it, remains interpreted (no VU0 image in this set) — its buckets should look unchanged.
- The verdict metric stays the owner's: fields actually advancing (frame-split) and how the game *feels*, not the host present counter.

## 7. Coverage limits, honestly

The compiled set is exactly one short session's worth of the game: title, menus, the starting village and one fight — 5 images, 22 entry points. Anything the game uploads only elsewhere stays interpreted until a session captures it: later stages and bosses, other characters' and enemies' special effects, minigames, and any VU0 microprograms the game may use in places this route never reached. That costs speed only where it applies, never correctness (M16 section 1), and capture remains armed in 0.18, so every future session's folder extends the set for a later coverage build. How much of the *originally measured* stall these 5 programs own is the open empirical question this build exists to answer — they are the programs the stalling route itself was running, but the [ee-prof] comp/interp split in the next log is the proof, not this report.
