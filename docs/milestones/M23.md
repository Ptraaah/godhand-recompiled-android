# God Hand Android — Milestone 23 (0.24-m23): pillar 3 learns the scan — coalesced window prefetch and a bounded stale policy for in-scan misses

The 0.23 verdict (owner run 2026-11-03 23:21 WITA, *"Masih sama"*) split in two when the log was read (owner-0.23-run/ANALYSIS.md). What ARUS promised, it kept: in light and menu windows the present-age bound holds (avg 1.1-1.3 fields, max 2-3, against 25-70 pre-gate), raster is no longer the fight bottleneck (24-49 ms per window under block shading), and async readback mode 3 works where it hits — fight windows count l2h sync 9-12 against async 15-19. What remained is the cost of the misses: **two fight windows still carry 3210-3332 ms of `readData`**, and the `[l2h-path]` trace shows exactly why. The misses are a sequential scan — positions 323,35 then 324,35 then 325,35, walking one row a step at a time — and the *first* read at each new position misses, pays a full synchronous queue drain (~280 ms a read at fight queue depths), and only the repeats behind it hit. A scan's next positions are the most predictable reads in the whole system. 0.24 teaches pillar 3 the scan's shape, and gives its misses an explicit, bounded, switchable policy.

The short version, three changes on top of M21's cache:

1. **Coalesced window prefetch.** After 3 consecutive misses advancing by one constant small axis stride, the scan is *armed*: the upcoming window of up to **16 positions** is read ahead as **one** gather transfer — the union rect of the covered positions, through the back end's existing copy path — into **one** staging slot behind **one** fence. No per-position GPU work is dispatched. When the fence retires, the staging bytes are sliced into one cache entry per covered position. The window rolls: a new one issues only when fewer than 4 covered positions remain ahead and none is in flight.
2. **A miss policy for the active scan (new mode 4, the shipped default).** A miss that continues an armed scan, whose *previous scan position* is cached, is served that neighbour's bytes immediately and counted as stale-served, while a normal refresh backfills the true entry in stream order. It pays no drain. Isolated reads — no active scan, no cached neighbour, any miss below mode 4 — stay synchronous and exact. Mode 3 (selectable in the same ini row) is mode 4 minus the stale policy: same gates, same key, same prefetch.
3. **Telemetry that can judge all of it in one device run.** Every `[gs-work]` window with speculation activity now prints one `[l2h-prefetch]` line: positions issued / useful / wasted / discarded on publish, the window's misses split stale vs sync, and the window's total `readData` time.

## 1. Why this shape

- **The miss, not the read, is the cost.** M21 established that a fight read's payload is at most 256 bytes and its bill is queue-drain latency; M22's field gate shrank the queue those drains wait on but cannot remove the drain itself — a synchronous read still waits for everything submitted ahead of it. The only way a first read stops paying is for its bytes to already be in the cache, or for the read to stop being synchronous. 0.24 does both, each where it is safe: ahead of the scan (prefetch) and inside it (the neighbour policy).
- **Coalesced, because the slot budget is real.** The download machinery has 4 staging slots. Sixteen per-position downloads would evict the refresh traffic the cache lives on and serialise on slot availability; one gather occupies one slot with one fence and retires once. The addressing is cheap in this back end precisely because VRAM is a flat SSBO at one word per guest pixel: the scan's positions are successive rects of one buffer, their union is one bigger rect, and the existing `copyRegion`/`BeginDownloadAsync` path reads any rect unchanged. Slicing the packed result back into per-position entries is host-side byte math on rows (positions along one axis, entries offset by the stride) — gated to byte-aligned formats (bpp 8/16/24/32); sub-byte (4bpp) scans keep a few single-position speculations instead, since nibbles do not slice out of a packed gather.
- **The stale policy follows shipped emulator practice, bounded by our own evidence.** PCSX2 ships an explicit unsynchronized local-memory read path (`GSReadLocalMemoryUnsync`, an MTGS bypass) for read sites that tolerate it, rather than pretending every local-memory read must be exact. Our classification evidence is narrower and stronger: these scan reads already tolerate one-step-stale data today — every mode-3 cache hit in the 0.22/0.23 device sessions served the previous transfer's bytes for the same key, with no observed corruption and no wrong-effect report from the owner across two sessions — because the cache's one-transfer-late semantics are exactly one step of this same staleness. Mode 4 extends that one step *sideways*, to the previous scan position, only inside an armed scan, only when that neighbour is genuinely cached, and always with an in-order backfill so the true entry lands immediately behind. Outside those bounds the read is exact, and the per-window stale count in the log makes the policy's actual use auditable after the fact rather than a matter of trust.
- **Prefetch rides the existing discipline, not a new one.** A window snapshot is taken by the same in-order, fence-based download a refresh uses, enqueued at the triggering miss's own point of the GS stream (the drain op follows the miss's own transfer op). Its bytes are never newer than the read that will consume them. When a prefetched entry is served, the serve enqueues the same refresh any hit enqueues, so from its first serve onward an entry is indistinguishable from a captured one.

## 2. The invalidation audit, and the dependency-stamp decision

This milestone was asked to confirm the cache's invalidation discipline and to evaluate a per-region write-sequence stamp for prefetched entries. The audit result, from the code as shipped in 0.23, stated plainly:

- **The cache has no write-submission invalidation, and never has.** No guest write, upload, local->local transfer, draw or poke removes or marks a cache entry; a grep for entry removal finds none outside the serve/capture bookkeeping. The discipline that exists is *ordering*: entries are written only by in-stream snapshots (sync captures and refresh/prefetch callbacks), a hit always enqueues a refresh, so any entry's staleness is bounded to one transfer of the same key, and the save-state reset drops in-flight serves/captures while keeping contents. Prefetched window entries sit under exactly this discipline, identically to normal entries — same write paths, same refresh-on-serve, same reset behaviour — plus two guards a normal entry does not need: a window slice is **dropped on publish** if a real entry for its position landed meanwhile (counted as `discarded`), and a sync capture for a prefetched key supersedes the mark (counted as `wasted` if the entry was never served).
- **The dependency stamp was evaluated and is not built.** The middle-ground proposal — store the region's write sequence at submission, discard on publish if it moved — has no sound granularity available in this back end. Keyed on guest *transfers* it would almost never fire (the writes that matter to rendered-class reads are draws, not transfers), giving false confidence. Keyed on *draw targets* it would fire constantly: the scan's source is redrawn per field, so every window would be discarded before publish and prefetch would be dead by construction — the same arithmetic that killed the exact generation cache in M21 (section 3.1 of the exploration). The exposure a stamp would close is also already bounded: a prefetched snapshot can be served at most until its first serve's refresh lands — the identical bound a normal hit on the same key has carried since M21. **Per-tile/per-region generation counters remain a considered-and-deferred item**: the machinery (a generation array bumped at the GPU back end's centralised write sites) is documented in m21-explore §3.1 for the milestone that has evidence an exact cache would hit often enough to pay for it. That evidence does not exist yet; the telemetry in this build is how it would be gathered.

## 3. Audit note: what `readData()`'s `glGetBufferSubData` actually is on this device

Asked for explicitly, answered from the loader (`gs_gl.cpp`, Milestone 12's work): `glGetBufferSubData` **does not exist in OpenGL ES in any form** — it is not an ES 3.2 core entry point. The Api table first tries `eglGetProcAddress("glGetBufferSubData")`; the 0.23 device boot log records the outcome on Pablo's Adreno 725: `[gs-gpu] ES entry points: glGetBufferSubData = map shim (no ES entry point exists)`. What actually runs for every synchronous read in `Impl::readData()` (and `downloadVram`, `ReadVram`, the CLUT read) is **our own map-based wrapper**, `esGetBufferSubData`: `glMapBufferRange(GL_MAP_READ_BIT)` + `memcpy` + `glUnmapBuffer`, honouring the desktop entry point's contract. Noted, and deliberately not changed in this build: the map is where the implicit synchronisation lives on this driver — mapping a buffer the GPU is still writing waits for that work, which is the drain M21 measured — so the name of the call was never the cost, and no call-site change alters it. The fence-based download path used by the cache (persistent-mapped slots, `glFenceSync`, non-blocking harvest) remains the only read route in the system that does not pay it.

## 4. What 0.24-m23 changes

Two files in the shipped tree (`godhand-recomp/runtime/ps2xRuntime`), plus the manifest version. No shader, frontend, host-loop, download-slot or `main.cpp` changes.

### 4.1 The threaded backend (`src/lib/gs/gs_threaded_backend.cpp`)

- **Mode 4.** `asyncReadbackMode()` gains mode 4 as the unset default; `=3`/`wide` selects mode 3; `=all`/`2`, `=1`, `=0`/`off` keep their exact prior meanings. Modes 3 and 4 share M21's admission (≤ 64 px total, any shape, depth + colour) and the position-exact key. Nothing about modes 0-2 changes.
- **Job kinds.** The refresh queue element becomes `RefreshJob{key, command, speculative, window…}`; the drain loop (previously a lambda local to `BeginTransfer`'s hit path) is hoisted to `drainReadbackRefreshes()` so miss paths can enqueue it too. Normal refresh jobs run through it byte-for-byte as before, plus one accounting hook (section 4.3).
- **Scan tracking (`noteScanMissLocked`).** Called under the readback mutex on every mode 3/4 miss. It tracks one series at a time (buffer page, width, format, shape), establishes a stride from a constant single-axis step of at most 16 px, and counts consecutive striding misses; at 3 the scan is armed. Series changes and stride deviations reset the run and the coverage marks (a window *generation* counter keeps a stale in-flight window from moving a new series' coverage).
- **Coalesced window issue.** While armed: if no window is in flight and fewer than 4 covered positions remain ahead, one `RefreshJob` is queued whose command is the gather rect (the current read's command with position moved to the window origin and size expanded to the union of up to 16 positions, clamped to the position range and the buffer's known width `sbw * 64`). One job, one download slot, one fence. All covered positions are marked prefetch-pending; `issued` counts positions, not jobs.
- **Window publish.** The job's callback (fence harvest, on the worker) slices the packed staging bytes into per-position entries and publishes them under the guards of section 2: a position whose real entry landed meanwhile is dropped (`discarded`); entries are marked `prefetched`. If the download could not be dispatched at all (no free slot, non-GPU back end), the window is dropped and marked covered — a busy slot must not make every following miss re-issue the same window; its positions simply stay uncached and are read as before. Speculation never takes a synchronous fallback anywhere.
- **Mode 4's stale serve.** In `BeginTransfer`'s miss branch, before any capture is set up: if the scan is armed, this miss continues the stride exactly, and the cache holds the previous scan position's entry for the same series, the guest is served that entry (`[l2h-path]` prints `async-stale`), a normal refresh job backfills the missed key in stream order, and the scan tracker advances as for any miss. The served bytes never enter the cache under the missed key (no capture is armed), so the neighbour's data cannot poison the position's own entry. First-ever and isolated reads — no armed scan, a broken stride, an uncached neighbour — take the synchronous capture path unchanged and are counted as sync misses.
- **Reset hygiene.** The save-state hook additionally clears the scan tracker, coverage and pending/prefetched marks (unserved prefetched entries are counted `wasted` there), beside the refresh queue it already cleared. Cache contents survive, as before.

### 4.2 The GPU back end (`src/lib/gs/gpu/gs_gpu_backend.cpp`)

One local declaration and, in `workMaybeReport`, the read-and-reset of the speculation counters plus the one summary line, printed right after `[gs-work]` in windows where any speculation counter moved:

```
[l2h-prefetch] issued N useful M wasted W discarded D | misses stale S sync Y | readData T ms
```

`readData T` is the window's own total from the existing `[gs-work]` accounting (`work.dataReadMs`), repeated here so the speculation line is self-judging. Nothing else in the file changes: pillars 1, 2 and 4's code, the `[l2h]` split, `BeginDownloadAsync` and its 4 slots are untouched.

### 4.3 Telemetry definitions (what each number means)

| Counter | Meaning |
|---|---|
| `issued` | Positions speculatively read in the window (window positions + 4bpp-fallback singles). |
| `useful` | Guest reads served by a prefetched entry (the window hit rate is `useful / issued`). |
| `wasted` | Prefetched entries overwritten by a capture/refresh, or cleared at a state load, before ever being served. |
| `discarded` | Window slices dropped on publish (a real entry landed first, or short bytes). |
| `misses stale` | Misses served by mode 4's neighbour policy. |
| `misses sync` | Mode 3/4 misses served synchronous-exact (the drains that remain). |
| `readData` | The window's total synchronous read time — the cost line itself. |

### 4.4 Untouched

The sync `readData` path and its exact semantics for every read that remains synchronous; mode 1/2 gates and keys bit-for-bit; the frontend; the CPU and PCSX2 back ends' behaviour (speculation never dispatches on them — a window job on a non-GPU inner is dropped, a backfill is a normal refresh as before); the compiled VU1 programs and registry; capture, still armed as before; all of `main.cpp`, including the ini rows and the ARUS master switch (section 6).

## 5. The numbers to judge this milestone by

Named in advance, from the 0.23 log's own fight windows:

- **`readData` ms per fight window**: 3210-3332 ms in the two heavy 0.23 fight windows (the `[l2h-prefetch]` line repeats the window total so no cross-referencing is needed). Every scan position the window covers converts a ~280 ms sync drain into an async serve, and every in-scan miss the neighbour policy catches converts one into a backfill. What should remain synchronous approaches the fight-entry reads plus non-scan reads.
- **Prefetch window hit rate, `useful / issued`**: for a clean row walk this should approach 1 over a window's issued positions (minus the walk's tail past where the fight ended). High `issued` with low `useful` means the prediction or the landing timing is wrong on device — downloads retire at present/download polls, and if the scan outruns the harvest the entries land behind it; the `wasted` count separates that failure (landed, never used) from `discarded` (a real entry won the race, which is benign).
- **Stale-served miss count**: how much of the fight's miss load mode 4 actually carried. Stale high *and* readData low is the policy working; stale high with any wrong-effect report from the owner is the policy indicted — the count exists so the two can be told apart in one run.
- **`misses sync`**: the residual drains, per window, attributable.
- **Presents/s and worst frame** (`[frame-split]`): the player's number. 0.23 fight windows ran 5-12 presents/s; this is what "masih sama" was about, and it is the line that must move.
- **Present age** stays the pillar-4 check (at most ~3 fields in fights) — speculation must not disturb it.

And the known ceiling, stated plainly: fence waits of 675-4595 ms per window in 0.23 are the field gate pacing submission against real GPU throughput. Removing drain latency from the EE thread's way does not create GPU throughput; if the fight's remaining cost is dominated by the gate's pacing rather than readback drains, presents/s will move less than readData does. The lines together — not any one alone — are the verdict.

## 6. Switches

| Switch | Effect on M23 |
|---|---|
| `asyncreadback=off` (ini) / `PS2X_GS_ASYNC_READBACK=off` | Mode 0: no admission, no cache, no prefetch, no stale policy — every read synchronous and exact. The full kill switch, unchanged. |
| `PS2X_GS_ASYNC_READBACK=1` | The pre-M21 gates and key. No prefetch, no stale policy. |
| `PS2X_GS_ASYNC_READBACK=3` | M21 admission + coalesced prefetch, **without** the stale policy — the isolation setting if mode 4's policy ever needs separating from the prefetch change. |
| `PS2X_GS_ASYNC_READBACK=4` / unset | Mode 4: everything in this build. The shipped default. |
| `arus=off` (ini, or `PS2X_ARUS=off`) | The master switch forces `PS2X_GS_ASYNC_READBACK=1` before the back ends parse it, so prefetch and the stale policy die with ARUS, with no M23-specific code in `main.cpp`. |

## 8. Owner test

Install 0.24-m23 over 0.23 (same signer, in-place upgrade; ISO and settings carry over). Same settings (GPU on, threads off), same short route: title ~20 s, village ~1 min, one real fight ~1 min, then share the boot log and the vu-capture folder. Three things to report:

1. **The fight FPS label** — and whether the fight *responds*: the drains this build removes were sitting between the game and its own effect/visibility samples, so inputs and reactions are the first place a change is felt.
2. **Anything that behaves wrong in the fight** — above all effects, flashes or enemy reactions that look a frame late, fire when they should not, or fail to fire. Mode 4's neighbour samples are the new risk surface here; that observation outranks every number.
3. **The boot log itself** — its fight windows now carry the verdict without interpretation: `readData` against 0.23's 3210-3332 ms, `useful / issued` for the windows, and the stale count showing how much load the neighbour policy carried.

To A/B without reinstalling: `asyncreadback=off` under `[video]` in `godhand.ini` makes every read synchronous and exact (0.21 behaviour); `asyncreadback=3` keeps the widened cache and prefetch but removes the stale policy, if the two changes ever need separating on device; `asyncreadback=1` restores the pre-M21 gates entirely.
