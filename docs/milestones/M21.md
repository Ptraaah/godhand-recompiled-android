# God Hand Android — Milestone 21 (0.22-m21): the async readback cache learns the fight-read profile

M20 collapsed the raster bucket (~2.3 ms/field in the heavy fight window, against 24-48 ms/field in 0.20), and the 0.21 verdict (owner run 2026-11-03 11:39 WITA, *"Masih sama"*, street screenshot 12 FPS / worst 247 ms, picture clean and blocky as predicted) exposed the next wall in the same log lines: with the queue no longer saturated by raster, the guest runs fights continuously, and in **every** fight window it issues 15-20 tiny local->host readbacks of rendered pixels — each at most 64 pixels, at most 256 bytes — and pays for every one of them a full GS queue drain in `Impl::localToHostTransfer()`'s synchronous `readData()` (`glGetBufferSubData` behind the narrowed barrier). The `[l2h]` stage split is unambiguous: flush ~0 ms, copy ~0.3-0.6 ms, pack ~0.1 ms, **mapread ~175-285 ms per read** (5993.7 ms for the single read queued behind the heaviest window), 3.5-6.0 s per fight window. The cost is queue-drain latency, not bytes: the read waits for everything submitted ahead of it, and the EE thread parks in `ConsumeLocalToHostBytes` until it lands. The exploration for this milestone (`m21-explore.md`) confirmed the path end to end and found the important fact: **an asynchronous readback cache for exactly this pattern already exists** in `GSThreadedBackend::BeginTransfer` (built for Urban Reign's depth-buffer flare test). The fight reads missed it only on admission — the shipped default (mode 1) admits only depth formats up to 8x8 per side; colour formats needed mode 2 (`=all`, up to 16x16 per side); a 64x1 strip fails both. 0.22 widens the admission to the fight-read profile, hardens the cache key, and makes every transfer's path visible in the log. Nothing else changes: the synchronous `readData` path keeps its exact semantics for every read that remains synchronous, and M20's block shading, the 0.20 upload dedup and the fence-based async download machinery are untouched.

The short version: a new mode 3 of `PS2X_GS_ASYNC_READBACK` — the shipped default in this test build — admits any local->host transfer of at most 64 pixels total, in any shape and any format the threaded backend can size, into the existing one-transfer-late async cache; its cache key now includes the source position (ssax/ssay), so an entry can never serve bytes from a different position of the same page; every local->host transfer prints one `[l2h-path]` line stating its page, format, position, shape and whether it was served `sync`, `async-miss` or `async-hit`. `PS2X_GS_ASYNC_READBACK=off` disables the cache entirely and `=1` restores the pre-M21 gates exactly; both are full kill switches back to synchronous reads.

## 1. Why this shape (the exploration's verdict, compressed)

- The stall is not the read, it is the wait. A fence placed after the read's own copy dispatch would sit behind the same flushed batch in the same single-context queue and cost the same drain; narrowing the flush to the source region's primitives would mean splitting `flushBatch` by page overlap — a ring-protocol restructure, out of scope, and it would still leave a per-read wait.
- The only way a synchronous guest read stops paying the drain is for the guest not to wait synchronously — which is precisely the existing async cache: on a hit the guest is served the previous transfer's bytes for the same key immediately, and the GS thread refreshes the entry in stream order through `GSGpuBackend::BeginDownloadAsync` (persistent-mapped buffer + `glFenceSync`, harvested by `pollDownloads`), falling back to an in-order synchronous transfer on the worker when no download slot is free. The GPU-side machinery needed no changes at all.
- An *exact* cache (serve only bytes provably unchanged since a generation snapshot) was considered and rejected for this milestone: the fight reads are rendered-class every window, and if their source pages are redrawn per field the generation changes between consecutive reads and the exact cache degenerates to the sync path plus bookkeeping. The staleness cache is the design that can actually win here; its price — one-transfer-late bytes — is weighed in section 3, not hidden.
- Widening had to be scoped: modes 1 and 2 keep their exact pre-M21 meanings so the old tuning (and the kill switches) behave as they always did. The widened profile is a new mode value, and it is the default only in this test build.

## 2. What 0.22-m21 changes

Two files in the shipped tree (`godhand-recomp/runtime/ps2xRuntime` and `godhand-recomp/src`), plus the manifest version. Nothing else.

### 2.1 The threaded backend (`src/lib/gs/gs_threaded_backend.cpp`)

- **Mode parsing.** `asyncReadbackMode()` now maps the variable as: unset/empty -> **3** (new; the shipped default so the test build exercises the widened cache with no ini edits), `0` or `off` -> 0 (cache disabled, pre-M21 `=0` behaviour), `1` -> 1 (the pre-M21 default, exactly), `all` or `2` -> 2 (pre-M21 mode 2, exactly), `wide` or `3` -> 3. Pre-M21, unset meant mode 1; that is the one intentional default change, and `=1` restores it.
- **Admission gate.** Modes 1/2 are unchanged (per-side limit 8 or 16, depth-only in mode 1). Mode 3 admits a direction-1 transfer when both sides are non-zero, the format has a known bits-per-pixel in the existing table, and **`rrw * rrh <= 64` pixels total in any shape** — 8x8, 16x4, 64x1, 1x64 all qualify, for depth and colour formats alike. Formats outside the bits-per-pixel table (their size cannot be computed at this layer) stay synchronous in every mode, as before.
- **Position-exact key (mode 3).** `ReadbackKey` gains the transfer's source position: `{sbp, sbw, spsm, ssax, ssay, rrw, rrh}`. Modes 1/2 store `0,0` for the position components, so their keys — and therefore their hit behaviour — are bit-for-bit the pre-M21 ones (the position-blindness there is deliberate, tuned to a flare that moves with the camera). In mode 3 the real ssax/ssay are stored, on both the capture (miss) side and the refresh side, so a cached entry can only ever serve the exact page, format, position and shape it was captured from. Correctness over hit rate: a game that reads the same page at two positions gets two entries and two first-read drains, never each other's bytes.
- **Per-transfer log.** `BeginTransfer` prints one line per local->host transfer (see section 5 for the format), classified `sync` (not admitted, or cache disabled), `async-miss` (admitted, first read of this key: runs synchronously once and is captured into the cache as the guest consumes it) or `async-hit` (admitted, served from the cache; a refresh is queued). The line carries the running hit/miss counters, which were previously counted in `g_readback` but never printed anywhere.
- **Untouched in this file:** the serve/capture/refresh mechanics themselves, the refresher's GPU/PCSX2/plain-backend fallbacks, `ConsumeLocalToHostBytes`, and the save-state reset hook (`ps2xGsResetAsyncReadback` still drops any in-flight serve/capture on load; the cache content itself survives, as before).

### 2.2 The kill switch on the phone (`godhand-recomp/src/main.cpp`)

One `kIniSettings` row, `{"video", "asyncreadback", "PS2X_GS_ASYNC_READBACK"}`, next to M20's `renderscale` row: `asyncreadback=off` under `[video]` in `godhand.ini` disables the cache on the phone (a real environment variable of the same name still wins, per the usual precedence). The Android shell does not set this variable, so the ini value reaches the backend unimpeded — without the row, the kill switch would exist in the binary but be unreachable on the device, which is not a kill switch.

### 2.3 Untouched

`gs_gpu_backend.cpp` in its entirety — the sync `readData`/`localToHostTransfer` semantics for reads that remain synchronous, the `[l2h]` classifier and stage split, `BeginDownloadAsync`/`pollDownloads` and the four Download slots, block shading (M20), the upload dedup (M19), present, readbacks of every other class; `gs_frontend.cpp` (its `PS2X_GS_DOWNLOAD_LOG` already exists for profile runs); the CPU and PCSX2 backends' behaviour (the gate lives in the shared threaded wrapper, as it always has); the compiled VU1 programs and registry; capture, still armed exactly as before.

## 3. The correctness invariant, and the honest risk

The load-bearing invariant, from the exploration, stated exactly: *bytes served for a local->host transfer must be the bytes the source region holds at the transfer's point in the GS command stream — after every write ordered before the transfer that touches the source pages, and before any write ordered after it.* The async cache **deliberately relaxes** this to "the previous transfer's bytes for the same key", and 0.22 does not loosen it further:

- A refresh is enqueued in stream order at the hit transfer's own queue point and reads through the fence-based async download, so refreshed bytes are the region's state as of that point — never anything written after it. Served bytes are therefore always **older than or equal to** the transfer's stream point, by at most one transfer of the same key. Nothing in the widening changes *which* bytes a hit serves; it changes only *which transfers are eligible* to be served that way and adds the position to the identity of "the same read".
- The first read of any key is a miss: synchronous, exact, and captured. No cache design removes the fight-entry drain; the win is over the remaining ~14-19 reads per window.
- The residual risk is the consumer, and it is genuinely unknown for God Hand: if these reads are a sampling test whose answer changes slowly (the Urban Reign flare pattern), one-transfer-late bytes are invisible. If they feed same-frame game logic — an effect trigger, a visibility or hit decision — last transfer's pixels can change behaviour subtly and intermittently: an effect firing a frame late or from a stale sample, a decision taken on where something *was*. That is worse than the stall if it happens, and it is exactly what the device test must watch for (section 6). What the reads are (which page, which format, whether the position is stable or roaming) will be plain in the first 0.22 log's `[l2h-path]` lines, which is most of the evidence the weighing needs.

## 4. Gate logic, before and after

| | Pre-M21 default (unset = mode 1) | Mode 2 (`=all`) | **Mode 3 (0.22 default)** |
|---|---|---|---|
| Formats admitted | depth only (Z32/Z24/Z16/Z16S) | depth + colour | depth + colour |
| Shape admitted | each side <= 8 | each side <= 16 | **total <= 64 px, any shape** |
| 64x1 colour strip | sync | sync | **async** |
| 16x4 depth block | sync | async | **async** |
| 8x8 depth block | async | async | async |
| Cache key position | not in key | not in key | **ssax/ssay in key** |
| First read of a key | sync + capture | sync + capture | sync + capture |
| Served bytes on a hit | previous transfer's | previous transfer's | previous transfer's (same position) |

Kill switches: `PS2X_GS_ASYNC_READBACK=off` (or `asyncreadback=off` in `godhand.ini`) -> mode 0, no admission, every read synchronous and exact — the strongest form. `=1` -> the pre-M21 default gates and key, bit-for-bit.

## 5. Log markers — what the next boot log must show

One new line per local->host transfer, printed by the threaded backend in the `[l2h]` family (field order mirrors the existing `[gs-download]`):

```
[l2h-path] mode=3 sbp=0x2fc0 sbw=64 spsm=0x31 pos=120,88 size=64x1 async-hit hits=41 misses=3
```

- `mode=3` on the fight reads proves the widened default is the running configuration. `mode=1` or `mode=0` in the log means an ini/env override reached the backend and the run says nothing about M21's gate.
- The fight reads should appear as one `async-miss` per distinct (page, format, position, shape) followed by `async-hit` lines with the hit counter climbing through the fight. A fight full of `async-miss` with the miss counter climbing means the keys are not repeating (roaming positions or pages) and the milestone's premise fails on evidence, in the log, without guesswork. Fight reads still printing `sync` in mode 3 means they fall outside admission after all (over 64 px, or a format outside the bits-per-pixel table) — the same line shows which.
- Cross-checks in the existing lines: the `[gs-work]` window totals count refresh reads under `l2h async` (they run through `BeginDownloadAsync`), and the `[l2h]` sync stage line should shrink towards the fight-entry reads only — its `rendered n=` count and mapread ms are the before/after measure, alongside fields/s, fences and presents, as always. Judge the milestone on those, not on the path labels alone.

## 7. Owner test

Install 0.22-m21 over 0.21 (same signer, in-place upgrade; ISO and settings carry over). Same settings (GPU on, threads off), same short route: title ~20 s, village ~1 min, one real fight ~1 min, then share the boot log and the vu-capture folder. Three things to report:

1. **The fight FPS label** — with the readback drains out of the EE thread's way, does the fight move, and does it feel different?
2. **Anything that behaves wrong in the fight** — above all effects, flashes or enemy reactions that look a frame late, fire when they should not, or fail to fire (the section-3 risk). Screenshot or describe it; that observation outranks the FPS number.
3. **The boot log itself** — the `[l2h-path]` lines in it are the verdict on the gate: mode, profile and hit rate, no interpretation needed from the phone side.

To A/B the cache off without reinstalling: add `asyncreadback=off` under `[video]` in `godhand.ini` (or set `PS2X_GS_ASYNC_READBACK=off` in the environment) and relaunch — every `[l2h-path]` line flips to `sync` and every read is exact and synchronous, exactly 0.21's behaviour. `asyncreadback=1` instead restores the pre-M21 gate (depth formats up to 8x8 only) if the widened admission itself ever needs isolating from the position-key change.
