# God Hand Android — Milestone 3: a real file for the disc (0.4-m3)

Date: 2026-11-02. Follows M2C.md. Trigger: the owner's on-device test of
0.3-m2c on his POCO F5 — the first boot where the native side spoke.
The ladder is now complete up to the disc itself:

```
launcher opened (0.3-m2c) → iso picked and stored → start pressed, iso=set
→ iso fd opened: /proc/self/fd/187
→ native: JNI_OnLoad - libgodhand.so loaded
→ native: main() entered (android_main thread, 0.3-m2c)
→ ===== godhand android 0.3-m2c boot =====
→ native: calling godhand_port_main now
→ [BOOT] settings: ... (godhand.ini + controls.ini written, 120 s limit)
→ [BOOT] disc image: /proc/self/fd/187
→ [CDIMAGE] cannot open /proc/self/fd/187
→ [BOOT] ERROR cannot mount /proc/self/fd/187 as an ISO9660 disc image
→ native: godhand_port_main returned 3
```

## 1. The dead end: the borrowed descriptor

The whole 2c ladder works — the shell, the JNI bridge, main(), the
port's own settings stage all run on the phone. The boot stops at the
one thing that was always a loan, not a file: the port is handed
`/proc/self/fd/187`, a magic symlink to the picker descriptor held open
by the Java side. The port's CD layer (PS2CdImage::open) needs to
fopen() that path, size it via the filesystem, and fseeko() around it;
somewhere in that sequence the borrowed path fails (the 0.3 log names
no errno — the [CDIMAGE] line printed only the path). Rather than
theorise about which call chokes on a pipe-like descriptor, this
milestone removes the loan: the port gets a real file with a real
path, the same shape it mounts happily on desktop.

## 2. What 0.4-m3 changes

Shell — the ISO copy (android/shell/src/dev/ptraaa/godhand/):

- `LauncherActivity` now copies the picked ISO once into the app's
  internal files dir: `getFilesDir()/godhand.iso` (on the phone that is
  `/data/data/dev.ptraaa.godhand/files/godhand.iso` — the port's own
  working directory, where it already writes godhand.ini/controls.ini).
  The copy runs on a background thread through a `godhand.iso.tmp`
  file renamed into place only when complete, so an interrupted copy
  never looks finished.
- When it runs: on pick (immediately, so the copy is usually done
  before he ever taps Start) and on Start whenever the copy is missing
  or stale; a Start that arrives during a copy is latched and the game
  launches itself when the copy lands. Pick and Start are disabled
  while a copy runs.
- Progress is on the status line, refreshed every 16 MB:
  "Copying the ISO into the app (one time): N of 1536 MB (P%). Leave
  the app open." Start / done / failure each also append a line to
  godhand-boot.log.
- Reuse key (size-keyed, per the brief): the copy is reused when
  godhand.iso's length equals the recorded length of the completed
  copy AND that copy was made from the currently picked document AND
  that length still equals the provider-reported document size
  (OpenableColumns.SIZE, with the descriptor's stat size as fallback;
  when a provider reports no size, the uri+copy-length record is what
  carries the check). Picking a different ISO therefore replaces the
  copy even at the same size; re-picking the same ISO copies nothing.
- Failure handling: a free-space pre-check against the document size
  fails early with the numbers on the status line and in the log;
  a mid-copy failure deletes the partial .tmp, logs
  "iso copy FAILED after N bytes: <exception>", puts the same text on
  the status line, and leaves the app alive for another tap. Nothing
  in the copy path can crash the shell.

- `GameActivity` fills the new IsoHolder field before loadLibrary:
  if godhand.iso exists it logs "iso copy present: <path> (<N> bytes)
  - the port gets the real file" and the glue hands the port that
  path. The provider fd is still opened and held — now purely as the
  fallback for a run where the copy is missing ("iso copy missing -
  the port falls back to the picker fd").
- `IsoHolder` gains `isoFilePath` (field + accessor, same pattern as
  the existing bridge entries).

Glue (android/glue/godhand_android_main.cpp):

- Caches the new `isoFilePath()` method in JNI_OnLoad and resolves
  --iso in main() as: the real copy path first, the /proc/self/fd
  path only if the copy path comes back empty. The banner now prints
  both `iso: <path>` and `iso source: app copy (real file)` /
  `picker fd (fallback)`, so the next log states which world it is in
  without inference. The iso argv buffer grows 64 → 512 bytes.
- Version strings bumped to 0.4-m3 (banner, main()-entered line).

Port (runtime/ps2xRuntime/src/lib/ps2_cd_image.cpp):

- The one remaining mute failure gets a voice: when fopen() fails,
  PS2CdImage::open now prints
  `[CDIMAGE] cannot open <path>: <strerror> (errno <n>)` (errno
  captured immediately at the failure). If anything still goes wrong
  at the disc — a bad path, a permissions change, a truncated copy —
  the log names the reason instead of leaving another riddle. The
  port's successful-mount line ("[CDIMAGE] mounted <path> (<N>
  entries)") and the [BOOT] SYSTEM.CNF / boot-ELF lines already exist
  and keep flowing to godhand-boot.log unchanged.

Unchanged: package dev.ptraaa.godhand, same debug keystore, headless
boot, 120 s time limit, CPU rasteriser default, ISO prefetch off, no
touch input yet. The owner's 0.3 ISO preference survives the update
(same SharedPreferences); the first 0.4 launch performs the one-time
copy when he taps Start.

## 4. How to read the next boot log

Same ladder as M2C §5, with the disc section replaced:

1. "launcher opened (0.4-m3)", then on first launch after a pick or
   after this update: "iso copy started: ..." and, a while later,
   "iso copy done: godhand.iso is <N> bytes - the port now gets the
   real file". A "iso copy FAILED ..." line instead names its reason
   on the spot (space, provider stream, size mismatch).
2. "iso copy up to date (<N> bytes) - no copy needed" on later runs.
3. GameActivity: "iso copy present: /data/data/.../files/godhand.iso
   (<N> bytes) - the port gets the real file". ("iso copy missing"
   here would mean the launcher copy vanished between the two
   activities — the fd fallback then applies, and the banner's
   "iso source" line says so.)
4. Banner: "iso: /data/data/dev.ptraaa.godhand/files/godhand.iso" +
   "iso source: app copy (real file)".
5. The port: "[BOOT] disc image: /data/data/.../godhand.iso", then
   the success marker for this milestone:
   "[CDIMAGE] mounted <path> (<N> entries)" and the [BOOT] lines for
   SYSTEM.CNF, the disc files and the boot ELF's SHA-256. Wherever
   the port stops AFTER a successful mount is the next frontier —
   per this milestone's scope it is the report, not a failure.
   A remaining mount failure now prints its errno inline.

## 5. Owner test steps

1. Install package/godhand-android.apk — it updates the existing app
   in place (same signer); no uninstall, the picked ISO is kept.
2. Open "God Hand (recompiled)" — title now reads 0.4-m3. The status
   line says the ISO is picked but not yet copied.
3. Tap "2. Start the game". First time only: the ISO is copied into
   the app — the status line counts up in MB. It is ~1.5 GB, so this
   can take a while; leave the app open and the phone alone until
   the copy finishes. The game then starts by itself. (Later starts
   skip the copy entirely.)
4. Leave the game up to ~2 minutes; the app closing itself when a
   boot ends is expected. Nothing on screen is still normal — this
   build is headless by design.
5. Reopen the app, tap "Share boot log", send the log back in chat.
   (The file also lives at
   Android/data/dev.ptraaa.godhand/files/godhand-boot.log.)
6. Worth sending too: roughly how long the copy took, and whether
   the game screen showed anything new (a logo, text, a picture —
   or still black).

One space note: the app will now hold ~1.5 GB more than before (the
ISO copy), on top of the ISO he already keeps in Downloads. That is
the expected price of giving the port a real file; the copy can be
reclaimed later by clearing the app's data once a leaner disc path
exists.
