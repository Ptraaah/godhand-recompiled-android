# Milestone 12 — past the function-table wall (0.13-m12)

The owner's 0.12-m11 run (2026-11-02 11:12 WITA, log
godhand-boot_2_96w6.log, last session, `gpu=on`) got a full stage
further than 0.11 and hit a new wall, exactly one diagnostic
deep:

```
renderer: gpu (owner setting)
[gs-gpu] missing GL functions: glGetBufferSubData, glGetQueryObjectui64v, glQueryCounter
```

and then nothing — no `EGL context created` line, no shader
compile summary — while the app ran at full speed with an empty
picture (`[frame-split] presents=284 avg 17.6 ms, gs-fetch
0.45 ms (3%), sync 92%`; his screenshot shows 57 FPS / worst
48 ms over a fully black screen, touch overlay alive). This
build resolves the three functions for OpenGL ES, and makes
every init failure name itself, so the next wall — if there is
one — arrives pre-diagnosed. With the toggle OFF nothing here
runs: the glue still delivers env `"0"`, the GPU backend is
never constructed, and the default run is the 0.12 run.

## 1. The traced control flow (why one line was the whole log)

`Impl::ensure()` (gs_gpu_backend.cpp) is the only caller of
`GSGL::Context::Create`. On the Android branch of `Create`
(gs_gl.cpp), execution went:

1. `eglGetDisplay` / `eglInitialize` / `eglChooseConfig` /
   `eglCreateContext` (3.2 attribs) / 1×1 pbuffer /
   `eglMakeCurrent` — **all succeeded**. (Any failure in this
   block returns its own error string; none appeared.)
2. The `Api` table fill via `eglGetProcAddress`: every core ES
   3.0–3.2 name resolved. Exactly three did not:
   `glGetBufferSubData` (not an ES function at all),
   `glGetQueryObjectui64v` and `glQueryCounter` (desktop names;
   ES exposes timer queries only as the `EXT`-suffixed entry
   points of `GL_EXT_disjoint_timer_query`). The three names
   accumulated into the loader's `missing` list.
3. `glClearBufferData` and `glBufferStorage` were resolved
   (shim / EXT) as in M11 — then the missing check fired:
   `error = "missing GL functions: ..."`, `Destroy()` tore the
   fresh EGL context down, `return false`.
4. **The two chain lines that never printed live after that
   check.** The `EGL context created` line is printed at the
   *end* of a successful `Create`, after the missing check and
   the ES 3.2 version gate; the renderer/version line and the
   shader compile summary are in `ensure()`, after `Create`
   returns. The abort sits before all three.
5. `ensure()` printed the error as `[gs-gpu] <error>` (the one
   line the owner saw), latched `failed = true`, and returns
   false on every later call. Every backend entry point —
   `Present` included — early-outs on `!ensure()`, so
   `Present()` returns a default-constructed (empty)
   `PresentationFrame` forever. That is the whole black screen:
   same outward shape as the 0.11 stub, one stage deeper in,
   cause completely different.

So the warning was not advisory: in this loader, *any* missing
core-listed name is fatal to context creation, and the three
names are simply not exported by any ES driver under those
spellings.

## 2. The three functions: call-site audit and resolution

All call sites are in gs_gpu_backend.cpp; all run on the GS
worker thread with the backend context current (every backend
call funnels through `GSThreadedBackend::RunOnWorker`, M11 §1).

### glGetBufferSubData — real data path; real shim

| Site | Caller | What it reads |
|---|---|---|
| 1740 | `dumpPlaneSnapshot()` | whole VRAM buffer, debug only (`PS2X_GS_PLANE_DUMP`, scale > 1) |
| 1787 | `downloadVram()` | VRAM → host: the GIF local-to-host transfer path |
| 1795 | `readData()` | present data buffer: the synchronous `Present()` readback |
| 3079 | `harvest()` | an async-present slot buffer, **only** when that slot's persistent map failed |
| 3212 | `readClut()` | 1 KB of the CLUT buffer back to the host |

This one is correctness-critical (frames, VRAM downloads, CLUT
readback), so a zero/empty stub was never an option. The shim
`esGetBufferSubData` (gs_gl.cpp, Android branch) honours the
desktop contract — read the buffer currently bound to the
target, at offset, size bytes — via
`glMapBufferRange(GL_MAP_READ_BIT)` + `memcpy` +
`glUnmapBuffer`, all core ES 3.0. Contract checks against the
call sites: each binds its buffer to the target immediately
before the call; none targets a buffer that is persistently
mapped at call time (the upload ring is never read back, and
`harvest()` reaches the shim only for slots whose persistent
map already failed, i.e. unmapped buffers), so the transient
map cannot collide with an existing mapping. If a map ever
fails anyway, the shim zeroes the destination and prints one
`[gs-gpu] failed:` line once — a stale frame must never
masquerade as a fresh one.

### glQueryCounter — telemetry only; EXT binding, zero shim behind it

Two call sites, `profBegin()` (577) and `profEnd()` (586),
both inside the GPU profiler and both gated on `prof.enabled`,
which is set only from the env vars `PS2X_GS_GPU_PROFILE` /
`PS2X_GS_GPU_PROF` in the `Impl` constructor. The glue sets
neither; profiling is off in every shipped configuration.

### glGetQueryObjectui64v — telemetry only; EXT binding, zero shim behind it

Four call sites: three in `profResolve()` (614, 627, 628 —
the same opt-in profiler: availability poll + interval reads
feeding pass-time statistics and reports) and one in
`harvest()` (3058), which reads a `GL_TIME_ELAPSED` result
into `presentStats.gpuNs`. That read only happens for slots
whose `slot.query` was set, which only happens when
`presentStats.enabled` — set only from `PS2X_GS_GPU_STATS`,
also unset by the glue. No rendering decision anywhere reads a
query value: the consumers accumulate timings for reports, and
`harvest()`'s frame delivery is fenced on the slot's sync
object, not on the query.

### The resolution (gs_gl.cpp, Android table fill only)

The three `loadEs` calls are gone from the strict list, so the
names can no longer enter `missing`. In their place, after the
extension string is fetched (the same spot that resolves
`glBufferStorageEXT`), each entry resolves **core name →
EXT name → registered shim**:

- `glGetBufferSubData`: core name tried (never exists on ES),
  then bound directly to the map shim — there is no EXT form.
- `glQueryCounter` / `glGetQueryObjectui64v`: the EXT entry
  points (`glQueryCounterEXT` / `glGetQueryObjectui64vEXT`)
  are bound **only when `GL_EXT_disjoint_timer_query` is in
  the advertised extension string** — an `eglGetProcAddress`
  hit for an unadvertised extension is not trusted, the same
  discipline M11 applied to `glBufferStorageEXT`. If the
  extension is absent (or a proc is missing despite it), the
  zero shims are registered: `QueryCounter` is a no-op and
  `GetQueryObjectui64v` writes 0, with `GL_QUERY_RESULT_AVAILABLE`
  returning 1 — the profiler's availability poll then resolves
  immediately with zero-length intervals instead of waiting
  forever on results that can never arrive. (Adreno 7xx
  advertises the extension, so the owner's device is expected
  to take the real EXT route; the boot line below says which.)

One line at the end of the fill names the routes taken:

```
[gs-gpu] ES entry points: glGetBufferSubData = map shim (no ES entry point exists); timer queries = GL_EXT_disjoint_timer_query (glQueryCounterEXT / glGetQueryObjectui64vEXT)
```

(the timer half reads `zero shim (GL_EXT_disjoint_timer_query absent)`
on a device without the extension). Windows and the generic
stub are untouched; the CPU backend is untouched.

## 3. Failure is loud now

Every init latch in the GPU backend prints
`[gs-gpu] failed: <specific reason>`:

- `ensure()`, context creation failed:
  `[gs-gpu] failed: <Create's error string>` — e.g. a future
  missing list, an EGL failure, or the ES 3.2 gate now arrive
  with the prefix. (This replaces the bare `[gs-gpu] <error>`
  print; success-path lines are unchanged.)
- `ensure()`, shader chain failed:
  `[gs-gpu] failed: one or more shaders did not compile (info logs above); GPU backend disabled`
  (the per-shader info-log dumps and the compile summary still
  print above it — they were already loud; the latch was not).
- The `esGetBufferSubData` map failure (one-shot):
  `[gs-gpu] failed: glGetBufferSubData shim could not map the readback buffer; readbacks return zeros`.

These are the only two `failed = true` latch sites in the
backend (grep-verified), and `Present()`'s empty-frame
behaviour only ever follows an `ensure()` failure, so there is
no remaining silent route to a black screen from init.

## 4. Second-wall scan (what runs right after Create now succeeds)

Audited, no second wall of the same class found:

- Rest of `ensure()`: `GetString` renderer/version,
  `GetInteger64v(GL_MAX_SHADER_STORAGE_BLOCK_SIZE)`, the
  `makeBuffer` set — all core ES entry points, all in the
  table. The upload ring's `BufferStorage` +
  persistent `MapBufferRange`: `GL_EXT_buffer_storage` on the
  owner's device class, with M11's honest fallbacks (staged
  uploads; `presentAsync`'s guarded readback) behind it.
- Shader chain: unchanged sources, unchanged runtime
  translation; §5 re-validates 9/9. The one thing no host tool
  can see is the device driver's own compiler — if it rejects
  a shader, the info log + summary + the new `failed:` line
  name it. That wall, if it exists, is already loud.
- `presentAsync` readback: slot buffers via `BufferStorage`
  (EXT route on Adreno) with persistent maps; `harvest()`
  copies from the map, or — M11's fallback — through the new
  `glGetBufferSubData` shim after the slot's fence. The sync
  present path's `readData()` is the same shim.
- Downloads: `beginDownloadAsync` maps-or-returns-false, and
  false takes the synchronous `downloadVram()` path — through
  the shim. `pollDownloads` only dereferences `slot.mapped`
  for slots whose fence was set, which only happens after a
  successful map.
- One adjacent note, not a wall: `GL_TIME_ELAPSED` queries
  (`BeginQuery`/`EndQuery` are core ES 3.0, and both load
  fine) are only *accepted* by ES drivers with
  `GL_EXT_disjoint_timer_query`. They are issued only under
  `PS2X_GS_GPU_STATS`, which the glue never sets; if someone
  sets it on an extension-less device, only the stats line
  degrades — the frame path does not touch queries.

The remaining named unknowns are M11's, unchanged: the SSBO
numbers on the `EGL context created` line (bindings 0–9 used
at scale 1 vs the ES guaranteed 8) are the first thing to read
if the picture is broken *with* a live context and 9/9 shaders.

## Owner steps

1. Install 0.13-m12 over 0.12 (same signer, update in place,
   ISO copy reused). Leave every setting as it is except the
   one below.
2. In the launcher, **GPU renderer (experimental)** ON. START,
   go toward the PRESS START title, sit a full minute, note
   **what the screen does**, then exit and **Share boot log**.
3. The success chain in the log, in order:
   - `renderer: gpu (owner setting)`
   - `[gs-gpu] ES entry points: glGetBufferSubData = map shim ...; timer queries = GL_EXT_disjoint_timer_query (...)`
     — the old `missing GL functions:` line is **gone** (if a
     `missing GL functions` text ever appears again, it now
     arrives as `[gs-gpu] failed: missing GL functions: ...`
     and names the next wall verbatim)
   - `[gs-gpu] EGL context created: OpenGL ES 3.2 ... | max SSBO bindings <N>, max SSBO block <M> bytes, EXT_buffer_storage yes`
     — read the two SSBO numbers first if the picture is wrong
   - `[gs-gpu] <renderer> / <version>`
   - `[gs-gpu] shader compile summary: 9 compiled, 0 failed`
   - `[frame-split]` windows with real GPU gs-fetch numbers,
     against the CPU title's 679–1257 ms and the stub/empty
     runs' ~17 ms.
4. Reading the result:
   - **A real picture** (even wrong colours, torn, or slow) =
     the renderer drew through the readback: first light,
     round two. The `[frame-split]` title windows price it.
   - **Black screen** = find the `[gs-gpu] failed:` line; it
     names the wall. No such line + a context line + 9/9
     shaders + black screen points at the SSBO numbers on the
     context line — send the log either way.
   - A crash is also a result: the log up to the crash plus
     where it stopped is the evidence.
5. Toggle OFF afterwards returns the exact 0.12 behaviour —
   same env value, GPU backend never constructed.
