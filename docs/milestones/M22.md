# God Hand Android — Milestone 22 (0.23-m22): ARUS pillar 4 — the field gate, and the ARUS master switch

Across 0.18-0.22 the same constant survived every fix: depth. M19 proved the present path is already decoupled and already serves the newest *retired* frame; M20 cut the raster stream by an order of magnitude and the fight still presented at swap pace; M21 removed the synchronous readback drains from the EE thread's way. The exploration for this milestone (`m22-explore.md`) found where the remaining seconds live, and it is not in any bucket: **nothing in the system ever compared fields produced with fields retired by the GPU.** The guest and the worker submit into a single GL stream whose only retirement-coupled throttle was the upload ring's wrap fence — one fence per 48 MB of stream, which at fight rates (~0.7-2.7 MB of stream per field) is **25-70 fields of in-flight GPU work**. The screen faithfully showed the newest retired image; retirement was seconds behind submission. 0.23 bounds the depth where it is created: at submission, on the worker, in stream order, denominated in fields. It drops no GS work and skips no `Present()` calls.

This build also gives the four mechanisms their collective name and their one switch. The system is **ARUS** (Indonesian: flow, current): an adaptive GS pipeline for recompiled PS2 games on mobile GPUs, standing on one diagnosis — the classic PS2 GS pipeline assumes a fixed-function chip wired straight to its memory with zero latency, while a mobile GPU is a queued, high-latency machine, and every stall measured in M17-M21 is that assumption breaking. Pillar 1 is the upload dedup (0.20), pillar 2 the 2x2 block shading (0.21), pillar 3 the async readbacks (0.22), pillar 4 the field gate below. 0.23 is the ARUS 1.0 release: the first build in which all four ship together under one master switch, `arus` in godhand.ini. The public write-up is `ARUS.md`. Note, plainly: 0.22 has no device verdict yet; 0.23 is the release the owner tests as a whole system, and the instrumentation added here exists so that test can judge the system, not a feeling.

The short version: the threaded wrapper now enqueues one zero-payload mark (`Op::FieldGate`) per guest field; when the worker executes a mark, the GPU backend fences the field just ended into a three-slot ring and, once two fields are ahead, waits for the oldest fence to retire — ringPut's own wait shape, counted in the same `[gs-work]` fence bucket. Submitted-but-unretired work is thereby bounded to **K = 2 fields**. `Present()` also threads the latch's `vsyncTick` into the readback slots, so the stats lines now print the returned frame's **age in fields** (pre-gate: 25-70 in fights; the bound promises at most K + 1 = 3). And `main()` gains the ARUS master switch: `arus=off` rewrites the four pillar variables to their pre-ARUS values before any back end is constructed, except any pillar variable set explicitly in the real environment, which keeps its value.

## 1. Why this shape (the exploration's verdict, compressed)

- **Freshest-field presentation needed no building — it already ships.** A presentation request is synthesised from the live DISPFB/DISPLAY registers at latch time; fields the guest advances during one swap block are never composited at all, and the readback ring's slot-busy path already re-serves the newest harvested frame. Presentation is a read-only copy chain out of VRAM (composite -> slot -> host pixels -> texture); the guest's framebuffers, flip copies, feedback effects and readbacks never pass through it, so dropping *presentations* is safe by construction — and useless, because the composite still has to retire through the same deep queue before it can be the newest *retired* frame.
- **The bound had to be in fields.** Fields are the unit the guest paces in and the unit `[gs-work]` counts — and after pillars 1-3 shrank a field's byte size unevenly by scene, a byte bound's depth in fields varies ~3x between an upload-heavy menu window and a prim-heavy fight window. At the default K = 2, expected in-flight latency is ~20-40 ms at 0.21's fight rates (~100 ms at 0.20's), against 2.0-4.3 s today; and the bound self-scales as later work shrinks per-field cost, with no retuning.
- **The bound had to live on the worker, at the field mark, in stream order** — the only point upstream of every retirement consumer (ring wrap fences, sync readbacks, download fences, the composite, and transitively the host swap). The producer queue (64 op chunks) bounds unexecuted ops, not submitted-unretired GPU work; the present path is downstream of the depth entirely (M19 §3 convicted that family).
- **M19's objection, answered head-on.** M19 ruled that bounding frames-in-flight "could only help by deleting queued GS work, and that is unsafe". It was right about deleting, and this design deletes none. But a producer that submits faster than the GPU retires, forever, with nothing dropped and its run-ahead untouched, accumulates unbounded latency by definition — no sound design satisfies all three. Pillar 4 gives up the third: the producer's run-ahead becomes bounded by the *same* mechanism that already bounds it today (the op queue's `PublishLocked` wait, which M19 measured the guest already paying 90-168 ms on average in fights). The gate itself executes on the worker; no guest thread gains a new blocking call. What changes is only which queue is deep: the GPU's backlog, bounded today by 48 MB of ring, becomes bounded by 2 fields.
- **Rejected placements**, for the record: a smaller upload ring (wrong unit, and even 16 MB of lookback is ~8-25 fields at fight rates); a smaller producer chunk limit (bounds the wrong queue — the worker would still drain it into the GL stream as fast as it decodes); capping or skipping `Present()` calls (downstream of the depth, and `Present()` is also a flush point, so skipping calls would defer draws and corrupt `[gs-work]` attribution).

## 2. What 0.23-m22 changes

Three files in the shipped tree (`godhand-recomp/runtime/ps2xRuntime` and `godhand-recomp/src`), plus the manifest version. No shader changes, no frontend or host-loop changes.

### 2.1 The field mark (`src/lib/gs/gs_threaded_backend.cpp` + its header)

- **The worker had no in-stream field boundary.** `GSGpuBackend` does not override `VSync()`, and for the shipped (non-raw-GIF) path `GS::vblank()` returns before the VSync op would fire (the M14 comment in gs_frontend.cpp) — fields reached the worker only as the EE-thread atomic `fieldTotal`, useless for stream-order gating. So the mark is new machinery, built from the codebase's own patterns.
- `GSThreadedBackend::NoteFieldBoundary()` — already called once per guest field from `GS::vblank()` on the EE thread, for every back end — now also `Enqueue(Op::FieldGate)`, a new zero-payload op appended at the end of the `Op` enumerator. Enqueue serialises on the producer mutex, the same lock the field's own draw submissions take, so the mark lands *approximately* at the field's end in the stream. Approximately is sufficient: the gate is a statistical depth bound, not a correctness boundary; a few of the next field's draws slipping ahead of the mark move the bound by a few draws, not a field.
- The constructor parses `PS2X_GS_QUEUE_DEPTH` once, like `m_queueChunkLimit`: when the gate is disabled (`off`/`0`) the marks are **not enqueued at all** and the op stream is the pre-M22 one record for record. Unset (the shipped default) enqueues them.
- In `WorkerLoop`'s dispatch, `Op::FieldGate` calls `GSGpuBackend::FieldGate()` through the same `dynamic_cast` pattern `Op::VSync` uses for `NoteFieldBoundary` — no virtual added to the header chain (the M14 constraint), and CPU/PCSX2 inners see a no-op. The call is skipped while a stop is being requested (read under the queue mutex): the gate must never delay shutdown.

### 2.2 The gate (`src/lib/gs/gpu/gs_gpu_backend.cpp` + its header)

- `GSGpuBackend::FieldGate()` is a plain public method beside `NoteFieldBoundary()`. With the gate off it returns before any GL work; otherwise it takes the usual outermost-call busy timer, ensures the back end, and delegates to `Impl::fieldGate()`.
- `Impl::fieldGate()` keeps a fence ring of `queueDepth + 1` slots (three at the shipped depth) beside `ringFences`, sized in the constructor: at field mark N it deletes whatever stale fence occupies slot N (in the normal flow it was already waited on and deleted; the branch is belt-and-braces), places `glFenceSync` for the field just ended — enqueued after everything the mark followed, so it stands for all of that field's submitted work — and, once `queueDepth` fields are ahead, `ClientWaitSync`s field N−depth's fence with `kSyncFlushCommandsBit` and a 5 s timeout, proceeding on timeout. The wait is added to `work.fenceCount`/`work.fenceMs`, so `[gs-work]` attributes it exactly like a ring-wrap wait. A wedged fence degrades the bound; it cannot hang the worker (and with it every `Drain` caller, including save-state load).
- **Parse.** `PS2X_GS_QUEUE_DEPTH` beside the other `Impl` constructor parses: unset -> 2 (on, in this build); `off` or `0` -> disabled; a positive value -> that depth in fields (clamped to 64; the ring grows with it). The ini row is `{"video", "queuedepth", "PS2X_GS_QUEUE_DEPTH"}` in `godhand-recomp/src/main.cpp`, so `queuedepth=off` in godhand.ini reaches it on the phone — the M21 lesson.
- **Boot log.** `ensure()` prints one line either way, in the `[gs-gpu]` style:
  - on: `[gs-gpu] queue depth gate on: submitted work bounded to 2 fields in flight (PS2X_GS_QUEUE_DEPTH=off turns it off)`
  - off: `[gs-gpu] queue depth gate off: submission unpaced, retirement bounded only by the upload ring`
- **Reset hygiene.** Outstanding field fences are pure runtime objects; `GSGpuBackend::Reset()` (guarded on the back end being initialised) and `ImportState()` drop them without waiting and restart the field count, alongside the flush both already do — a state loaded into a shallow queue must not inherit fences from the old one. The destructor deletes any still outstanding.
- The gate acts only at field marks, never mid-field; it cannot produce a half-submitted field. Guest readbacks observe exactly the same bytes as today — they are in-stream and wait for their own position — only sooner after their stream point, because the queue ahead of them is now at most 2 fields deep (M21's drains shrink from ~175-285 ms of queue to ≤ K fields of queue).

### 2.3 Present age (both stats windows)

- `GSGpuBackend::Present()` passes `request.vsyncTick` — present in the request since forever, ignored by this back end until now — into `presentAsync()`, which stores it on the readback slot at copy time; `harvest()` carries it into `lastFrameTick` when it adopts a newer frame. At every return, `presentAsync()` records the returned frame's age (latch tick − frame tick) into both stats windows.
- `reportPresentStats()` prints it (`present age %.1f/%llu fields`, mean/max) and resets it with its window, as the exploration prescribed. **One deliberate widening of the prescription:** the same accounting also feeds the `[gs-work]` window, whose line gains `| present age %.1f/%llu fields`. Reason: in the shipped phone configuration `PS2X_GS_GPU_STATS` is unset (zero `presents/s` lines in every owner boot log), so an age that lived only in `reportPresentStats()` would be invisible exactly where the milestone is judged — and the exploration's own §5.3 states the line exists to be the device verdict. Two independent accumulator sets, one per window, each reset by its own window: each line is self-consistent.
- Guard: no age is recorded before the first harvested frame, or when a tick predates the frame's tick (a reset boundary); the structural floor is the readback ring's one-present lag, which is why the bound promises K + 1 = 3, not K.

### 2.4 The ARUS master switch (`godhand-recomp/src/main.cpp`)

Entirely front-end, exactly as the exploration designed it — every pillar parses its variable at or after back-end construction, and back-end construction happens after `main()` applies settings, so rewriting the variables in between is sufficient and no back-end code knows ARUS exists.

- One ini row: `{"video", "arus", "PS2X_ARUS"}` beside `queuedepth` — `arus=off` under `[video]` in godhand.ini, or `PS2X_ARUS=off` in the environment.
- A snapshot in `main()` **before** `loadSettings()`: which of the four pillar variables are present in the real environment. (loadSettings itself already implements "real env wins over ini" per variable; the snapshot preserves that contract for the master switch.)
- `applyArusMasterSwitch()` runs immediately after `loadSettings()`, before the runtime is created. If `PS2X_ARUS` resolves to `off`/`0`, it forces — via the existing `setEnv()` — `PS2X_GS_UPLOAD_DEDUP=0`, `PS2X_GS_RENDER_SCALE=1`, `PS2X_GS_ASYNC_READBACK=1` (mode 1 was the shipped default in 0.19-0.21, so `1`, not `off`, is the exact pre-ARUS value; `off` remains the stronger per-pillar kill switch), `PS2X_GS_QUEUE_DEPTH=off` — **except** any pillar variable present in the real environment at snapshot time, which keeps its explicit value. Ini-set pillar values are not exempt: the ini is one file the user edits as a whole, so `arus=off` beside `renderscale=0.5` in the same file means the whole system off.
- One boot-log line either way, in the existing settings style, stating the effective pillar state after enforcement — e.g. `[BOOT] settings: ARUS on (PS2X_ARUS): pillars governed by their own switches PS2X_GS_UPLOAD_DEDUP=unset PS2X_GS_RENDER_SCALE=unset PS2X_GS_ASYNC_READBACK=unset PS2X_GS_QUEUE_DEPTH=unset`, or the `ARUS off` form listing the forced values and naming any variable kept from the environment. The pillars' own boot lines (block shading on/off, `[l2h-path] mode=`, the queue-gate line) then corroborate it in the same log, as they do today. The Android shell `setenv`s none of the four pillar variables, so enforcement ordering on the phone is the desktop's.

**Semantics, stated once:** ARUS off = the pre-ARUS build's behaviour (the 0.19/0.20 configuration: no dedup, native shading rate, readback mode 1 gates, no queue gate), restored by one setting. ARUS on (the default) = each pillar governed by its own switch, with the shipped defaults being the ARUS defaults (dedup on, block shading on, readback mode 3, depth 2). Setting an individual switch while ARUS is on works exactly as it did in M20-M22 — the A/B recipes are unchanged.

### 2.5 Untouched

All of pillars 1-3: the dedup and its invalidation, the LORES shader and its plumbing, the async readback admission/key/mechanics and the `[l2h-path]` line. The frontend, the host present loop, raylib, the shaders, the CPU and PCSX2 back ends' behaviour (for a PCSX2 inner the marks dispatch to a no-op; for a CPU inner the threaded wrapper is not in the path at all when threading is off, and when it is, the same no-op applies). The sync present path (`asyncPresentMode() == 0`) records no age — its frame is read back synchronously at its own latch, so the readback-slot accounting does not apply to it. The compiled VU1 programs and registry; capture, still armed exactly as before; all Android glue and shell code except the manifest version.

## 3. The bound, and how to judge this milestone

At any field boundary, at most 2 fields' worth of submitted work may be unretired: the field being submitted and one ahead of it retiring. At the 0.21 heavy fight window's rates (~10 ms/field submission, ~2.3 ms/field raster after block shading) that is ~20-40 ms of in-flight latency; at 0.20's rates (~51 ms/field) ~100 ms — against 2.0-4.3 s of fence waits per window in the 0.19/0.20 logs. The displayed image can never be newer than the newest retired composite, and a composite can only retire after the work ordered before it: pillar 4's promise is not "the current field, now", it is "the newest retired field, at most ~K fields behind the guest" instead of 25-70.

**The judging lines, named in advance** (the exploration's §4/§7 requirement, because M18's innocent barrier is what happens when a milestone is judged by the wrong line):

- `[frame-split]` **presents/s and worst frame** — these must improve; they are the player's experience denominated honestly.
- `[gs-work]` **fence ms** — the gate's waits land here, replacing ring-wrap waits; the total and its per-window shape are the cost side of the trade.
- `[gs-work]` (and `[gs-gpu]`, where enabled) **present age** — must read at most ~3 fields in fights. This is the milestone's verdict line: it is the depth, measured at the screen.
- `[l2h]` **drain times** — M21's sync-entry reads and any remaining sync reads should drain against ≤ 2 fields of queue, not seconds.

**And the line that must NOT be judged as a regression:** the EE-side `fields=` rate in `[gs-work]` will **fall toward the GPU's true retirement rate** in fights. That is arithmetic, not damage: fields "completed" into a seconds-deep queue were never completed in any sense the screen recognises — the guest was writing cheques the GPU cashed seconds later, and the FPS label's 1 FPS was the honest one all along. With the gate, `fields=` finally counts fields the display can actually be within 2 of. If presents/s, worst frame, fence ms and present age improve while fields/s falls to meet them, the milestone did exactly what it said.

## 4. Switches

| Switch | Values | Effect |
|---|---|---|
| `PS2X_ARUS` (ini `arus`) | unset/on (default), `off`/`0` | Master switch. Off forces all four pillars to their pre-ARUS values (environment-set pillar variables exempt). On changes nothing: each pillar's own switch rules. |
| `PS2X_GS_QUEUE_DEPTH` (ini `queuedepth`) | unset -> 2, positive integer, `off`/`0` | Pillar 4. Depth in fields of submitted-but-unretired work. Off: no marks enqueued, no fences placed — the pre-M22 path exactly. |
| `PS2X_GS_UPLOAD_DEDUP` | unset -> on, `0` | Pillar 1 (M19), unchanged. |
| `PS2X_GS_RENDER_SCALE` (ini `renderscale`) | unset -> on, `1` | Pillar 2 (M20), unchanged. |
| `PS2X_GS_ASYNC_READBACK` (ini `asyncreadback`) | unset -> mode 3, `1`, `2`/`all`, `off`/`0` | Pillar 3 (M21), unchanged. |

## 6. Known risks — what to look for on the phone

1. **The fields/s optics (the big one).** Section 3: judged by `fields=` alone, this build will look like a regression while every wait in the system improves. The owner test below names the lines to read instead.
2. **Menu/title phases.** Presents there already collapse for a different reason (upload volume, 76-110 MB per window through the same queue; the swap waits behind it). A 2-field gate does not reduce upload *bandwidth* — the GPU copies at its rate regardless of depth — so menus should neither gain nor lose materially. Two second-order effects to watch in the log: the latch's `Present` can now execute behind a gate wait, moving a bounded slice of time from the swap bucket into gs-fetch in `[frame-split]` (same total, different label — the M19 bucket-attribution trap in miniature); and during long streaming loads the gate serialises the worker against retirement more tightly, so a pathological upload burst could stretch a load screen by the depth it removes. If the second shows up, the escape is a larger K during high-upload windows — deliberately not built speculatively; measure first.
3. **Fence churn.** Three extra fence cycles per field at the default depth is well inside the load the ring already imposes (a fence per 16 MB plus per-download fences). The wait uses the flush flag and a timeout and proceeds on timeout, by construction.
4. **The mark's position is approximate.** Worst case the effective bound is K fields ± a few draws. It cannot be less safe than the status quo by any amount that matters: the status quo's bound is 48 MB.
5. **ARUS off is a configuration, not a code path.** It restores pre-ARUS behaviour by rewriting variables before the pillars parse them — which means a boot with `arus=off` is only as pre-ARUS as the pillars' own off states are (each proven in its own milestone: dedup off = always dispatch; `renderscale=1` = byte-identical pre-M20 raster source; `asyncreadback=1` = the pre-M21 gates bit-for-bit; queue gate off = no marks, no fences). The one intentional asymmetry: an environment-set pillar variable survives `arus=off`. That is deliberate (explicit beats master), and the boot line names any variable it kept.

## 7. Owner test

Install 0.23-m22 over 0.22 (same signer, in-place upgrade; ISO and settings carry over). Same settings (GPU on, threads off), same short route: title ~20 s, village ~1 min, one real fight ~1 min, then share the boot log and the vu-capture folder. Four things to report:

1. **The boot log's ARUS and gate lines** — `[BOOT] settings: ARUS on ...` near the top, and `[gs-gpu] queue depth gate on: submitted work bounded to 2 fields in flight` when the renderer initialises. If either says *off*, an ini/env override reached the build and the run says nothing about M22.
2. **The fight FPS label and the worst frame** — the number on screen, and whether the fight *responds* differently: inputs landing when they are pressed, rather than seconds after, is the gate's whole point and is visible before any log is opened.
3. **Anything that behaves wrong** — a stall at a field boundary that was not there in 0.22, a load screen that hangs, an effect or reaction that changed. Describe it; that observation outranks the numbers.
4. **The boot log itself** — its `[gs-work]` lines carry the verdict: `present age` at or below ~3 fields in fight windows, fence ms replacing the old multi-second wrap waits, and `fields=` lower than 0.22's and *matching* the presents the screen actually showed.

To A/B the whole system off without reinstalling: add `arus=off` under `[video]` in `godhand.ini` and relaunch — the boot log's ARUS line flips to *off*, the four pillar lines corroborate (no dedup, native shading rate, `[l2h-path] mode=1`, queue gate off), and the build behaves as the pre-ARUS one did. To isolate pillar 4 alone, `queuedepth=off` instead leaves pillars 1-3 exactly as shipped.
