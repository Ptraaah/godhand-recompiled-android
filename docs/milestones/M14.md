# Milestone 14 (0.15-m14) — hunting the in-game starvation upstream, characterising the drains

Measurement only, like M13, plus the [gs-work] field-counter fix. Nothing in this
milestone changes a rendering, scheduling or transfer decision: every addition is a
counter, a timer, or a bitset that nothing reads except the window printers. The one
behaviour-adjacent change is where [gs-work] gets its field count from, and that is a
bookkeeping source swap, detailed below.

## What the M13 device run proved, and what it could not see

The owner's 0.14-m13 run (2026-11-02 11:42 WITA, godhand-boot_6_qscx.log) showed the
in-game shape precisely, on the worker side:

- Exploration: 36-39k prims per 5 s window but the GS worker busy only 2-3%, flush
  7-13 ms total, 8-10 presents per window. The worker crunches a field's draws in
  about a millisecond and then idles. The starvation is upstream of the worker.
- [frame-split] agreed from the host side: fields +6..+14 per window (1.2-2.8
  fields/s), 81-90% of frame time in the sync bucket (the 50 ms present poll cap
  saturating). One window burst to +98 fields, so field production can burst; this
  is pacing/coupling or scene-dependent guest cost, not a hard ceiling.
- Combat: 7-8 synchronous local-to-host transfers per window at 643-1036 ms per
  window total (~90-130 ms each), the EE parked in RunOnWorker for each one.
  downloadVram and readClut read zero times in every window, acquitted on device.

What no existing witness could say: what the EE thread, the VU worker and the GIF
stage were doing during those same windows. That is FRONT B. And the drains were
counted but not characterised — how big, and reading what kind of data. That is
FRONT A.

## The fixed field counter

Root cause of [gs-work] fields=0: GS::vblank() early-returns unless the backend is
raw-GIF, so the milestone-13 route (threaded wrapper's Op::VSync -> GPU backend's
NoteFieldBoundary) never fires with the GPU backend. [frame-split]'s alive fields
column counts EeScheduler's vsync tick, which the VBlankStart handler increments
immediately before calling GS::vblank().

Fix: GS::vblank() now notifies before the raw-GIF early return, so the count is
taken at exactly the point [frame-split] counts, once per guest field, for every
backend. GSGpuBackend::NoteFieldBoundary() only increments an atomic total
(fieldTotal); the [gs-work] window snapshots it and prints the delta, so the fields
column is the same quantity [frame-split] reports (window boundaries differ — 5 s
steady clock vs accumulated present intervals — so the two can differ by a field or
two either way, never by an order of magnitude again).

Routing note: the notification goes through dynamic_cast (front end -> threaded
wrapper -> GPU backend, with a direct cast for an unwrapped GPU backend), not a new
virtual on GSRasterBackend. gs_backend.h is in the game code's precompiled-header
chain (ps2_runtime.h -> gs_frontend.h -> gs_backend.h); adding a virtual there
planned a 13,120-step rebuild of the 10.6k generated TUs. The cast version touches
only .cpp files and non-PCH headers. The wrapper's old Op::VSync hook is still in
place; on the raw-GIF path its dynamic_cast finds no GPU backend, so nothing is
double-counted.

## FRONT B — [ee-work]: the guest side of the coupling

A new window line, printed from EeScheduler::run() on the same ~5 s cadence as
[gs-work] (windows with no fields and no guest time slide silently, same rule):

    [ee-work] fields=N (F/s) ee M MHz cyc/f=C disp=D guest G% idle I% |
      parked: sync n/ms present n/ms consume n/ms read n/ms other n/ms |
      callExec n/ms queueWait avg ms max ms gsIdle % |
      VU % (jobs) GIF % (jobs, MB) | dma n gif n vif n (MB)

Where each number comes from:

- fields / ee MHz / cyc/f / disp: the scheduler's own vsync tick, EE cycle counter
  and guest-dispatch counter, deltaed per window. cyc/f near the vblank period
  (~4.92M cycles at 60 Hz) means emulated time is advancing at field rate; cyc/f
  far above it means EE cycles are burning without fields coming out.
- guest %: wall time inside recompiled guest function dispatches (RAII timer around
  the dispatch try/catch in run()). VU0 is included by construction: in this port
  VU0 microprograms execute in EE context, there is no separate VU0 thread to meter.
- idle %: wall time inside waitForEvent() (the scheduler asleep waiting for the
  next deadline/event).
- parked split: time producer threads spent inside the threaded wrapper's Drain(),
  tagged by RunOnWorker call site — Sync, Present, ConsumeLocalToHostBytes
  (Consume), ReadVram, everything else (Other) — recorded through a new counters-only
  channel (include/runtime/gs/gs_coupling_stats.h). This is where the combat drains
  show up from the EE's side: a drain's cost appears both as guest time (the guest
  stub is inside a dispatch) and, separated out, here.
- callExec: count/time of Op::Call payloads executed on the GS worker — the worker-
  side view of the same parks (queue wait + callExec vs the producer's parked time
  separates waiting-for-the-worker from the work itself).
- queueWait avg / max: time chunks sat in the wrapper's queue between publish and
  pickup (per-chunk publish timestamps added to the wrapper). avg is per window;
  max is since boot (a max does not delta).
- gsIdle %: share of the window the GS worker spent waiting for work to arrive.
  ~97% alongside worker busy 2-3% in [gs-work] is the starvation signature stated
  from the other thread.
- VU % / GIF %: busy share of the MTVU VU worker and the GIF stage thread, from
  always-on accumulators added next to the existing env-gated PS2X_MTVU_STATS
  accounting in ps2_async_vif.cpp (job execution time, job counts, GIF job bytes,
  VIF1 job bytes enqueued). VU1 interpretation cost, if that is the wall, lands here
  and in the VU cycles-per-field the [mtvu] print already knows how to show.
- dma / gif / vif + MB: PS2Memory's existing atomic counters (DMA channel starts,
  GIF copies, VIF writes) deltaed, plus the asyncvif GIF/VIF byte totals — whether
  the guest is even feeding the pipeline in-game.

What each pattern convicts:

- EE saturated, VU the wall: guest % high, idle low, parked small, VU busy ~100%,
  ee MHz at or near the guest's demand, fields low with cyc/f high. The guest is
  running full tilt and the VU worker cannot keep up; the vblank-wait model then
  stretches fields exactly as observed. Next probe goes into the VU1 interpreter
  (slice size, compiled vs interpreted paths), not the GS.
- EE saturated, VU innocent: guest % high, VU busy low, GIF busy low. The cost is
  EE-side guest code itself (or its stubs) — read with disp and cyc/f: many cycles
  per field with few dispatches points at long-running guest loops (spinning on a
  flag the pipeline sets late is the known family here; hostCatchUp exists because
  of it).
- Parked on the worker: parked total (esp. consume/sync) is a large share of the
  window and matches [gs-work]'s flush/readData time. In exploration windows M13
  says the worker has almost nothing to do, so a big parked number there would be
  a surprise conviction; in combat windows it should confirm the drain cost from
  the EE side and size it against the whole frame budget.
- Pacing throttle: guest % AND idle % both middling with idle the larger, fields
  low, cyc/f near one field's worth of cycles per produced field, VU/GIF mostly
  idle, parked small. The scheduler is sleeping in waitForEvent while deadlines
  pace emulated time — then the question becomes which deadline host-times are
  being computed from what (vblank deadlines are cycle-scheduled; the wait burns
  the elapsed cycles on wake). The +98-field burst window argues the throttle, if
  present, is conditional (scene or state dependent), not a constant rate cap.
- Pipeline not fed: dma/gif/vif deltas near zero in-game while all busy shares are
  low — the guest itself is not submitting work (blocked on something outside this
  set of witnesses: an IOP/RPC wait, a semaphore, a missing interrupt). That
  outcome moves the probe to the EE wait reasons and the IOP, with fields as the
  trigger.

## FRONT A — the drains, characterised; the fast path, deferred on evidence

Instrumentation shipped in the GPU backend:

- A provenance bitset (renderedPages, 512 VRAM pages): set where GPU-side writes
  land — draw targets in prepareTarget (the same bounding-page set the hazard
  tracker computes, alongside writePages), framebuffer clears, local-to-local
  copy destinations, WriteVram pokes; cleared for a transfer's pages when a
  host-to-local upload begins (BeginTransfer, direction 0); reset on Initialize.
  Whole-page granularity, same as the tree's own hazard sets: over-marking is the
  safe direction. It is advisory only in this milestone — nothing reads it except
  the classifier below.
- localToHostTransfer() now classifies each synchronous transfer: provenance
  (source pages intersect renderedPages -> rendered; otherwise upload-only) x
  size bucket in pixels (<=64, <=1k, <=16k, <=64k, larger), with the whole
  transfer timed. Aggregates print as a second line, only in windows where a
  synchronous transfer actually ran, so title/menu output is unchanged:

    [l2h] sync reads: upload-only n=N ms sizes a/b/c/d/e | rendered n=N ms sizes a/b/c/d/e

Why no fast path ships in this build, even though the design is ready:

1. The premise needs the runtime profile, and the profile is what this build
   measures. M13's data says how OFTEN and how SLOW the combat drains are; it
   cannot say what they read. If the owner run of 0.15 shows rendered reads
   dominating — quite possible for combat effect readbacks — a shadow fast path
   would serve nothing, and per the milestone rule an improvised rendered-read
   shortcut would change guest-visible semantics.
2. There is no existing CPU shadow to serve from. In GPU mode the front end does
   NOT mirror uploads into its local memory (GS::processImageData only forwards
   to the backend), so the "CPU-side shadow of upload-written data" would be new
   machinery: a backend-owned 4 MB mirror fed by UploadImage/BeginTransfer with
   the transfer addressing reproduced exactly, gated by the provenance bitset
   (serve only pages the bitset calls upload-only; any GPU-side write to a page
   invalidates it — the bitset maintenance points above are exactly that
   invalidation, already shipped and observable via the [l2h] classes). Building
   it blind, before knowing upload-only reads dominate, risks guest-visible byte
   differences for zero proven gain.

Decision rule for the next milestone, decidable from one owner run: if upload-only
reads carry most of the drain milliseconds, implement the shadow behind the
provenance gate (formats restricted to those whose GPU copy-out conversion is
provably byte-identical to a CPU GSMem read — CT32/CT24 first). If rendered reads
dominate, the [l2h] size/ms profile says what the game is likely doing (few large
reads ~100 ms each looks like full-pipeline-drain latency on a big region, not
byte cost: at these sizes the map read itself is small; the money is the
flushFor(3) + implicit sync ahead of it), and the candidate designs — widening the
async readback cache (one-field-late semantics the tree deliberately scoped to
tiny depth blocks), or a fence-scoped partial flush — get weighed with their
guest-visible risks written down before anything ships.

## Owner test steps

Same drill as M13, one run, GPU renderer ON:

1. Title screen: sit on it ~20 s (healthy baseline: [ee-work] should show ~60
   fields/s, guest/idle split like a normal loop, VU/GIF modest).
2. Load in and walk the village for about a minute without fighting (the
   starvation case: compare [ee-work] guest/idle/parked and VU% against
   [gs-work]'s starved worker in the same windows — the log timestamps align).
3. Pick a real fight and stay in it about a minute (the drain case: [l2h] lines
   appear in [gs-work] windows; [ee-work]'s parked consume should move with them).
4. Share the boot log as usual.

Reading the run back: [gs-work] fields should now track [frame-split] (both count
the same tick). The conviction table under FRONT B says which pattern the village
windows match; the [l2h] split decides the FRONT A next step by the rule above.
