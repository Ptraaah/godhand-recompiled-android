# VU-join test build (0.29-m28-vujoin, versionCode 36)

**Provenance — read this first.** Unlike m27 (whose core was b5's
byte-identical `libgodhand.so`), this build's core is the restored
mainline core plus the live-register-reads patch from the VU-join
stage (PATH-VUJOIN.md) — the same core provenance that booted on
Pablo's device in the m25 native build: m25 shipped the pre-change
restored-mainline core (`b1f3bf2bb62584affb38f54bebfb845f`,
99,711,576 B), and this build's core is that same mainline plus the
4-file live-regs patch (`82fc27c5437d15144387b0cd0a384699`,
99,713,624 B, +2,048 B — exactly the stage's reported delta). So
this is a **two-variable** build against m27 by design: the core
lineage changed (disclosed here, not hidden) *and* the lever is in
it. Everything else is m27's bytes: the shell/defaults, classes.dex,
resources.arsc, libshaderc and — critically — the bridge are taken
from the m27 APK, so the GS side is the approved pipelined bridge
byte for byte. Attribution between the two variables is provided by
the kill switch `PS2X_VU1_LIVE_REGS=0` (restores the m27-style
draining register reads in this same binary) and by the stage's
`[vu1] joins:` attribution line. Method: binary repackage of the
m27 APK (no payload compilation) — manifest version fields patched
in the binary AXML (string-pool rebuild + in-place int patch;
`aapt2 dump xmltree` diff of m27 vs this manifest shows the two
version attributes and nothing else), payload entries stored,
manifest deflated, entry set and order identical to m27,
`zipalign -p 4`, signed with build-tools 36.0.0 and the shared
debug keystore (`recomp-android/probe/debug.jks`). All hashes below
were computed from the *final signed* APK, extracted and compared
file by file.

## The lines that arbitrate the device run (from PATH-VUJOIN.md §5)

No performance outcome is claimed here; the device boot log
decides. Same protocol as m27 (cool phone, the pathb5 route, wide
off, pipeline on at depth 2). Baseline: M27-LOG-ANALYSIS.md
(crowd `[vu1] join_wait` 507–1,694 ms per 5 s window; crowd
fields/s 39–49; pipeline `ahead_max` never above 1).

- **Boot/config proof:** `[pcsx2-gs] pipeline on: ... depth 2
  fields` must still print (bridge unchanged — its absence
  convicts packaging or an ini-seeded `PS2X_GS_PIPELINE=0`); the
  `[BOOT] settings` lines should show the renderer/scale state of
  the known pathb5 route.
- **`[vu1] join_wait` (the conviction metric):** crowd windows
  fall from 507–1,694 ms toward the light-window scale —
  **target < ~150 ms per 5 s window**. Light windows stay at
  35–45 ms or below.
- **`[vu1] joins:` (the new attribution line):** with the lever
  on, **`regread` ≈ 0** outside download moments. Where the
  remaining join_wait sits is the verdict's second half: `idle`
  growth means the vblank barrier inherited the wait;
  `regwrite`/`vumem` growth means the game's true dependencies
  live there. Any of those is a successful measurement even if
  fields/s disappoints.
- **Fields/s:** crowd windows rise from 39–49 toward **55–60**;
  `[ee-work]` guest% rises as parked time converts to execution;
  `[frame-split]` presents avg falls toward ~17 ms, sync share
  back under ~90%.
- **`[pathb] pipeline: ahead_max` touches 2 in crowd windows** —
  the pipeline finally being fed faster than it drains is the
  proof the producer side was unblocked. `park` stays a small
  fraction of the old drain totals; **`dropped_captures` stays
  0**; harvest `readback_wait` stays in its 67–106 ms family.
- **Audio:** no separate metric exists; choppiness should track
  the crowd fields/s rise (SPU2 is slaved to guest timing).
- **Kill switches / A/B attribution:** `PS2X_VU1_LIVE_REGS=0` in
  the external `godhand.ini` restores the draining register reads
  — comparing the two logs in this same build separates the
  live-regs lever from the core-lineage change disclosed above.
  `PS2X_GS_PIPELINE=0` re-isolates the bridge stage (runs the
  Direct twins, the reconstructed b5 behaviour);
  `PS2X_GS_PIPELINE_DEPTH=n` (1–8, default 2) remains the
  pipeline latency knob.
- The owner-ini caveat applies unchanged: an external
  `godhand.ini` renderer line overrides the variant seed, so the
  ini must be in the known pathb5-route state for a clean verdict.
